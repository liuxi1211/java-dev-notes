# 电商匿名访问限制与限流体系设计

> 沉淀自一次关于电商商品详情接口风控的讨论：匿名登录限制、IP 限流、强制登录三者之间的关系与 PC 浏览器场景的落地方案。

## 一、核心结论：三个概念不是一回事，但同属风控体系

| 机制 | 计数维度 | 目标 | 性质 |
|---|---|---|---|
| 限流告警 / IP·用户级限制 | IP、用户ID、QPS | 防爬虫、保护后端资源 | 技术防护 |
| 匿名登录次数限制 | 匿名身份（设备指纹/游客token） | 匿名流量可追溯、可管控 | 业务/风控策略 |
| API 通用限流 | 用户ID / token / 接口 | 保护后端资源 | 基础设施 |

- 三者是**不同计数维度的限流，同一体系的不同层**，生产环境叠加使用，不是二选一
- 典型分层：`CDN/WAF（IP限流）→ 网关（通用API限流）→ 业务层（匿名身份计数）→ 风控层（指纹评分、行为验证码）`
- **不要指望上了强制登录就能让限流告警消失**——告警问题要靠限流手段解决

## 二、强制登录防不了爬虫访问，但能抬高成本

爬虫应对强制登录的三条路，成本递增：

1. 批量注册账号（接码平台）→ 注册环节可做行为风控
2. 账号池租赁（黑产现成账号池）→ 单账号成本从 0 变几分~几毛
3. 养号（长期维护）→ 成本最高

关键转变：流量从"匿名不可追踪"变成"带账号来"，于是可以按账号维度限流、做行为分析（真人浏览有停留/翻评论，爬虫匀速翻页）、异常账号可封禁。

**风控的本质是经济学，不是密码学**：攻击成本 > 收益，攻击自然消失。前端校验都是纸糊的，但纸糊的门也能挡住顺手牵羊的人；真正的保险柜在业务和资金层（奖励延迟发放、提现门槛、实名认证）。

## 三、攻击者分层决定防御目标

| 攻击者 | 能力 | 匿名限制效果 |
|---|---|---|
| 普通用户（薅羊毛小白） | 手动、最多换 IP | 完全防得住，占实际流量 90%+ |
| 脚本小子 | 现成脚本 + 代理池 | 指纹+多维度计数能防大部分 |
| 专业黑产工作室 | 群控/农场机/接码/打码 | 单点校验失效，靠成本对抗 |

匿名限制的目标：**用 20% 的成本拦住 90% 的低级滥用**，不是防住专业逆向。

## 四、PC 浏览器匿名身份计数方案（重点）

PC 是匿名标识最难做的场景（无原生设备 ID、隐私插件、无痕模式），方案 = 四层叠加。

### 第 1 层：服务端下发 guest_id（主体）

- 首次访问服务端生成 UUID，`Set-Cookie: guest_id`，属性 `HttpOnly + Secure + SameSite=Lax`，有效期 1 年
- 服务端生成而非前端 JS 生成：HttpOnly 无法被普通 JS 读取，增加伪造门槛
- 弱点：清 Cookie / 无痕 / curl 不带 Cookie → 每次都是新身份

### 第 2 层：浏览器指纹（对抗清 Cookie）

采集弱特征组合：UA、语言、时区、分辨率、色深、Canvas 指纹、WebGL、AudioContext、字体列表。组合区分度可达十几万分之一。

- 方案：FingerprintJS（开源可自建）、商业方案（同盾、数美）
- 指纹不直接当身份，做**关联补漏**：guest_id 丢失时算指纹，指纹今天已计过数则继承旧计数

### 第 3 层：IP 兜底熔断

IP 不能单独当身份（公司/校园出口共享），只做粗粒度熔断：单 IP 匿名详情页请求超阈值（如 5000/天）→ 直接验证码或强制登录。

### 第 4 层：接口签名 + 行为验证码（抬高脚本成本）

- 参数带 `timestamp + nonce`，sign key 混入 guest_id，签名算法放 JS 混淆代码（AST 混淆）
- 服务端校验签名，错误/重放直接拒绝
- 把"清 Cookie 绕过"升级为"逆向 JS 绕过"，成本提升一个量级

### 计数实现（Redis，多维度"或"判断）

```java
// Java 17+ / Spring Data Redis
long guestCount = incrWithDailyExpire("guest:view:" + guestId);        // 主计数
long fpCount    = incrWithDailyExpire("guest:fp:" + fingerprintHash);  // 指纹计数
long ipCount    = incrWithDailyExpire("guest:ip:" + clientIp);         // IP 兜底

if (guestCount > THRESHOLD_NORMAL) {   // 软阈值如 30 次
    return needLogin();                // 弹登录引导，可恢复拦截
}
if (ipCount > THRESHOLD_IP) {          // 硬阈值如 2000 次
    return challenge();                // 验证码挑战
}
```

工程细节：

1. **按自然日重置**：key 带日期 `guest:view:{guestId}:20260820`，TTL 48h，跨天自然切换
2. **阈值取正常 P99 的 2~3 倍**，先"引导登录"再"硬拦"
3. **多维度或判断**：Cookie 被清了指纹计数还在，指纹被改了 guest_id 还在

### 体验建议

- 软硬两级阈值：软阈值弹登录（可恢复），IP 异常才上验证码
- 登录引导要顺滑：扫码 + 验证码登录
- 别用直接 403：共享 IP 误伤很伤体验，优先"强制登录"这种可恢复拦截

## 五、整体架构

```
浏览器
  ├─ Cookie: guest_id (HttpOnly, 服务端发)
  └─ 前端: 指纹采集 + 接口签名
        ↓
网关/中间件
  ├─ 签名校验（防脚本直调）
  ├─ IP 维度限流（防爬兜底 + 告警）
        ↓
业务层
  ├─ guest_id 缺失 → 指纹关联旧身份
  ├─ Redis 多维度计数（guest_id / 指纹 / IP）
  ├─ 超软阈值 → needLogin，前端弹登录引导
  └─ 超硬阈值 / IP 异常 → 验证码挑战
```

## 六、对抗专业黑产的完整体系（端到端）

1. 端侧加固军备竞赛：加固 SO、VMP 混淆、native 指纹、模拟器检测
2. 风控引擎实时打分：行为序列（滑动轨迹、点击间隔、停留时间、传感器）
3. 设备关联图谱：同设备历史多账号 → 关联标记
4. 收益端兜底（最狠）：奖励延迟发放、提现门槛、实名——假设前端必被攻破的兜底设计
5. 灰度与熔断：活动异常领取率飙升自动熔断

## 七、有了 IP 限流，还要账号维度限流吗？（防爬视角）

**要，且账号维度才是主战场。** IP 限流只对"单机固定 IP 的傻爬虫"有效：

| 绕 IP 手段 | 黑产成本 | 效果 |
|---|---|---|
| 代理 IP 池 | 几块钱/天，几万 IP | 单 IP 请求量降到阈值以下，IP 限流失效 |
| 短效代理（秒级切换） | 按量付费，单价极低 | 每个 IP 只发几个请求，计数器永远是 1~2 |
| 家庭宽带拨号重连 | 0 成本 | 换 IP 重来 |
| 分布式肉鸡/农场机 | 一次性投入 | 天然海量 IP |

核心逻辑：

- **IP 是消耗品（几厘/次），账号是资产（几分~几毛，还要养、封了要补）**。账号限流把对抗从"廉价 IP"升级到"昂贵账号"，成本抬一个量级
- IP 限流限制的是"每个 IP 的速率"，**不限制总流量**——爬虫加 IP 线性扩容；账号限流限制"每个账号总量"，配合账号获取成本才能约束**总抓取量上限**
- 账号可封禁、可追溯：封 IP 爬虫无感（自动换），封账号是黑产真金白银的损失
- 反向收益：IP 限流会误伤共享出口真人，账号维度天然精确到人

## 八、匿名入口是闸门，不是后门（压力传导链）

"详情页匿名可访问，爬虫不登录怎么办？"——这正是强制登录要消灭的漏洞：**匿名访问给免费额度（正常人够用），超额必须登录**。爬虫只���三条路，每条都有成本：

```
详情页匿名可看 N 次（如 30 次）
    ↓ 想多抓
选项1: 登录 → 账号成本 + 账号限流 + 可封禁
选项2: 伪造匿名身份重置计数 → 指纹工具成本 + 代理成本 + 签名对抗 + IP 熔断风险
选项3: 一个身份只抓 N 次 → 总量被锁死在 (身份数 × N)
```

| 要重置的维度 | 绕过成本 |
|---|---|
| guest_id (Cookie) | 清 Cookie，成本 ≈ 0 |
| 指纹 | 指纹浏览器（AdsPower 等），几十元/月 |
| IP | 代理池，几厘/次 |
| 接口签名 | 必须执行/逆向 JS |

单独绕任何一层都便宜，**同时绕三层 + 保持签名正确 + 不触发 IP 熔断**，单次成本已是纯代理池方案的很多倍。设计精髓：不需要完全阻止爬虫，只需让"每抓一页的边际成本"高于数据对它的价值。

三件套缺一环就漏：只做 IP 限流不强制登录 → 爬虫匿名+代理池；只强制登录不做账号限流 → 账号池无限抓；三者齐上才闭环。

## 九、IP 超限后强制登录：共享出口的最佳实践

学校/公司/移动网络出口几百真人共享一个 IP，硬拒绝（403/429）会无差别误伤。更优方案：**IP 超限后不拒绝，而是把匿名请求升级为强制登录**——把"IP 维度的群体嫌疑"转化为"账号维度的个体验证"。

```
IP 未超限   → 一切正常，匿名可访问
IP 超软阈值 → 匿名请求强制登录；已登录请求正常放行（走账号维度限流）
IP 超硬阈值（如 10 倍）→ 验证码 / 拒绝（大概率不是学校）
```

设计要点：

1. **强制登录是"可恢复的拦截"**：真人花 10 秒自证清白，体验损失可控；比验证码温和、比封 IP 精确
2. **阈值按"真人叠加"定**：出口型 IP 正常 P99 × 2，宁可偏高漏掉爬虫，也别让学校天天弹登录
3. **精准豁免**：IP 触发后只拦匿名流量，已登录用户无感
4. **防蹭待遇**：黑产会用住宅代理伪装"共享出口"，所以超限后的登录必须真强制（不登录不给内容）；真学校出口流量有多样性（不同时段/UA/行为/有人登录），住宅代理流量单一（匀速、同 UA、从不登录）
5. 登录后转入账号维度限流，登录不是免死金牌

## 十、防御层与友好 AI 爬虫的兼容

指纹 + 签名防御会"无差别打击"友好 AI 爬虫（GPTBot/ClaudeBot 等无 Cookie、不执行 JS、无指纹、数据中心 IP）。逐层影响：Cookie 计数天然兼容（计数永远不涨）；指纹（空指纹被判可疑）、签名（拿不到 sign 直接被拒）、IDC IP 策略（误伤）会挡死。

解法：**不削弱防御，在防御层之前加"验证过的白名单通道"**：

1. **robots.txt**：君子协议，GPTBot/ClaudeBot/PerplexityBot 都遵守，Allow/Disallow 按业务决策
2. **UA + 反向 DNS 双向验证**：OpenAI 验 `*.openai.com`、Google 验 `*.googlebot.com`，不能只看 UA（可伪造）；验证通过跳过签名/指纹/登录，走单独限流阈值
3. **给 AI 单独的结构化通道**：`llms.txt`、商品页嵌 Schema.org JSON-LD、内容 API/Feed——真人走浏览器+防御，AI 走白名单+结构化数据，互不干扰

业务决策三分支：希望被 AI 索引（引流）→ Allow + 白名单 + JSON-LD；不希望（核心资产）→ Disallow + 正常拦截；想收费可控 → 授权 API（Reddit/StackOverflow 模式）。

## 一句话总结

**Cookie guest_id 做主体、指纹做关联补漏、IP 做兜底熔断、签名+验证码抬高脚本成本**；匿名限制只是最外层过滤器，真正的对抗靠端侧加固 + 风控引擎 + 资金端兜底的完整体系。IP 超限后的强制登录把限流从"惩罚机制"变成"分流机制"，是共享出口场景的最佳实践。
