
## 目标：
我们搜索小组现在缺少一份公共的缓存框架，现在项目中用到的缓存都是在方法中独立定义，各有各的写法不统一
而且自己写的缓存功能越复杂漏洞就越多，所以我需要系统性调研下业界缓存的实现标准和注意事项，给后续搜索组的缓存使用定一个通用标准

### Step 3.5｜25 个参数逐个深挖：默认值取舍、设计动机、代价与替代

这一块是最后那份设计文档占比最大、也最有深度的内容，过程其实费了不少劲，不是一轮就搞定的，主要就是针对每一个参数进行挖掘，因为有很多参数我自己也不清楚设计用意

第一轮让它「按设计取舍角度逐个讲 JetCache 每个参数」，拿到的结果结构非常乱：有的参数写了一两百字（比如 expire），有的参数（比如 cacheNullValue、condition）就一句话带过，而且每个参数讲的角度也完全不一样——有的参数只讲了利弊，没讲为什么默认值这么选；有的参数讲了为什么需要，没讲业界有没有别的做法。

后来我就自己总结了一个**四件事模板**，要求每个参数回答时必须按顺序覆盖：为什么需要这个参数 → 为什么 JetCache 这么设计（它在权衡什么）→ 好处坏处分别是什么 → 业界其他实现是怎么做的。\*\*这个模板不是拍脑袋出来的，是因为第一轮输出这四点缺什么的都有，我索性把最容易漏的四个点固定下来。\*\*而且明确要求每个参数，不管这个参数看起来多简单，四件事一件不许少。

有了这个模板之后，参数级的输出终于稳定了，每个参数都能输出差不多深度的内容。下面举几个深挖过程中最有代表性的参数例子，还原一下当时的提问推进过程：

**参数一：expire（过期时间）—— 全局和注解层都没设时为什么是"永久不过期"**

第一轮拿到的说法非常简单：过期时间单位毫秒，没设时取全局配置，全局也没设时默认无限大。等于什么都没讲。

我当时追问了三个方向：

- 「无限大是真的永久，还是某个大数字？具体是多少？」

- 「为什么 JetCache 要选择『没设就永久』这种默认策略，而不是强制用户必须填，或者给一个 24h 安全兜底？」

- 「业界其他缓存框架（Caffeine、Spring Cache 默认值、Redisson）都是怎么做的？」

最后逼出来的结论深度比第一轮高一个档：

1. "永久"其实不是真的永久，内部是一个 2^62 左右的毫秒数，换算成年大概是 68 年。这是实现细节上的一个小技巧，不用单独判断 infinity 分支，但写文档时不能真当永久写。
2. 默认值选"无限大"本质上是**最小惊讶原则和安全性原则之间的妥协**。强制必填会让很多写快速 Demo 的用户第一时间报错觉得不好用，给 24h 兜底又可能在用户没注意的情况下把热点 key 写死 24 小时过期造成 24 小时后的集中雪崩。无限大等于把"你自己决定什么时候过期"的责任完全甩给用户——不是最佳实践，但反过来说用户忘了设时出了问题也只能怪自己。
3. 业界另外两条常见路径：Spring Cache 默认不过期（和 JetCache 一致），Caffeine 本地缓存默认也不过期，但是 Caffeine 在文档最显眼的位置会提醒你"过期时间和最大条数必须设至少一个"。业界相对激进的做法是 Guava Cache 给了最大容量兜底（没设的话不报错但容量很小相当于没开）；还有一些内部框架是写死强制校验，没设直接抛异常启动失败——这是最安全但最不友好的方式。

这个参数最后成了设计文档第一章里默认值哲学的核心案例。

**参数二：cacheType —— 为什么默认 REMOTE 不默认 BOTH**

第一轮说 REMOTE=只走远程，LOCAL=只走本地，BOTH=两级都用，默认 REMOTE。跟没说一样。

追问：「BOTH 是本地 Caffeine + 远程 Redis，性能上读请求本地命中就不走 Redis，应该明显更快啊，为什么不直接默认 BOTH？是性能收益没那么大还是副作用扛不住？」

结论：

1. 性能收益确实有，但只在"命中率极高的热点 key"场景下才显著，一般场景读延迟 Redis 本身就是亚毫秒级，本地再省那点用户根本感知不到。
2. 副作用才是决策关键：BOTH 模式引入了 L1 跨节点一致性问题，而 L1 一致性的处理要么靠 Pub/Sub 广播失效（丢消息可能导致脏读窗口），要么靠版本号校验（每个 key 多一次远程读取开销），要么靠短 localExpire 自愈（等于 L1 命中率被人为压低）。这一套的复杂度和踩坑概率远远高于它带来的收益。
3. 默认值选 REMOTE 的根本哲学：\*\*新手第一次用 JetCache 时，最优先的是不踩坑，不是跑得快。\*\*写个 DEMO 用 BOTH，不小心把订单金额字段做了 L1 缓存，订单状态变更后没及时失效，用户看到旧金额直接下单，这种事故是可预期的。REMOTE 慢 1ms 但少 90% 的踩坑概率，作为默认值更合理。

**参数三：localLimit —— 本地缓存最大条数为什么默认 200，不是 2000 也不是 20**

第一轮只说了"本地缓存条目上限"。这么一个不起眼的数字，深挖起来内容非常多。

追问：「200 这个数字怎么来的，为什么不是 2000 或者 20？是经验值还是有计算依据？」

得到的内容：

1. 200 是偏保守的堆内安全阈值，按一条缓存 value 平均 1KB 估算，200 条就是 200KB 左右，堆压力基本可以忽略。
2. 这个数字对应的隐含前提是"本地缓存只存最热的 top N hot key"。如果有人误以为 200 是推荐值然后照着开 2000，一条 1KB 就是 2MB，好像也不大——但真实的线上 value 平均大小经常能到 5~~10KB，2000 条就是 10~~20MB。
3. 更严重的是 JVM 层面：一台 8G 堆的服务节点，老年代一般 3\~4GB，20MB 就是 0.5%\~1% 看起来也不大。**但是缓存对象一般都是长命对象，会直接进老年代，而且 key 分布离散时会导致很多不可回收的碎片，最后增加 CMS / G1 的老年代回收频率和停顿时间。** 这个坑 90% 的人第一次用本地缓存都不会考虑，等压测时看到老年代频率异常高都想不到是 localLimit 开太大了。
4. 选 20 就太保守了，20 条热点 key 对于稍微有点商品的电商场景都不够用，等于本地缓存白开。200 是两边各打 50 大板的中间数，不完美但两边都不致命。

这个结论后来直接进了设计文档的 BOTH 模式落地参数建议一节。

**参数四：@CachePenetrationProtect（单飞）开关 —— 为什么默认关，而且只做单 JVM 不做分布式**

第一轮说了开启后同一 key 缓存未命中时只让一个线程回源，其他线程等待，防止击穿。但完全没解释为什么默认是关闭的。

追问两条：

- 「防止击穿难道不是缓存框架的基本职责吗？为什么默认关闭，反而要让用户主动打开？」

- 「为什么 JetCache 只在单个 JVM 内做单飞，真正的击穿场景一般是大促时所有节点同时 miss 同一个热点 key，不应该分布式单飞才有用吗？」

结论的信息量非常大：

1. 「99% 的 key 根本不值得防击穿。」单飞加的 synchronized / 锁会让每一次缓存未命中都带来一次锁竞争开销，对于 99% 的低并发 key 来说，这点开销比回源还慢。默认值策略是「10% 的热点 key 需要单飞 → 让用户自己选着开 → 剩下 90% 的 key 不白受锁开销」，而不是反过来默认全开浪费性能。
2. 还有一个没公开提的隐含原因：嵌套调用场景下的死锁风险。JetCache 的单飞是基于方法级 synchronized 监视器的，如果方法 A 里的缓存调用触发单飞锁，里面又嵌套调用了另一个也带单飞注解的方法 B，锁顺序搞反时理论上会死锁。这种 case 概率极低，但一旦发生就是整条线全 hang。默认关等于把「你确认你的调用链上没有嵌套死锁」这个确认动作交给了用户。
3. 为什么不做分布式单飞：分布式单飞牵扯的东西太多了—— Redis 锁怎么续约（没续约刚好回源超时就炸了）、锁超时时间怎么定（定太短回源还没结束锁过期了）、可重入性怎么支持（同一个线程递归调用同一 key 时不能死锁）、失败降级策略（锁拿不到是等还是直接回源）。这些东西不是几个类就能写完的，每个点都能单独写一个模块。JetCache 的定位是「轻量级库」而不是「完整缓存平台」，所以把这块留给上层应用或者其他更重的框架来做，是定位上的有意识选择不是能力缺失。

**参数五：cacheNullValue —— 防穿透需要缓存 null 值，为什么默认 false**

第一轮的解释是「是否缓存 null 值，防止穿透」，默认 false。

追问：「防穿透的基本手段就是缓存空值，为什么默认反而关了。是缓存空值有什么我没看到的代价吗？」

结论：缓存空值的核心矛盾是\*\*「防穿透」和「数据新鲜度」的二选一\*\*：

1. 打开时，某个 key DB 里确实不存在，缓存了一个 null，TTL 期间即使写入了新数据，缓存层还是返回 null，这段时间用户就看不到新写入的数据。等于"这个 key 不存在"的假象在 TTL 窗口内一直维持。
2. 默认 false 就是 JetCache 在这条矛盾里选了新鲜度优先：防穿透你自己按需开，我不替你背"用户看不到新写的数据"的锅。
3. 业界其他路径：有的框架选择 null 值用单独更短的 TTL（比如正常值 30min，null 值 2min），两边各让一步——防穿透的能力有了，最多 2min 的写不进去窗口。
4. 更工程化的做法：区分「真的不存在」和「暂时查不到」，返回两种不同类型的 sentinel value（比如 `AbsentValue` 和 `TombstoneValue`），TTL 策略不同。JetCache 没做这块是因为实现复杂度 + 序列化兼容性代价过高，属于「不值得为了 5% 的场景让 95% 的用户多理解一个概念」。

这五个参数深挖完之后，后面剩下的二十个参数处理起来就有模板了，速度和深度一起上去了。最后文档里的参数章节就是按这轮整理出来的内容直接写的。

#### 案例 A：挑战 @CacheRefresh 定时器设计，提出 SWR 替代思路

当时的提问大致是这样的：

> 这个 @CacheRefresh 的设计思路我不认可，这种模式如果 key 多基本上就是死局，为什么不用另一种——每个缓存写的时候记录过期时间，每次访问时判断过期时间是否到了阈值，到了就启动异步线程刷新，防止定时器数量爆炸的问题。

这一轮不是被动问「@CacheRefresh 有什么用」，而是带着自己已经想清楚的问题和替代方案来的。千万级 SKU 场景下 per-key 定时器的资源爆炸是实打实的问题，SWR 思路也是自己提前推演过可行的，所以不是瞎质疑。

第一次拿到的答复基本认可了这种 Stale-While-Revalidate 模式，也说了 JetCache 选定时器是因为精度高语义简单。但是答案有两个明显的偏向：一是只讲了 SWR 的好处（零常驻资源、key 数可扩展），对 SWR 的代价完全没展开，stale read 窗口、冷 key 长期旧值、分布式去重锁加失败重试加线程池隔离这套实现复杂度根本没提；二是没讲定时器模式在什么场景下其实更合适——字典表、配置项这种几十到几百个 key 又对刷新精度有要求的场景，定时器是最简单也最正确的选择，SWR 反而属于过度设计。

后面两轮追问补了回来。先问了 SWR 有没有现成的框架可用、1000w SKU 量级怎么落地，逼着对方回答实际路径而不是空夸优点；再追加了两道硬要求：一是自己反驳自己的结论，构造三个场景 SWR 不如定时器，二是两种模式的利弊对照必须对称列出来好处坏处各至少五条，不许一边倒。

最后拿到的结果除了补齐 SWR 的坏处和定时器的反向适用条件之外，还挖出了一个比较极端的反例：商品详情页做 SWR 时，如果页面里内嵌了实时库存字段，返回旧库存的 stale read 直接等于用户下单时超卖。这种场景不能把整页一起做 SWR，必须把库存字段拆成独立 key 走短 TTL 实时查询，不进 SWR 机制。这个反例最后写进了设计文档「SWR 禁止使用场景」一节，也是后面逐场景决策表的重要判据。

***

#### 案例 B：抓回答前后矛盾追问 CF 模式的推荐理由

事情起因是讨论单飞两种实现方式时，同一段回答里前后出现了矛盾的说法。前面说推荐用 CompletableFuture 模式，理由是扩展性好，synchronized 属于老写法；后面分析同步阻塞调用场景时又说 99% 用户都是同步接口访问，CF 模式在延迟上没什么优势。

当时直接抓住这个矛盾问了一句：

> 你刚说 99% 用户都是同步访问接口、用 CF 没好处，为什么还推荐我们用？我们就是 100% 同步调用。

这么问的好处是不用凭空质疑结论，直接拿对方自己写出来的两处矛盾让它解释为什么结论还是推荐 CF。含糊其辞是不可能混过去的。

修正后拿到的结论和之前差别不小：
第一，在 100% 同步阻塞调用场景下，延迟层面 CF 模式确实没有优势，低并发短回源的情况下 synchronized 反而可能略快，原因是 JVM 层对偏向锁和适应性自旋的优化强度非常高。
第二，CF 模式真正的不可替代优势其实是可观测性。出现问题时 inflightMap 里面可以直接看到卡在刷新上的具体 key 名称、卡住的时间以及 waiter 数量，这对于线上排错的价值非常大；而 synchronized 只能看到 monitor 对象地址，几乎挖不出什么有用的信息。
第三，顺带还暴露了一个 CF 模式独有的暗坑：如果回源线程抛的是 Error 而不是 Exception，并且没有被正确 catch，CompletableFuture 就永远不会 complete，inflightMap 里对应的条目会永久驻留变成内存泄漏。这个极端边界 case 在最初推荐 CF 的时候是绝对不会主动提到的。

***

#### 案例 C：反方立场论证纠正选型倾向

选型阶段一开始是略微偏向从零自研的，主观感觉 3 个月工期可以接受。后来让对方站在「坚决反对自研、坚持 JetCache + 少量二开」的立场给三条最强攻击性论证，每条要求带量化对比不准讲空话。其中第三条论证印象比较深：

> JetCache 经过 8 年线上打磨，单测覆盖率 85% 以上，bug 率在每百万次调用个位数级别；从零自研 3 个月工期，单测和边界覆盖撑死做到 60%，bug 率的数量级差距估计在百倍左右，不是两倍。首发上线大概率要再花 1 个月集中处理线上边界 bug，等效工期 4 个月，而且稳定性保障水平还是差一个数量级。

这个数量级差距之前从来没有认真量化过，看完之后直接就打消了从零自研的念头。最终选型定为 JetCache + 少量自研 SWR 切面。

这里有个小前提要提一下：正反方辩论最好是两个独立会话分别立论，不要在同一个会话里让同一个模型先当正方再当反方。同一个会话里连续切换立场，模型很容易倾向和稀泥——两边各打五十大板然后说视情况而定，那就达不到纠正偏好的效果了。独立会话分别输出再人工拼起来做对照卡，效果最好。

***

### Step 5｜第一次汇总：方向直接跑偏

聊完 8 轮左右的聚焦内容后，让对方把讨论过的设计取舍系统性整理一下，对接 JetCache 的设计要素不要遗漏。当时没有给组织结构方面的要求。

拿到的结果是一份《落地全景》型的文档，里面包含了 Spring Boot yml 配置写法、SWR 切面 300 行完整代码、故障排查表、业务场景逐场景决策表，全是我不要的使用层面的内容。原因其实很简单：没有结构锚点的时候，输出方一定会默认写受众最广的通用内容形态，也就是实战使用手册而不是设计方法论。这是一个默认倾向，不是个别错误。

后来没有选择在原有文档上修补，直接推倒重来。下了从零重写的指令，并同时给了三条硬要求：一是删除清单，实战代码、yml 配置、业务决策、故障排查这类使用层面的内容全部移除；二是组织结构锚点，目录按 JetCache 注解分章节，逐注解逐参数分析；三是最小单位输出模板，每个参数固定四段结构，分别是为什么需要、为什么这么设计 trade-off、利弊对照、业界替代实现。三条全是没有歧义的硬要求，不许模糊理解。

重写的方向一次性纠正到位。

***

### Step 6｜独立模型审核 + 人工终查

审核环节是单独做的，三个步骤：一是开全新的会话，不加载任何上文内容；二是换另一个模型来担任审核角色，不用写文档那一个；三是给审核设定了四个维度的检查要求：事实错误、结构缺项、前后矛盾、深度与废话占比，扣分点必须精确到章节号和原句，不能含糊。

审核的实际产出是：4 处事实错误清零、7 处完整性遗漏补齐、2 处前后章节的矛盾统一。举两个具体的例子，一个是 @CachePenetrationProtect.value 的注解开关默认为 true，但全局 penetrationProtect 开关默认为 false，这个反转关系原文写得不清楚容易误读；另一个是 Pub/Sub 在 Redis Cluster 模式下的 fan-out 带宽爆炸问题，原文遗漏了。这两个都属于原模型的知识盲区，同一个模型再审多少次也审不出来。


全过程连同审核大约花了2个小时。同等质量如果纯手写，估计 3 天起步，而且还不一定能覆盖自我反驳、反方论证这些非直觉层面的广度内容。
