# A2A 落地边界与多 Agent 决策框架

> 本篇源于我对 A2A 的一个尖锐质疑：
> **"A2A 是多智能体的协调，但 Harness 主要是讲把一个 agent 约束好。如果你一个 agent 都做不好约束，讲那么多 A2A 干什么？现在场景有那么多需要 A2A 的地方吗？"**
>
> 本篇的结论：这个质疑本质成立——A2A 被过度营销，真实需求区间很窄。但要先把一个概念混淆拆掉：**多 Agent ≠ A2A**。拆掉之后，问题会变成一个清晰得多的问题：什么情况下该拆 agent，拆到哪一层。

核心论点：
- **"多 agent 协作"绝大多数是单 harness 内的 subagent 编排（同进程），根本不涉及 A2A 协议**
- **A2A 的真实价值区间只有一个：跨组织边界**（跨供应商、跨生态、跨信任域）
- **多 agent 是乘法不是加法**：单 agent 可靠性不足时，协作会放大问题而不是解决问题

---

## 1. 先拆概念：多 Agent ≠ A2A

这是整个问题的地基。日常语境里"多 agent 协作"至少指三种完全不同的东西：

| 层级 | 形态 | 例子 | 是否需要 A2A |
|---|---|---|---|
| **L1 同进程编排** | 一个 harness 内的 subagent，共享宿主，Manager 派活 | Claude Code 的 Subagents、Agent SDK 的 Task tool | **不需要** |
| **L2 同组织多进程** | 多个独立部署的 agent，同一团队/平台内协调 | 自建平台：报销 agent → 审批 agent → 支付 agent | **通常不需要**（自定义 API/消息队列即可，A2A 只是可选的标准化外壳） |
| **L3 跨组织互操作** | 不同供应商/不同信任域的 agent 互调 | 买方 agent 与卖方 agent 谈判、企业 agent 调用外部服务 agent | **A2A 的设计目标** |

我最初的质疑错在把三层混为一谈：我看到的"A2A 宣传"大多讲的是 L1/L2 场景（这些根本不需要 A2A），而 A2A 真正瞄准的 L3 场景，宣传里反而没讲清楚。

**深度总结——为什么 L1 占了"多 agent"话题的 90%**：因为 subagent 编排解决的是真实且高频的工程问题（上下文隔离、并行加速），它的收益立即可见。而 L3 的收益需要整个生态先行（就像 HTTP 需要大家都上网才有用）。**判断一项 agent 技术是不是被过度营销，看它宣传的场景在 L1/L2/L3 哪一层：宣传 L1 收益卖 L3 协议的，都是在蹭热点。**

## 2. A2A vs MCP：精确对比

| 维度 | MCP | A2A |
|---|---|---|
| 解决什么 | agent ↔ 工具/数据（垂直） | agent ↔ agent（水平） |
| 类比 | USB-C：设备怎么接 | HTTP：主机之间怎么通信 |
| 发起方 / 时间 | Anthropic，2024.11 | Google 2025.04 → 2025.06 捐给 Linux Foundation |
| 核心抽象 | tools / resources / prompts | **Agent Card**（agent 的自描述名片：能力、端点、鉴权） |
| 交互模式 | 请求-响应为主 | 任务委派（长时异步）+ 消息流 |
| 成熟度（2026） | **事实标准**，OpenAI/Google 均支持 | 试点期，落地集中在企业间互操作 PoC |

两个协议是**互补的两层**，不是竞争关系：

```
   Agent A  ──A2A（对话、委派任务）──▶  Agent B
     │                                     │
     MCP（调工具）                         MCP（调工具）
     │                                     │
   数据库/搜索/文件...                    数据库/搜索/文件...
```

A2A 通信的两端 agent，各自在内部用 MCP 调自己的工具。类比：**两台电脑用 HTTP 互相访问网页，但每台电脑插外设都还是用 USB。**

## 3. 回应质疑：A2A 的真实需求到底有多少

### 3.1 诚实的现状盘点（2026）

| 场景 | 宣传热度 | 真实落地 | 判断 |
|---|---|---|---|
| 企业内工作流串联（报销→审批→支付） | 高 | 多 | **但这是 L2**——同平台内编排，用消息队列/HTTP 也能做，A2A 只是锦上添花的标准化 |
| 跨供应商谈判（采购 agent ↔ 销售方 agent） | 高 | 少量试点 | L3 正主，但生产级案例稀少 |
| 消费级互操作（"我的手机助手调用你的家 agent"） | 中 | 几乎没有 | 生态前提不成立 |
| Agent 市场（agent 之间互相发现、组网） | 中（长期愿景） | 无 | 类比"互联网普及前的 TCP/IP" |

### 3.2 质疑的正面回答

**"现在场景有那么多需要 A2A 的地方吗？"——没有。** A2A 今天是"为未来生态修的路"。修路没错（协议要先于生态存在，HTTP 也是先有协议后有网站），但把修路宣传成"高速公路已经通车"，就是当前市场上普遍的过度营销。

**"一个 agent 都约束不好，讲 A2A 干什么？"——这个直觉在工程上完全正确**，而且可以直接形式化为一条原则（见下节）：多 agent 是单 agent 可靠性的乘法。乘法意味着：**单 agent 不可靠时，加 agent 是降级不是升级**。

## 4. 多 Agent 的隐性成本（最深的一层）

拆 agent 之前，必须看清账本背面：

### 4.1 上下文蒸馏损耗

跨 agent 传递信息时，必须先蒸馏成消息（"23 处调用，5 个文件"），细节永久丢失。人越多传话越失真——**agent 也一样，而且 agent 的蒸馏比人更激进**（受 token 预算约束）。两个 agent 协作，中间那条消息就是信息瓶颈。

### 4.2 调试复杂度指数级

- 单 agent 失败：1 条日志流，单链路排查
- N 个 agent 协作失败：N 条日志流 + **N×(N−1)/2 个交互面**

定位"是谁引入的错误"变成分布式追踪问题，而当前 agent 可观测性工具链远未成熟到能覆盖这个复杂度。

### 4.3 延迟与成本叠加

每一跳都是一次完整的 LLM 推理。串行三 agent = 三倍延迟起步；迭代模式 = N 倍 token 成本。**多 agent 的速度收益（并行）经常被协调开销（汇总、对齐、重试）吃掉**——Amdahl 定律在 agent 编排里同样成立。

### 4.4 责任模糊

出了错算谁的？Manager 的提示词问题，还是 subagent 的执行偏差？A2A 的 Agent Card 描述能力，**不包含问责模型**。跨组织场景里这是致命缺口（也是为什么 L3 落地慢——不是技术问题，是信任与法务问题）。

### 4.5 安全攻击面的乘法

每个 agent 都是 prompt injection 的入口。单 agent 链上，注入最多污染一个上下文；**agent 链上，注入会随协作传播**——被污染的 subagent 产出的"结论"会被上游 agent 当作可信事实。攻击面随 agent 数量线性增长，防御成本非线性增长。

### 4.6 可靠性的乘法模型（深度总结）

```
单 agent 交付率：p
N 个 agent 串行协作交付率 ≈ p^N × 协调成功率

p = 0.7 时：
  1 个 agent：0.7
  2 个 agent：0.49 × 协调成功率（乐观 0.9）≈ 0.44
  3 个 agent：0.34 × 0.9 ≈ 0.31
```

**多 agent 是单 agent 可靠性的乘法而非加法。** 这就是"约束先行原则"的数学形式：先把单 agent 的 p 从 0.7 做到 0.95，比从 1 个 agent 拆成 3 个重要一个数量级。拆分只有一种情况是划算的：拆分本身能提高 p（比如用 subagent 隔离污染上下文，恰好就是在提高主 agent 的 p）。

## 5. 决策树：什么时候拆，拆到哪层

```
任务需要拆分吗？
│
├─ 否 ──▶ 单 agent + 好 harness          【90% 的场景，先到这里】
│          （把 harness 做厚：上下文管理/验收闭环/权限）
│
└─ 是 ──▶ 拆分的真实动机是什么？
           │
           ├─ 上下文隔离（脏活别污染主线）
           │    └─▶ L1：同进程 subagent（Claude Code / Agent SDK 模式）
           │         成本最低，Manager 可全程观测，默认选它
           │
           ├─ 并行加速（任务真独立）
           │    └─▶ L1 并行 subagent
           │         先自问：任务真的互不依赖吗？
           │
           ├─ 异构需求（不同模型/不同权限等级/不同成本档）
           │    └─▶ L2：多进程多 agent，同组织内自定义编排即可
           │         （不同子任务用不同模型：便宜模型干粗活，贵模型做决策）
           │
           └─ 跨组织边界（不同供应商/信任域/生态）
                └─▶ L3：A2A                     【<1% 的场景】
                     仅当对方 agent 不归你管时才成立
```

三条使用规则：

1. **每往下一层，成本上一个台阶**（L1 几乎免费，L2 需要部署与运维，L3 需要信任与法务）——**默认停留在能解决问题的最浅层**
2. **拆分前先修单 agent**：如果拆分的动机是"单 agent 做不好"，大概率该补的是 harness（上下文管理/验收闭环），而不是加 agent
3. **L1 的四种编排模式（串行/并行/层级/迭代）见系列第二篇**，那是日常真正用得上的部分

## 6. 本篇深度总结

### 总结一：约束先行原则

**多 agent 是单 agent 可靠性的复用，不是补救。** 一个 agent 都约束不好就去讲多 agent 协作，是在错误的层面解决问题——单 agent 的失败模式（上下文污染、幻觉、目标漂移）会在多 agent 系统里被指数放大。正确的路径永远是：先把 p 做上去，再考虑乘法。

### 总结二：A2A 的正确定位

A2A 是 L3 的基础设施，当前处于"修路期"。工程决策上把它当**远期期权**处理：知道它存在、知道它解决什么、但不要为它设计今天的系统。今天为 A2A 过度设计的架构，大概率会在生态真正到来时重写。

### 总结三：拆 agent 的唯一正当理由

排除所有噪音后，拆分 agent 的正当理由只剩两个半：
1. **上下文隔离**（subagent 让主上下文保持干净——本质上是在提高 p）
2. **异构资源配置**（不同任务用不同档次的模型/权限——成本与安全的优化）
3. 半个：**真并行的独立任务**（只有任务真的独立时收益才存在）

除此之外的拆分——"多个 agent 显得更智能"、"架构图更好看"、"老板听说要多 agent"——都是为拆而拆，是 agent 工程里的过度设计，与微服务拆分过度的病根一模一样：**用组织复杂度掩盖单体内功不足**。
