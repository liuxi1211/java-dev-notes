# SDD 开发实践总结

这阵子用 SDD（Spec-Driven Development，规范驱动开发）干活，加上踩了一堆坑，把感受记下来。

## 一、SDD 到底是怎么个流程

SDD，全称 Spec-Driven Development，规范驱动开发。「规范驱动开发」这六个字其实已经把流程说完了：**先有 spec，后有代码**。动手写代码之前，先把"要做什么、做到什么程度算完"写成一份文档，人看过、认可了，AI 再照着干。

完整跑起来一般四步：

1. 把需求写成 spec，说清楚要做什么、怎么算做完
2. 人审 spec，确认需求写得没问题
3. AI 根据 spec 拆任务，写代码
4. 按清单实现，最后对照 spec 验收

说句实话，很多人纠结的点不在流程本身，而在"到底什么才算 SDD"。比如 Claude Code 的 plan 模式算不算？Kiro 的 spec 模式当然算，那 plan 呢？名字都不一样。

这个问题我绕了挺久才想明白：**别被名字骗了，判断是不是 SDD，不看生成了几份文档、文件叫啥名，看有没有那个核心循环——代码之前，有没有"先落成文档 → 人审放行 → 实现跟着文档走"这一步。** 有，就带 SDD 基因；没有，就是聊天式编程，想到哪写到哪。

拿这个标准去套，就清楚了：

* **Kiro 那种 spec 模式**：是 SDD 的完整形态。有 requirements/design/tasks 三件套，人审完才动工，验收标准写得明明白白（EARS 语法那种），做完一条一条对着测——三个要素全占了：文档外化、人审把关、可裁决验收。

* **Claude Code 的 plan 模式**：也是 SDD，但属于**薄 SDD / 最小形态**。它把三层东西压扁成一份 plan 文档，保留了"先想清楚、人批了再动手"这两个骨架动作，但验收标准写得比较松，就是大纲式的，没有那种 WHEN/THEN 一条条能直接测的硬标准。所以约束力弱一截，但底子还是 SDD。

说白了，plan 和 spec 不是两种东西，而是**同一根光谱上的两个档位**：spec 在厚的那端，文档全、约束硬、验收清楚；plan 在薄的那端，文档精、约束软、大概齐就行。光谱的另一头（连文档都没有，直接开干）才叫非 SDD。

还有一点容易搞混：工具提供的是按钮和机制，SDD 是你自己用出来的。比如你开了 plan 模式，批完 plan 就扔一边，代码写歪了也不管，那其实不算在做 SDD；反过来，你就算不用任何工具的 spec 模式，自己先写一份需求、自己审一遍、写完对着验收，那也是 SDD。

所以后面我说"用 plan 还是用 spec"，本质上就是在问：**这个活配多厚的文档？** 不是问"要不要做 SDD"。

现在各家都在推动 SDD 落地，落地形式差不多，我长期用过的有这几种：

* **Kiro**：requirements / design / tasks 三件套，requirements 还规定用 EARS 语法（"当 xx 时，系统应 yy"）写验收条件

* **TRAE**：内置了 plan 和 spec 两种模式，轻量 plan 模式对应小需求，重型 spec 模式对应大需求（checklist / spec / tasks 三件套）

* **Claude Code**：只有一个 plan 模式可用，没有自己的 spec 模式（但是可以装插件）

* **superpowers**：Claude Code 可用的插件，提供了一整套开发相关的 skill：先头脑风暴、再写设计文档、再拆任务开干这一套工作流

* **zcode**：我们自己的工具，和 superpowers 非常像，加上了 PRD 知识库、质量评审、E2E 测试相关内容，spec 落地文件比 Kiro、TRAE 等多不少

## 二、实际用下来，真实感受

我长期使用 Claude Code 的 plan 模式、superpowers 插件、TRAE 的 plan 和 spec 模式，一直用来写代码，好处很明显。

第一，最明显的是返工少了。以前 AI 理解歪了，要等代码写完才发现，删了重来。现在 spec 写完我先审核，看看是否跑偏、和自己理解的是否一致，不一致直接让 AI 修改，保证方向正确，最终写出来的代码效果基本上就是想要的。

第二，大需求有记录。spec 落地之后，即使临时去干其他任务，有这份规范文件，下次也能接着开发。

第三，评审轻松了。AI 写的 spec 文件整理得比较细致，分类合理、条理清晰，很多细节我自己都想不到。AI 写一份，我审核后再从自己的角度完善一下，需求最终效果基本上都很完美。

## 三、踩过的坑和怎么改的

1. 什么都走重型 SDD 流程，包袱越来越重

   * 以前迷信 SDD 和 spec，觉得什么任务都用 spec，出来的效果绝对好。但是随着模型越来越好，我发现 spec 带来的提升越来越有限，而耗费的时间和 token 反而有点得不偿失

   * 特别是小任务开发，直接用提示词，或者用轻量的 plan 模式处理得又快又好；上了重型 spec，过程文档写了很多，时间要多花几倍，最终代码效果差不多

   * spec 文档写出来就是给人审核的。如果写 spec 要等 1 个小时，写出来洋洋洒洒上千字，时间太长断了思考节奏，字数太多没人愿意看，那这个 spec 路子就走错了，没有意义

   改进：所以现在我一般很少用重型的 spec 模式，除非是很复杂的大任务；稍微复杂一点的，直接用 Claude Code plan 模式，生成一个 plan 文档，我看看整体的计划和一些比较重要的细节（比如数据库、接口设计等），针对性补充完善一下，效果也可以了

2. spec 没有主动维护，烂掉了

   spec 需要维护的文件过多，需求变动频繁，导致 spec 同步维护调整困难，偏差越来越大，最后越来越不可信，过时的 spec 还会把 AI 带偏。

   改进：需求不稳的阶段用 plan 模式写，等需求稳了再补 spec。

## 四、怎么落地

1. 分档用，别一刀切

   * 小活（一句话说清、肉眼能验收）：不用 SDD，直接干

   * 中活（动几个文件、需求清楚）：用 plan 模式即可

   * 大活（从零起、跨模块、需求说不清）：重型 spec 模式，文档全落地

2. 无论用哪种模式都必须维护好知识库。有了完善的知识库，AI 才能结合项目现状开发，不然 AI 开发的代码只会脱离现状

3. SDD 流程中生成的过程文档一定要人工审核，不然就没有意义
