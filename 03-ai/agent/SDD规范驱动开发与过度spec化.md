# SDD 规范驱动开发与过度 Spec 化

> 本篇回答四个层层递进的问题：
> 1. Claude Code 不内置 SDD，是不是有什么自己的原因？（Plan Mode 只有一个文件、列出基本大纲——这么薄是不是没做完？）
> 2. SDD 是行业已经成型的规范吗？还有其他道路吗（TDD 等）？
> 3. SDD 仅针对编程行业，还是通用行业？
> 4. **"过度 spec 化"到底是什么意思——是无论大小都用 spec 算过度，还是 spec 产物增多算过度？**
>
> 第 4 问是本篇的核心交付：给出"过度"的准确定义、四种形态与检查清单。

核心论点：
- **SDD 不是行业规范，是"最佳实践集合的名称"**，且正处于战国时代（各家产物结构互不兼容）
- **Claude Code 不做 SDD 是哲学押注**：spec 厚度与模型能力成反比，Anthropic 在为更强的模型设计产品
- **"过度 spec 化"的本质不是大小问题也不是数量问题，而是：spec 的维护成本超过其对齐收益的临界点**

---

## 1. SDD 是什么：定义与代表实现

### 1.1 定义

> **SDD（Spec-Driven Development，规范驱动开发）**：先写结构化规范文档（spec），AI 按规范实现，规范是唯一事实源（single source of truth）。实现与规范冲突时，要么改实现，要么改规范——不允许"实现悄悄偏离规范"。

它要解决的问题非常具体：**AI 编码的规模化对齐**。当任务大到"一次对话说不清"（涉及多模块、多轮修改、需求本身模糊）时，靠对话里的自然语言互相确认会漂移，需要一个持久的、结构化的中间产物锚定共识。

### 1.2 代表实现与产物结构

| 实现 | 命令/流程 | 产物结构 |
|---|---|---|
| **GitHub Spec Kit**（开源 CLI） | `/specify → /plan → /tasks → /implement` | constitution（项目宪法）+ spec.md + plan.md + tasks.md |
| **AWS Kiro**（spec 驱动 IDE） | requirements → design → tasks | requirements.md（EARS 语法）+ design.md + tasks.md |
| Tessl / OpenSpec / claude-spec-workflow 等 | 各自变体 | 大同小异的三层 |

### 1.3 SDD 三层产物详解

```
┌─────────────────────────────────────────────────┐
│ 第一层：spec.md / requirements.md（做什么）        │
│   需求与验收标准。用户故事、功能边界、               │
│   可验收的 WHEN/THEN 条目（EARS 语法）。           │
│   写给：人（审） + 模型（对齐）                    │
├─────────────────────────────────────────────────┤
│ 第二层：plan.md / design.md（怎么做）              │
│   技术方案。架构选型、模块划分、数据流、             │
│   与现有代码的集成点、风险点。                      │
│   写给：模型（执行前的路线图）                      │
├─────────────────────────────────────────────────┤
│ 第三层：tasks.md（分几步做）                       │
│   可勾选的任务清单。每个任务粒度到                  │
│   "一次可验证的增量"（改完能跑测试）。              │
│   写给：模型（逐步执行）+ 人（进度追踪）            │
└─────────────────────────────────────────────────┘
```

三层的本质：**需求的三个分辨率**——spec 是望远镜（看边界），plan 是地图（看路径），tasks 是脚步（看下一步）。外加人审门：每层产出都经人批准才进入下一层。

## 2. SDD vs TDD vs BDD

| 维度 | TDD | BDD | SDD |
|---|---|---|---|
| 驱动物 | 测试用例 | 行为场景（Given-When-Then） | 规范文档 |
| 所在层次 | 代码级 | 需求-代码桥接 | 需求级 |
| 先写什么 | 测试 | 场景 | spec |
| 主要执笔人 | 开发 | 开发 + 业务方 | 人 + AI 共写 |
| 验收方式 | 测试通过 | 场景通过 | spec 条目满足 |
| 诞生背景 | 2003（极限编程） | 2006（Dan North） | 2025（AI 编码规模化） |

三个关键判断：

1. **三者不互斥，是不同层次**：SDD 的 spec 层可以内嵌 BDD 场景（Kiro 的 requirements 就是 EARS 语法，与 BDD 同源）；tasks 执行时完全可以用 TDD（先写测试再实现）。堆叠起来是：**SDD 管"做的是对的事"，TDD 管"代码是对的"**
2. **SDD 是 TDD 在 AI 时代的向上延伸**：TDD 解决"实现正确性"由人写测试保证；AI 时代出现了新问题——"需求正确性"（模型对任务的理解和人不一致）。SDD 用 spec 把需求层固化下来，本质是把 TDD 的"红绿重构"循环上移到了需求层
3. **还有其他道路**：除 SDD 外，可执行验收的路线还有 evaluator-based（用另一个模型评估产出）、diff-review-based（git diff 人工审）、测试先行直接让 AI 写测试（TDD 原教旨路线）。**SDD 是其中最重的一条路**，天然适合大任务、不适合小任务

## 3. SDD 是行业成型规范吗

**不是。** 准确的现状描述：

- **没有标准**：Spec Kit 的 constitution/plan/tasks 与 Kiro 的 requirements/design/tasks 结构不同、理念有别（Spec Kit 强调宪法约束，Kiro 强调 EARS 可验收性），互不兼容
- **没有 ISO/IEEE 级别的规范**，也没有像 MCP 那样的跨厂商收敛
- **正在形成的共识**（可以视为 SDD 的公约数）：① spec 先行、② 人审门、③ 任务可勾选可验证、④ spec 是唯一事实源
- 更准确的定位：**SDD 是"一组最佳实践的集合名称"，不是规范**。它处于 TDD 在 2005 年、MCP 在 2024 年初的相同阶段——方向被验证，标准待统一

## 4. SDD 仅针对编程行业吗

**思想通用，工具链专精编程。**

- spec 思想本身是全行业的老智慧：盖楼先图纸、拍片先剧本、写书先大纲——SDD 只是"图纸先行"在 AI 交付上的翻版
- 但当前 SDD 工具链 95% 以上集中在编程，原因不是编程特殊，而是**编程拥有可执行的验收闭环**（编译/测试/lint 是客观裁判）。规范的价值取决于"违反规范能否被自动发现"——代码违反 spec 会编译失败、测试变红；营销文案违反 spec 只能靠人肉判断
- 通用行业的对应物是 prompt / SOP / skill（TRAE 的 Skill 体系就是通用行业的 SDD 形态——写给 LLM 看的结构化工作手册）。**判断一个领域会不会长出自己的 SDD：看它有没有客观裁判。有裁判的领域 SDD 会成熟，没裁判的领域 spec 只能薄到"人可审"为止**

## 5. Claude Code 为什么不内置 SDD（完整版）

四个原因，按权重排序：

### 5.1 押注模型能力曲线（根本原因）

Anthropic 的判断：**spec 的合理厚度与模型能力成反比**。

```
模型弱 → 需求一句话说不清 → 必须用厚 spec 把细节喂给模型 → spec 三层全上
模型强 → 一句话需求 + 上下文 → 模型自己推断出合理实现 → Plan Mode 足矣
```

如果这个判断成立，为当前模型设计的厚重 SDD 工作流是**过渡期产物**——下一代模型会让它的价值窗口关闭。Anthropic 在为"更强的模型"设计产品，而不是为"当前模型的缺陷"设计产品。这是我看完 Plan Mode 那个单文件后困惑的答案：**不是没做完，是刻意做薄**。

### 5.2 通用 harness 定位（产品原因）

Claude Code 的哲学是提供**原语**（Plan Mode / Skill / Hooks / Subagent），而不是**工作流引擎**。SDD 是一种工作流——想用的用户通过 skill 装一个 spec-kit 就是了（GitHub Spec Kit 正是以 CC skill 形式工作的）。内置等于强制所有用户交"三层文档税"。

### 5.3 Building effective agents 的立场（方法论原因）

Anthropic 公开方法论的核心主张：从最简单的开始，只在失败模式被验证时才加复杂度。内置 SDD 违背这条立场——它假设所有任务都需要三层文档，而实际上（见第 6 节）绝大多数任务不需要。

### 5.4 Plan Mode 已覆盖核心价值（功能原因）

SDD 的价值拆解：**对齐（防跑偏）+ 人审门（防失控）+ 可追溯（防失忆）**。Plan Mode 用一个轻量文件提供了前两者（强制先研究后动手 + 人工审批门），覆盖了约 80% 的场景收益。剩下的可追溯性，git diff 和 CLAUDE.md 部分承担。**为 20% 的场景收益内置 100% 的流程成本，不划算。**

> 反方观点（保持诚实）：这个押注也可能错。如果模型能力增长放缓而任务复杂度继续上升，spec 厚度的合理值会不降反升，SDD 就会从"过渡期产物"变成"永久基础设施"。目前证据两边都有，Anthropic 的押注胜在与其自身利益（卖更强的模型）和技术演进方向一致。

## 6. 过度 Spec 化：准确定义与四种形态

### 6.1 先回答"到底哪种算过度"

我的原始困惑是二选一：**"无论大小都用 spec"算过度，还是"spec 产物增多"算过度？**

准确的回答是：**两种都只是表象，都不是本质。**

> **过度的准确定义：spec 的维护成本超过其对齐收益的临界点。**
>
> 大小（任务规模）和数量（产物件数）只是触发这个临界点的两个常见变量，同级的变量还有：粒度（spec 写多细）、同步（要不要回写）。判断过度与否的唯一标准是成本收益比，不是任何单一维度。

### 6.2 四种过度形态

**形态一：层级过度（"无论大小都用"）**

- 表现：改一个按钮颜色也走 spec → plan → tasks 全流程
- 本质：任务的**对齐收益趋近于零**（一句话能说清 + 验收肉眼可见），但成本全付了
- 信号：任务能否一句话说清？验收是否肉眼可见？两个都是 → 跳过 spec

**形态二：粒度过度（"spec 写太细"）**

- 表现：spec 里出现变量名、伪代码、具体算法、表结构 DDL
- 本质：**越过了需求层，侵入了实现层**。两个后果：① 模型变成打字员——它对实现细节的判断力被剥夺，代码质量反而下降（模型的本职就是做实现决策）；② spec 与实现必然漂移（实现时发现更好的做法，spec 却锁死了）
- 信号：spec 里任何"怎么做"的内容都是嫌疑，spec 只该写"做什么"和"怎么验收"

**形态三：产物过度（"件数太多"）**

- 表现：spec / plan / tasks / constitution / checklist 五件套起步，每层都是要维护的 Markdown
- 本质：**文档间一致性成本随件数超线性增长**——改一个需求要同步改五个文档，漏改一个，文档间的矛盾就成了模型的毒输入（模型不知道听哪个的）
- 信号：改一行代码需要动几个文档？**> 2 个就是过度信号**

**形态四：同步过度（"强制双向同步"）**

- 表现：实现变更后强制回写 spec，保持 spec 永远最新
- 本质：spec 从"驱动源"异化为"维护负担"。团队最终的结局不是同步，而是**放弃维护**——spec 腐化成没人信的谎言，比没有 spec 更糟（没有 spec 模型自己推断，腐化的 spec 主动误导模型）
- 信号：spec 更新是"流程要求"还是"有人真读"？没人读 → 删

### 6.3 成本收益公式（深度总结）

```
spec 净价值 = 对齐收益（减少的返工与漂移） − 维护成本（写 + 改 + 同步 + 读）

其中：
  对齐收益 ∝ 任务复杂度 × 需求模糊度 × (1 − 模型推断能力)
  维护成本 ∝ spec 厚度 × 变更频率 × 文档件数
```

从公式直接读出三个非显然结论：

1. **对齐收益与模型能力成反比**——模型越强，越能从模糊需求直接推断出正确实现，spec 该越薄。**SDD 的流行本身就是当前模型能力不足的信号；spec 厚度是模型能力的负相关指标**
2. **变更频率是被低估的杀手**——静态项目（需求稳定）厚 spec 无妨；活跃项目（每天变）薄 spec 才活得住。同一个任务在原型期和稳定期需要不同厚度的 spec
3. **文档件数是复利毒药**——一件文档的成本是线性，五件文档的成本是组合爆炸（一致性检查是 N² 问题）

### 6.4 反过度检查清单

动手写 spec 之前过一遍：

- [ ] 这个任务**一句话能说清**吗？能 → 跳过 spec，直接 Plan Mode
- [ ] 验收标准**可执行**吗（能跑测试/能编译/能 diff）？不能 → 先补裁判，否则 spec 无牙
- [ ] spec 里有没有实现细节（变量名/伪代码/算法）？有 → 删，只留行为与验收（形态二）
- [ ] 改一行代码需要动几个文档？**> 2 → 砍层**（形态三）
- [ ] spec 编写时间 vs 预计实现时间？spec > 实现 → 过度
- [ ] 执行时模型/人真的会**回读** spec 吗？不会 → 删（形态四前兆）
- [ ] 三个月后这个 spec 还会有人维护吗？不会 → 现在就写薄，**薄到不值得腐化**
- [ ] 需求这周会变吗？会 → 只写 spec 第一层（做什么），plan/tasks 让模型即兴

### 6.5 正反案例

| 案例 | 判断 | 理由 |
|---|---|---|
| 新系统从零搭建：10+ 文件、跨模块、需求方说不清要什么 | **三层全上，收益巨大** | 任务复杂度高 + 需求模糊 → 对齐收益最大；变更少 → 维护成本可控 |
| 修复一个根因明确的 bug：单文件、有回归测试 | **直接修 + 跑测试** | 一句话说得清 + 有客观裁判 → spec 是纯负资产 |
| 给现有系统加一个中等功能 | **只写 spec 第一层 + Plan Mode** | 对齐需求有价值；plan/tasks 让模型自由发挥，粒度过度是最大风险 |
| 活跃迭代中的产品持续开发 | **薄 spec（user story 级）+ 强验收闭环** | 变更频率高 → 厚 spec 必然腐化；把钱花在裁判（测试）上，不花在文档上 |

## 7. 本篇深度总结

### 总结一：spec 厚度是模型能力的负相关指标

这是整篇最有预测力的判断：观察一个团队的 spec 厚度变化，就知道他们对模型能力的真实信心。spec 越写越薄 = 团队在实践中验证了模型能力增长；spec 越写越厚 = 模型跟不上任务复杂度，或团队在用文档量缓解焦虑。**Claude Code 与 SDD 工具链的分歧不是功能分歧，是对这条曲线斜率的分歧。**

### 总结二：SDD 的正确用法是"分级供给"

不要问"用不用 SDD"，问"这个任务配多厚的 spec"。三级供给：

```
轻任务（一句话+可验收）→ 无 spec，Plan Mode 即兴
中任务（多模块+需求清晰）→ spec 第一层 + Plan Mode
重任务（从零+跨模块+需求模糊）→ 三层全上 + 人审门
```

把 SDD 当开关（用/不用）是过度 spec 化的根源；把它当旋钮（多厚）才是正解。

### 总结三：钱该花在裁判上，不是文档上

SDD 各流派共同的底层教训：spec 的价值上限由**验收闭环的强度**决定。有客观裁判（测试/编译），薄 spec 也可靠；没有裁判，厚 spec 也是自我安慰——文档写得再细，"模型照做了没有"依然没人知道。**资源恒定的前提下，优先补验收（写测试），其次才补文档（写 spec）。**
