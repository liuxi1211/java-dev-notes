# SDD 本质论：为什么规范先行能提效

> 上一篇《[SDD规范驱动开发与过度spec化](SDD规范驱动开发与过度spec化.md)》讲的是**怎么用**（三层产物、过度形态、检查清单）。

>
> 1. **SDD 到底是什么**——剥掉工具外壳后的第一性定义

## 1. SDD 到底是什么：第一性定义

### 1.1 定义的三次剥壳

**第一层（工具外壳）**：spec.md / plan.md / tasks.md、`/specify → /implement` 命令流——这是 GitHub Spec Kit、Kiro 等实现给出的"SDD 长什么样"。

**第二层（方法论外壳）**："先写规范，再写实现，规范是唯一事实源"——这是大多数文章对 SDD 的定义，但它没有回答"规范凭什么驱动"。

**第三层（第一性定义）**：

> **SDD 是把"交付物的验收标准"从人脑和口语中抽离出来，固化为一份机器可读、人可审批、可执行检查的中间产物，并让这个产物成为整个交付流程中所有角色（人、AI、CI）共同遵守的最高约束。**

拆出三个不可缺的要素，缺一个就不是 SDD：

| 要素                      | 含义                     | 缺失后果                   |
| ----------------------- | ---------------------- | ---------------------- |
| **外化**（Externalization） | 验收标准脱离人的脑子，落在持久的载体上    | 标准只存在于"上次对话"，换人/换会话即蒸发 |
| **可裁决**（Adjudicable）    | 有办法客观判定交付物符不符合规范       | 规范沦为摆设，"做没做到"靠争论       |
| **最高约束**（Supremacy）     | 实现与规范冲突时，规范赢（除非正式修订规范） | 规范被实现"悄悄绑架"，逐步腐化失效     |

### 1.2 SDD 的本质：一个"编译器"，把意图编译成可执行契约

最有解释力的心智模型：**spec 是源代码，实现是编译产物，验收是编译器**。

* 需求（人的意图）是自然语言的、模糊的——这是"源代码"

* spec 是第一次编译：把意图翻译成结构化、无歧义的陈述（用户故事 + WHEN/THEN 验收条目）

* 实现是第二次编译：把 spec 翻译成代码

* 测试/验收检查是"编译器报错"：实现违反 spec 时被拦截

这个模型直接解释了 SDD 的两个特性：

1. **为什么要人审 spec 而不是人审代码**——编译产物（代码）人读不动，但中间表示（spec）人可读。把人审插在中间表示层，是唯一"人审得起"的位置
2. **为什么规范冲突时规范赢**——源代码（意图）优先于编译产物（实现），这是所有编译系统的默认语义。实现"自作主张"偏离 spec，等价于编译器乱改源码

### 1.3 与"文档驱动开发"的区别（常见混淆）

SDD ≠ "写文档"。传统文档驱动开发的文档是**描述性**的（descriptive）——先做完再补文档，文档是实现的事后注解；SDD 的 spec 是**规定性**的（prescriptive）——先于实现存在，实现必须向它对齐。**判断标准很简单：改了实现要不要回改 spec？要 → spec 是规定性的（SDD）；不要 → 文档只是注解（不是 SDD）。**

## 2. 好处理：为什么规范先行能提效

"先写文档再干活"听上去是负资产（多一道工序），SDD 却在 AI 时代被验证为提效手段。收益不是玄学，可以逐条机理化：

### 2.1 机理一：把返工前移（成本不对称原理）

软件工程最古老的铁律：**缺陷发现的阶段越晚，修复成本越高**（Boehm 曲线：需求阶段修 1 倍，发布后修 100 倍）。

对话式开发的缺陷发现位置是"实现写完之后的 review"，甚至"上线之后"。SDD 把审查点前移到 spec 阶段——**在人审 500 字 spec 时拦住方向性错误，代价是 10 分钟；在 review 5000 行代码时拦住同样的错误，代价是几天的返工**。SDD 的本质收益之一：用 spec 的书写成本，置换实现的返工成本，利用的正是两者之间 10\~100 倍的成本不对称。

### 2.2 机理二：压缩沟通带宽（对齐的 N² 问题）

N 个人（或人 + 多次 AI 会话）协作，两两对齐的沟通成本是 N² 量级；没有共同锚点时，每次对齐都从零开始复述上下文。

spec 的作用是把对齐从 **N² 次对话** 压缩为 **N 次读同一份文档**：

* 没-spec：产品跟开发说一遍，开发跟 AI 说一遍，AI 第二次会话忘了再说一遍……每次传递都失真（传话游戏）

* 有-spec：所有人（和所有 agent 会话）读同一份 spec，分歧点显式暴露在文档里，一次修订全员生效

这就是"唯一事实源"的物理含义：**spec 不是又一份文档，它是把 N² 对齐坍缩成 N 读取的那个质点。**

### 2.3 机理三：给模型装上"防漂移锚"（AI 时代的核心收益）

长任务中 LLM 的目标漂移（goal drift）是实证现象：任务越长，模型对原始意图的偏离越大，且**每一步局部看都合理**（漂移不表现为突变，表现为逐步的合理化偏航）。

spec 在 here 的作用机制：spec 常驻上下文（或按层注入）时，模型的每一步生成都有一个"意图快照"可回查——**spec 是把"一次性听懂"改造成"随时可回看的需求"**。没有 spec 的长任务，意图只存在于对话开头几条消息，早被后续工具输出淹没。

这也是为什么 spec 的第三要素（最高约束）不可缺：如果模型偏了但 spec 说了不算，锚就不存在。

### 2.4 机理四：验收自动化（从"人肉感觉对不对"到"机器判定"）

spec 的验收条目（WHEN/THEN、EARS 语法）天然可以翻译成测试用例。这带来一个结构性收益：**验收标准的作者不需要是测试的作者**——业务方写"当订单金额>500 且会员等级≥金牌时免运费"，AI/测试工具把它转成用例。

编程之外的行业没有"测试"这个编译器，但机理相同：验收条目越结构化，"做没做到"的裁决越不需要吵架。SDD 收益的强度，直接取决于验收条目的可裁决程度（呼应第一性定义第二要素）。

### 2.5 机理五：知识资产的复利（spec 是"可执行的记忆"）

对话是易逝的，spec 是持久的。一份好的 spec 三个月后：

* 新成员（或新 agent 会话）读 spec 即可获得 80% 的任务上下文，不用考古聊天记录

* 需求变更时，diff 的对象是 spec 而不是代码——**评审一次 spec diff 比评审一次全量代码 diff 便宜一个量级**

* 多个实现（前端、后端、迁移脚本）共享同一份意图源，不会各自理解分叉

### 2.6 收益机理速查表

| # | 机理    | 一句话               | 利用的不对称            |
| - | ----- | ----------------- | ----------------- |
| 1 | 返工前移  | 人审 500 字拦住方向错误    | 修复成本 1:100 的阶段差   |
| 2 | 对齐坍缩  | N² 对话 → N 份读取     | 沟通组合爆炸 vs 线性读取    |
| 3 | 防漂移锚  | 意图快照常驻，随时回查       | 长任务漂移 vs 开头几条消息   |
| 4 | 验收自动化 | WHEN/THEN 直接翻译成裁决 | 人肉感觉 vs 机器判定      |
| 5 | 记忆复利  | spec diff 替代代码考古  | 文档 diff vs 代码考古成本 |

> 诚实标注（机理的边界）：以上收益都有前提——任务足够复杂（否则机理 1、2 收益趋零）、验收可裁决（否则机理 4 失效）、spec 会真被回读（否则机理 3、5 失效）。前提不成立时 SDD 净收益为负，这正是上篇"过度 spec 化"四种形态的由来。

## 3. 演进过程：规范先行思想的七十年

SDD 不是 2025 年的发明，是**一条老思想的最新一轮复兴**。完整脉络：

### 3.1 前史：工程图纸时代（1950s–1980s）

* 思想源头：土木/机械工程的"图纸先行"——先设计图后施工，图是施工的最高约束。软件工程从诞生起就在抄这个模式

* 瀑布模型（1970，Royce 提出，被误读为教条）：需求 → 设计 → 实现 → 测试 → 运维，严格顺序。**注意：瀑布的问题不是"规范先行"本身，而是假设规范一次写对、不再修改**

* 形式化方法（1980s）：Z 语言、VDM 等用数学语言写 spec，可证明程序正确性。学术上辉煌，工程上败退——**数学 spec 严谨到人写不动、人读不懂**。这次失败留下重要遗产：spec 必须人可读写才有生命力

### 3.2 反叛：敏捷时代（1990s–2010s）

* 敏捷宣言（2001）"可工作的软件高于详尽的文档"——这是对瀑布**文档形式主义**的反叛，不是对"规范先行"的反叛。敏捷真正反对的是：写了几百页没人读的需求规格说明书（SRS），然后按过时图纸施工

* 用户故事（XP，1990s 末）：把 spec 从几百页 SRS 压缩成"作为…我想…以便…"一句话卡片 + 验收条件。**这是 spec 的最小化革命：粒度从"项目级"降到"故事级"**

* BDD（2006，Dan North）：把验收条件从口语固化成 Given-When-Then 结构，并让这个结构可执行（变成测试）。**BDD 是"spec 可裁决化"的第一次成功落地**

### 3.3 内化：TDD 与敏捷的成熟（2003–2020）

* TDD（2003，Kent Beck）：不在需求层写 spec，而是把"规范"下沉为测试代码——先写测试（红色）→ 写实现（变绿）→ 重构。测试就是可执行的需求

* 上升趋势中的共识：**规范并没有消失，而是换了形态**——从"前置的文档"变成"可执行的测试"。TDD 的测试本质上是"实现层的 spec"

* 这个阶段的遗产：业界学会了"spec 必须可执行才不腐化"，也暴露了 TDD 的边界——**测试写得再好，也裁决不了"做的是不是对的事"**（需求层无裁判），只能裁决"代码是不是对的"

### 3.4 复兴：AI 时代的 SDD（2025 至今）

AI 编码把需求层对齐问题重新炸出来，SDD 换了一个引擎复活：

* **问题的变化**：TDD 时代，写代码的是人，需求对齐靠人肉对话可以兜底；AI 时代，代码生成速度提升 10\~100 倍，**瓶颈从"写"移到"说清楚要写什么"**。意图传递成为新的第一瓶颈

* **能力的出现**：LLM 恰好是第一个**能读写自然语言 spec 的"工人"**——七十年前形式化方法失败，是因为"工人"（编译器/程序员）读不懂数学 spec 或人写不动；现在"工人"能读结构化自然语言了，spec 作为接口第一次在工程上闭环

* 关键节点：

  * 2024–2025：OpenAI/Anthropic 的实践社区先提出"spec 是给 AI 的最好输入"类经验，spec 先��重新流行

  * 2025.09：**GitHub 开源 Spec Kit**，把 `/specify → /plan → /tasks → /implement` 流程标准化为 CLI，SDD 作为术语正式出圈

  * 2025 下半年：**AWS Kiro** 以 spec 驱动 IDE 的形态商业化（requirements/design/tasks 三件套 + EARS 语法），同期的 OpenSpec、claude-spec-workflow 等社区工具涌现

  * 同期对照：**Claude Code 选择不内置 SDD**，只保留 Plan Mode（最小可行 spec）——这构成了 SDD 光谱的两端（详见上篇第 5 节）

### 3.5 演进时间线

```
1950s    图纸先行（借自传统工程）
  │
1970     瀑布模型 —— 规范先行 + 一次写对（教条化）
  │
1980s    形式化方法 —— 规范严谨到人写不动（失败，留下"人可读写"遗产）
  │
2001     敏捷宣言 —— 反文档形式主义（反的是"没人读的厚 SRS"）
  │
2003     TDD —— 规范下沉为测试（可执行化）
  │
2006     BDD —— 验收条件结构化、可裁决化
  │
2025     AI 时代 SDD —— 规范重新前置，工人第一次能读懂它
         （Spec Kit / Kiro / OpenSpec…）
```

### 3.6 演进的螺旋（深度总结）

七十年转了一个圈：**瀑布（重 spec）→ 敏捷（薄 spec）→ AI-SDD（spec 回归但形态改变）**。这不是简单回摆，螺旋每圈都留下了升级：

| 演进阶段       | spec 的形态                          | 失败/成功原因                        |
| ---------- | --------------------------------- | ------------------------------ |
| 瀑布 SRS     | 几百页散文，人写人读                        | 写了没人读，改了不同步 → 形式主义             |
| 敏捷故事卡      | 一句话 + 验收条件                        | 成功但对齐靠人肉，规模一大失真                |
| TDD 测试     | 代码形态的可执行规范                        | 成功但只在实现层，需求层无裁判                |
| **AI-SDD** | **结构化 Markdown + 可验收条目，人审 AI 执行** | **工人第一次能读懂 spec，人第一次审得起 spec** |

AI-SDD 与瀑布的本质区别一句话说清：**瀑布的 spec 是给人执行的（所以怕写细，执行不动）；AI-SDD 的 spec 是给机器执行的（所以敢写细，机器不怕细）——但上篇的"过度 spec 化"警告依然有效：写细不等于写实现细节，spec 该细到验收为止。**

## 4. 本篇深度总结

### 总结一：SDD 的定义要素是"外化、可裁决、最高约束"，工具只是外壳

判断一个实践是不是真 SDD，不看有没有 spec 文件，看三要素：验收标准是否离开人脑（外化）、是否可客观判定（可裁决）、实现偏离时谁赢（最高约束）。三缺一，spec 就是装饰品。

### 总结二：收益全部来自不对称性

SDD 不是"写文档的爱好"，它套利了四组不对称：**修复成本阶段差（1:100）、沟通组合差（N²:N）、裁决方式差（人肉:机器）、知识存续差（对话:文档）**。套利空间随任务复杂度、协作人数、任务时长放大；任务小到不对称消失时，SDD 从提效手段变成纯开销——这与上篇"spec 是旋钮不是开关"的结论完全咬合。

### 总结三：七十年演进的核心矛盾是"spec 的严谨性 vs 人的读写带宽"

瀑布败于"人执行不动细 spec"，形式化方法败于"人读写不动数学 spec"，敏捷以"薄到人肉可对齐"取胜，TDD 以"可执行"取胜但丢了需求层。**AI-SDD 是第一次两边同时破局：机器执行解决了严谨性的执行成本，人审中间表示解决了读写带宽。** SDD 能否长期成立，取决于这个双破局是否稳定——也就是上篇留下的开放问题：模型能力继续增长时，spec 的合理厚度会降到什么位置。
