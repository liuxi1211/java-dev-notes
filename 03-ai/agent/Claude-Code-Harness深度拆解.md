# Claude Code Harness 深度拆解

> 本篇回答的起点是我在学习 Claude Code 时自己列的能力清单：
> CLAUDE.md（全局说明）、MCP、Skill、Hooks、Memory（临时+永久会话）、Cron 定时任务。
>
> 这六层单看都像"LLM 的工具和使用手册"，确实关键，但**总感觉遗漏了一环**——如果面向的是大型需求和大型项目的编码，还缺什么？
>
> 本篇的三个核心交付：
> 1. 六层 → 九层的补全（缺的那一环是什么）
> 2. Plan Mode 的极简设计哲学，以及 Claude Code 为什么不内置 SDD
> 3. 子 Agent 四种编排模式的通俗拆解（串行/并行/层级/迭代，配具体例子）

核心论点：
- **缺的那一环是"验收闭环"**——面向大型编码项目，harness 的瓶颈不是给模型更多能力，而是给"完成"一个客观定义
- **Plan Mode 是"最小可行 spec"**：它的价值不在文档厚度，而在"强制先研究后动手 + 人工审批门"两个动作
- **子 Agent 的本质是 context 的分页机制，不是智能的复制**

---

## 1. 六层清单回顾与"缺环"诊断

我最初总结的六层：

| # | 层 | 职能 | 一句话 |
|---|---|---|---|
| 1 | CLAUDE.md | 全局说明 | 项目宪法，常驻上下文 |
| 2 | MCP | 工具接入 | 标准化插座，接外部能力 |
| 3 | Skill | SOP 按需加载 | 给 LLM 看的工作手册，用到才装 |
| 4 | Hooks | 事件干预 | 在流程节点上插用户自己的逻辑 |
| 5 | Memory | 会话记忆 | 临时（会话内压缩）+ 永久（跨会话） |
| 6 | Cron | 定时任务 | 无人值守的周期触发 |

**诊断**：这六层全部回答的是"模型如何获得输入和能力"（1、3、5）与"如何被触发和干预"（2、4、6）。它们合起来是一个优秀的**供给系统**。但一个面向大型编码项目的 harness，还必须回答三个问题：

1. 模型**不能做什么**？（安全边界——大型项目里模型误删代码、泄漏密钥的代价不可承受）
2. 任务**怎么扩展**？（上下文隔离与并行——大项目一次任务要读几十个文件，主上下文必然溢出）
3. **怎么算"做完了"**？（验收闭环——这是最关键的一环）

## 2. 补全后的九层模型

```
┌──────────────────────────────────────────────────┐
│  供给系统（我原本总结的六层）                        │
│  ① CLAUDE.md   ② MCP   ③ Skill                  │
│  ④ Hooks       ⑤ Memory  ⑥ Cron                 │
├──────────────────────────────────────────────────┤
│  边界系统（补全层）                                 │
│  ⑦ 权限与沙箱：读/写/执行分级，敏感操作确认，        │
│     文件系统沙箱，审计日志                          │
├──────────────────────────────────────────────────┤
│  扩展系统（补全层）                                 │
│  ⑧ Subagent 编排：独立上下文的子代理，              │
│     串行/并行/层级/迭代四种模式                     │
├──────────────────────────────────────────────────┤
│  验收系统（补全层 · 缺的那一环）                     │
│  ⑨ 验收闭环：测试/lint/编译作为客观裁判，            │
│     Checkpoints 可回滚，git 集成可 diff，           │
│     Plan Mode 人审门                              │
└──────────────────────────────────────────────────┘
```

### 2.1 第 7 层：权限与沙箱（不能做什么）

大型项目里这一层的价值急剧上升：

- **权限分级**：默认只读，写文件/执行命令需要分级授权（按会话/按项目/永久），`--dangerously-skip-permissions` 是逃生舱不是默认
- **沙箱**：文件系统隔离 + 网络隔离，模型跑 `rm -rf` 也炸不坏仓库
- **审计**：每次工具调用留痕——出问题时能回放"它当时为什么这么干"

### 2.2 第 8 层：Subagent 编排（怎么扩展）

详见本文第 5 节。核心认知：**subagent 解决的不是"多个模型更聪明"，而是"主上下文是稀缺资源"**——把读 30 个文件的脏活扔进独立上下文，只把蒸馏后的结论带回主线。

### 2.3 第 9 层：验收闭环（缺的那一环，最重要）

这是我六层清单的真正盲区。面向大型编码项目，harness 的瓶颈会从"模型能不能"转移到"**你知不知道它做对了**"：

- **客观裁判**：编译通过？测试通过？lint 通过？——编程场景的天赋优势是**验收可执行**，这是编程 harness 成熟度领先所有其他行业的根本原因
- **Checkpoints / git**：每步可回滚、可 diff，错误不会静默累积成雪崩
- **人审门（Plan Mode）**：不可逆操作之前，人看一眼

**深度总结**：六层清单的本质是"让模型能干活"，九层补全的本质是"让模型的活敢用"。面向大型项目，后者才是瓶颈——供给过剩、验证不足，是当前 AI 编码落地最大的结构性风险。模型越强、产出越快，验收闭环的价值越高（错误的生产速度也变快了）。

## 3. Plan Mode 哲学：为什么只有一个轻量文件

### 3.1 现象

Claude Code 的 Plan Mode 产出物就是**一个文件：基本大纲 + 大概描述**。相比 SDD 工具链的 spec/plan/tasks 三层产物，薄得不像话。

### 3.2 这不是没做完，是刻意设计

Plan Mode 的核心价值拆开看只有两个动作：

1. **强制先研究后动手**：进入 Plan Mode 后模型被禁止写文件/执行变更，只能读代码库、做调研——把"想清楚"变成流程上不可跳过的一步
2. **人工审批门**：`exit plan mode` 是一个闸门，计划必须经人批准才能进入执行——人作为信任链最后一环

**深度总结——"最小可行 spec"**：SDD 三层文档的 80% 价值（对齐 + 人审）来自这两个动作，而不是来自文档本身的厚度。Plan Mode 用 20% 的形式成本拿到了 80% 的对齐收益。剩下的 20%（可追溯、规范沉淀）对多数任务本来就是负资产（维护成本 > 收益，详见系列第四篇的过度 spec 化分析）。

### 3.3 为什么 Claude Code 不内置 SDD（简版，详见系列第四篇）

四个原因，按权重排序：

1. **押注模型能力曲线**：Anthropic 判断模型能力在指数增长，spec 脚手架的合理厚度随之单调下降。为当前模型打补丁的厚重工作流，会被下一代模型淘汰。他们是为"更强的模型"设计产品，不是为"当前模型的缺陷"设计产品
2. **通用 harness 定位**：CC 提供原语（Plan Mode/Skill/Hooks），工作流引擎交给生态——GitHub spec-kit 等就以 CC skill 形式存在，想要 SDD 的用户自己装
3. **Building effective agents 立场**：从最简单开始，只在失败模式被验证时才加层。内置 SDD 等于对所有用户强制三层文档税
4. **Plan Mode 已覆盖核心价值**（见 3.2）

## 4. 子 Agent 编排四种模式（Claude Agent SDK 官方）

### 4.0 先讲为什么需要子 Agent（前置认知）

很多人卡在编排模式，是因为没先理解 subagent 解决的问题。一个反直觉的事实：

> **Subagent 不是"多个大脑更聪明"，而是"上下文的分页机制"。**

主 Agent 的上下文窗口是稀缺资源。一次调研要读 30 个文件、跑 10 次搜索，这些中间产物会把主上下文塞满，导致模型"忘记"原始任务、推理质量下降。Subagent 的价值：**开一个独立上下文去干脏活，干完只把蒸馏结论（一段话）带回主上下文**。主上下文始终保持干净、聚焦。

（工程细节详见：[SubAgent上下文隔离与蒸馏实践](SubAgent上下文隔离与蒸馏实践.md)）

### 4.1 模式一：串行（Sequential）—— 流水线

**结构**：上一步的产出是下一步的输入，像工厂流水线的不同工站。

```
Manager: "重构这个模块，不能破坏任何调用方"
   │
   ├─→ [子Agent A] 搜索所有调用点
   │      返回：23 处调用，分布在 5 个文件，3 种用法
   │
   ├─→ [子Agent B] 基于 A 的结论，分析每种用法的兼容性风险
   │      返回：18 处无影响，4 处需适配，1 处有隐患
   │
   └─→ [子Agent C] 基于 B 的结论，执行重构 + 逐处适配
          返回：diff + 验证结果
```

**关键特征**：每步**必须**等上一步的结论才有意义；A/B/C 看到的是不断精化的上下文。
**适用**：任务有天然的阶段依赖（先调研 → 再设计 → 后执行）。
**要点**：Manager 自己不读原始文件，只持有三个蒸馏结论——上下文始终干净。

### 4.2 模式二：并行（Parallel）—— 分头行动

**结构**：多个子 Agent 同时出发，各自独立完成任务，Manager 汇总。

```
Manager: "给缓存选型做调研，对比三个方案"
   │
   ├─→ [子Agent A] 调研 Redis 方案 ─┐
   ├─→ [子Agent B] 调研 Tair 方案  ─┼─→ 同时进行
   ├─→ [子Agent C] 调研自建方案  ─┘
   │
   └─← 汇总三份报告 → Manager 做决策
```

**关键特征**：任务彼此**真正独立**（互相不需要对方的产出）。
**适用**：多方案对比、多文件批量审查、多模块独立修改。
**陷阱**：如果任务其实有隐含依赖（比如三个方案调研其实要共享同一个约束条件），并行结果会在汇总时打架——**并行前先自问：这些任务真的互不依赖吗？**

### 4.3 模式三：层级（Hierarchical）—— 树状委托

**结构**：子 Agent 自己也能派子 Agent，形成委托树。

```
Manager: "给整个服务做回归测试并出报告"
   │
   ├─→ [子Agent A] 测试执行总负责
   │      ├─→ [孙Agent A1] 跑单元测试
   │      └─→ [孙Agent A2] 跑集成测试
   │
   └─→ [子Agent B] 报告生成负责
          └─→ [孙Agent B1] 生成覆盖率分析
```

**关键特征**：**逐级委托，逐级汇报**。Manager 只跟 A/B 打交道，A1/A2 的细节不进入 Manager 上下文。
**适用**：任务天然分层（项目 → 模块 → 子任务），常见于大型代码库的批量改造。
**风险**：树太深会失控——错误发生在深层时，Manager 无法直接感知，只能看到失真的逐级摘要。**实践上限：两层，三层及以上就该重新审视任务拆分**。

### 4.4 模式四：迭代（Iterative）—— 生成器 vs 批评家

**结构**：同一流程反复执行，输出质量逐轮爬升，直到达标或触达轮次上限。

```
Manager: "把这段核心代码打磨到可上线质量"
   │
   循环 ┌→ [子Agent A·生成器] 产出/修改代码
        │        ↓
        │  [子Agent B·批评家] 审查 A 的输出，列出问题
        │        ↓
        └── B 的问题清单 → 回到 A 的下一轮输入
   │
   └─ 终止条件：B 认为达标 / 达到轮次上限
```

**关键特征**：**对抗出质量**——A 每轮都被 B 挑刺，被迫改进。本质是用流程循环兑换单次推理的质量。
**适用**：质量敏感且验收标准清晰的产出（核心代码、安全审计、关键文档）。
**成本警告**：N 轮迭代 ≈ N 倍 token。没有明确终止条件的迭代循环就是烧钱黑洞——**必须设轮次上限**。

### 4.5 四模式速查表

| 模式 | 结构隐喻 | 前提条件 | 典型场景 | 主要风险 |
|---|---|---|---|---|
| 串行 | 流水线 | 步骤间有依赖 | 调研→设计→执行 | 中间结论失真逐级放大 |
| 并行 | 分头行动 | 任务真独立 | 多方案对比 | 隐含依赖导致汇总打架 |
| 层级 | 树状委托 | 任务天然分层 | 大代码库批量改造 | 树深失控，错误被摘要掩盖 |
| 迭代 | 生成-批评对抗 | 验收标准清晰 + 轮次上限 | 质量打磨 | token 成本 N 倍 |

**选择口诀：有依赖串行，真独立并行，天然分层用层级，质量打磨用迭代。**

## 5. 本篇深度总结

### 总结一：九层模型的三分法

把九层重新归类，得到一个更本质的三分法——**供给系统（1/2/3/5）、触发与干预系统（4/6）、边界与验收系统（7/8/9）**。评估任何 Agent 产品（包括自研），先问三系统是否齐备：只做供给的是"能力演示"，三系统齐备才是"工程产品"。自研 harness 最常见的缺陷就是第三系统的缺失（只给能力，不设边界，无验收闭环）。

### 总结二：大型项目的那一环 = 验收，而非更多能力

我的六层清单遗漏验收闭环，恰恰反映了普遍直觉偏差：以为 AI 编码落地的问题是"模型还不够强/工具还不够多"。实际是**验证产能跟不上生成产能**。模型每升级一代，生成速度翻倍，这个剪刀差就扩大一倍——验收闭环的价值随模型变强而**上升**而非下降。

### 总结三：Plan Mode 与 SDD 的分歧是哲学分歧，不是完成度分歧

Claude Code 不内置 SDD 不是没做到，而是判断**不该做**：spec 厚度应与模型能力成反比。这个押注如果成立，意味着 SDD 类工具的价值窗口是"模型能力不足的过渡期"。（这个论断的完整推演与反面论证，见系列第四篇。）

### 总结四：子 Agent 的经济学本质

四种编排模式统一在一个第一性原理下：**上下文是稀缺资源，编排的本质是上下文的预算分配**。串行是按时间分期付款，并行是按任务切块，层级是逐级汇总结账，迭代是对同一账户反复充值。设计编排方案时，先算上下文预算，再谈智能分工。
