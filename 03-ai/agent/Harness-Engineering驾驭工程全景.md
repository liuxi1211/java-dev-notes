# Harness Engineering（驾驭工程）全景

> 本篇是四篇系列笔记的第一篇，回答一组层层递进的问题：
> 1. Harness Engineering 到底是什么？有没有准确定义，还是又是一轮概念炒作？
> 2. 它是怎么发展出来的？从 Prompt 工程到驾驭工程中间发生了什么？
> 3. 有行业规范吗？是每家各搞一套，还是有收敛的共识？
> 4. 当前落地的真实现状是什么水平？

核心论点：
- **Harness 的本质是"能力与约束的乘法"**：可靠交付 = 模型能力 × 驾驭质量，驾驭质量趋近于 0，再强的模型也输出垃圾
- **模型能力商品化之后，竞争全面转移到 harness 层**——同样调 Claude，不同产品效果差数倍，差的不是模型，是 harness
- **协议栈已经收敛**（MCP 赢了工具协议之战），但 **harness 的编排哲学各 家仍然分歧**，Anthropic（Claude Code）目前是最完整的参考实现

---

## 1. 准确定义：Harness 到底是什么

### 1.1 词源与软件工程先例

Harness 的本义是**马具/挽具**——把马的原始马力转化为犁地、拉车这种**可控、可指向的做功**的那套皮带与挽具装置。马再壮，没有挽具，力量就无法被驾驭。

软件工程里早有先例：**Test Harness（测试治具/测试夹具）**——包在被测代码外面、负责注入输入、捕获输出、模拟依赖的那层脚手架。被测代码本身不变，换一套治具就能跑出不同的测试场景。

**Agent Harness 继承的就是这个语义**：包在 LLM 外面的那层运行时系统。

### 1.2 准确定义

> **Harness Engineering（驾驭工程/治具工程）：围绕 LLM 构建运行时约束与供给系统的工程学科。它不负责让模型变聪明，它负责让模型的聪明可控、可验证、可复现地转化为可靠交付。**

拆开看，一个 Agent Harness 要回答四个问题：

| 问题 | Harness 提供的能力 | 失败模式（没有这层会怎样） |
|---|---|---|
| **模型看到什么？** | 上下文供给：CLAUDE.md、代码库检索、记忆、压缩 | 上下文污染，模型"忘了"任务，或被无关信息带偏 |
| **模型能做什么？** | 工具接入：MCP、文件系统、Shell、Skill | 模型只能"说"不能"做"，或者工具混乱互相踩 |
| **模型不能做什么？** | 约束：权限系统、沙箱、Hooks 拦截、审计 | 一条 prompt injection 就能把代码库删了 |
| **怎么知道做对了？** | 验收闭环：测试、lint、编译、checkpoint、人审门 | 模型说"完成了"，实际是幻觉，错误静默累积 |

### 1.3 一个反直觉的认知：Harness 不是让 Agent 更强，而是让 Agent 更稳

这是最容易误解的一点。Harness 不提升模型智力上限，它压的是**方差**：

- 裸模型跑同一个任务 10 次：2 次惊艳，5 次平庸，3 次灾难
- 好的 harness 跑同一个任务 10 次：8 次可用，2 次平庸，0 次灾难

工程交付要的不是惊艳，是**可预期的下限**。这就是为什么 harness 是"工程"——它处理的是可靠性问题，不是能力问题。

## 2. 发展过程：三阶段演进

### 2.1 时间线总览

```
2022 ────────── 2023 ────────── 2024 ────────── 2025 ────────── 2026
  │               │               │               │               │
  ChatGPT         Prompt Eng      Context Eng     Harness Eng     Harness 竞争
  时代            时代            时代            时代            常态化
  "怎么问"        "怎么问"        "喂什么"        "怎么框"        "框的好坏"
                  │               │               │               │
                  AutoGPT 失败     Agents 平台期    Claude Code     终端 Agent
                  (裸奔 agent)    "agents 不work"  Codex CLI       成为主流
                                  │               Cursor 崛起      开发工具
                                  MCP 开源
                                  (2024.11)
```

### 2.2 第一阶段：Prompt Engineering 时代（2023）

- 关键词：角色扮演、Few-shot、CoT、结构化输出
- 核心假设：**效果差距来自"怎么问"**
- 崩塌点：AutoGPT（2023.03）——第一个现象级"自主 Agent"，给了模型工具和循环，结果在稍微复杂的任务上就无限跑偏、死循环、烧 token。业界第一次集体意识到：**光有 loop 和工具，没有约束系统，agent 不可用**

### 2.3 第二阶段：Context Engineering 时代（2024）

- 关键词：RAG、上下文窗口管理、记忆压缩、"垃圾进垃圾出"
- 核心假设：**效果差距来自"模型看到什么"**
- 标志性认知转变：Anthropic 把 prompt engineering 升级描述为 context engineering——**在有限的上下文窗口里，为正确的任务、在正确的时机、提供恰好够用的信息**
- 这个阶段的遗产：上下文被承认为**稀缺资源**，一切后续 harness 设计（Subagent 隔离、Skill 按需加载、记忆分层）都建立在这个前提上

### 2.4 第三阶段：Harness Engineering 时代（2025 至今）

- 关键词：Claude Code、Codex CLI、AGENTS.md、MCP 生态、沙箱、Skills、Hooks
- 核心假设：**模型能力已经够用且商品化了（大家都能调到同级模型），效果差距来自"模型外面那层框"**
- 直接证据：
  - 同样的 Claude Sonnet，接进不同的 harness 产品，可完成任务的复杂度差一个数量级
  - 2024 年"agents don't work"的共识，到 2025 年被 Claude Code 推翻——**模型没有换代级提升，推翻共识的是 harness 工程**

### 2.5 演进的内在逻辑（深度总结）

三个阶段不是并列的潮流，是**逐层外包**的关系：

```
Prompt Eng  解决：单次交互的质量     →  被吸收进 harness，成为 prompt 模板层
Context Eng 解决：多轮任务的信息供给 → 被吸收进 harness，成为上下文管理层
Harness Eng 解决：端到端交付的可靠性 → 当前竞争主战场
```

每一代方法论都没有死，而是**降级成下一代的一个内部组件**。今天在 Claude Code 里，prompt 工程活在 system prompt 和 skill 描述里，context 工程活在压缩策略和 subagent 隔离里。理解这一点，就不会把 harness 看成又一层新概念，而是看成分层的沉淀。

## 3. 协议栈：标准化的现状

Harness 工程没有 ISO 规范，但**协议层已经收敛**。当前格局：

| 协议 | 发起方 | 时间 | 解决什么 | 类比 | 现状（2026） |
|---|---|---|---|---|---|
| **MCP**（Model Context Protocol） | Anthropic | 2024.11 | agent ↔ 工具/数据 | USB-C | **事实标准**，OpenAI/Google 均已支持 |
| **A2A**（Agent2Agent） | Google → Linux Foundation | 2025.04 | agent ↔ agent | HTTP | 试点期，落地集中在企业互操作 |
| **AGENTS.md** | OpenAI 推动 | 2025 | 项目级指令文件格式 | README | 事实标准，各家产品互相兼容读取 |
| **Agent Skills** | Anthropic | 2025.10 | 可安装的 SOP 包 | npm 包 | 快速普及中，开源标准 |

三个关键判断：

1. **工具协议之战已经结束，MCP 赢了**。OpenAI 在 2025 年初宣布 Codex 支持 MCP 之后，工具接入层不再有分裂。这相当于给所有 harness 厂商发了同一套"插座"。
2. **A2A 与 MCP 不是竞争关系，是互补的不同层**：A2A 通信的两端 agent，各自在内部用 MCP 调自己的工具。MCP 是垂直整合（agent 到工具），A2A 是水平互联（agent 到 agent）。（详见系列第三篇：[A2A落地边界与多Agent决策框架](A2A落地边界与多Agent决策框架.md)）
3. **协议标准化 ≠ Harness 标准化**。MCP 统一了"怎么接工具"，但"怎么编排上下文、怎么约束、怎么验收"仍然是各家核心竞争力，不开放也不统一。**这就是"有没有行业规范"这个问题的准确答案：协议层有且已收敛，工程层没有规范，只有各家实现与公开的方法论（如 Anthropic 的 Building effective agents）。**

## 4. 各家实现差异对比

### 4.1 主流产品横评

| 厂商 | 产品 | 指令文件 | 工具协议 | 扩展机制 | 安全边界 | 特色与差异 |
|---|---|---|---|---|---|---|
| Anthropic | Claude Code | CLAUDE.md / AGENTS.md | MCP | Skills + Hooks + Subagents | 权限模式 + 沙箱 + 审计日志 | **harness 最完整**，九层俱全 |
| OpenAI | Codex（CLI/云） | AGENTS.md | MCP | Config + 云环境 | **云沙箱优先** | AGENTS.md 标准推手，异步云端执行 |
| Anysphere | Cursor | .cursor/rules | 自有工具层 | Rules + Notepads | IDE 沙箱 | **代码库语义索引**是核心差异点 |
| Google | Gemini CLI | GEMINI.md | MCP | 扩展 | 基本权限 | 开源，免费额度大 |
| Cognition | Devin / Windsurf | rules | 自有 | — | 云沙箱 | 云异步 agent，主打并行任务 |

### 4.2 分歧的哲学（深度总结）

各家差异表面是功能表，底层是**对"谁来负责可靠性"的不同押注**：

- **Anthropic 押注"本地 + 人审"**：harness 层做厚（Hooks/权限/记忆/子代理），信任链最后一环永远是人。适合复杂仓库的深度工程。
- **OpenAI 押注"沙箱 + 异步"**：与其约束 agent，不如给它一个炸不坏的环境（云沙箱），失败了就重跑。适合任务可独立验证的场景。
- **Cursor 押注"检索即驾驭"**：认为 harness 的核心是让模型**看得懂代码库**（语义索引），约束反而是次要的。适合 IDE 内高频小循环。

没有哪家"正确"，这是同一问题（可靠性）在不同成本函数下的不同最优解。**选型时真正该问的不是功能清单，而是：你的任务失败成本高不高（高 → 人审型），还是失败可廉价重试（高 → 沙箱重试型）。**

### 4.3 已经收敛的共识

尽管哲学分歧存在，以下四点已成为跨厂商事实标准，可以视为"最小 harness 公约数"：

1. **项目级指令文件**（CLAUDE.md / AGENTS.md / GEMINI.md）——且互相兼容读取
2. **MCP 作为工具接入层**
3. **权限分级**（读/写/执行分离，敏感操作需确认）
4. **结构化的 SOP 注入机制**（Skill 或等价物：按需加载的 Markdown 工作手册）

## 5. 落地现状的诚实评估（2026）

### 5.1 成熟的部分

- **编程场景**：终端 Agent（Claude Code / Codex CLI）已进入一线工程师日常工作流，处理中小型任务的可靠率可接受。harness 在编程场景成熟的原因：验收闭环可执行（编译/测试/lint 是天然的客观裁判）
- **工具接入**：MCP 生态爆发，主流 SaaS 均有 server，接工具的成本从"周"降到"小时"

### 5.2 半成品的部分

- **长任务**：数小时的自主任务仍然方差大，各家都在用 checkpoint + 人审门打补丁
- **记忆**：跨会话长期记忆仍没有公认好方案，各家都在"压缩 + 检索"的路上摸索
- **多 Agent**：subagent 编排可用，但跨组织的 A2A 基本停留在试点（详见系列第三篇）

### 5.3 落后宣传的部分

- **通用行业（非编程）**：harness 理念通用，但工具链几乎全部为编程场景优化。通用行业的"验收闭环"缺乏客观裁判（没有编译器告诉你"这份营销文案对不对"），所以 harness 的最难点——验证——在通用行业远未解决
- **企业级治理**：审计、合规、多租户隔离在协议层有占位，工程实现参差

## 6. Anthropic 的演进路线（作为 harness 工程的活教材）

Claude Code 从 2025.02 research preview 到现在的逐月加层过程，本身就是一部 harness 工程演进史——**每一层都对应一类真实故障模式**：

| 时间 | 加的层 | 对应解决的故障 |
|---|---|---|
| 2025.02 初版 | 基础 Loop + CLAUDE.md + 工具 | 裸模型不可用 |
| 2025 上半年 | Subagents | **上下文污染**：搜索结果把主上下文撑爆，推理质量骤降 |
| 2025 上半年 | Hooks | **不可编程的干预**：所有防线都是内置死的，用户无法在自己的流程节点插逻辑 |
| 2025 年中 | Memory tool | **跨会话失忆**：每个新会话从零认识代码库 |
| 2025.10 | Agent Skills | **上下文爆炸的另一面**：所有 SOP 常驻上下文 → 按需加载 |
| 持续 | 权限 + 沙箱 + Checkpoints | **错误不可回滚** + **安全边界** |

这个演进揭示 harness 工程的核心方法论：**不是预先设计出九层，而是从最小可用开始，每次只针对被验证的失败模式加一层。** 这与 Anthropic 在《Building effective agents》中的立场完全一致：从简单开始，按失败证据增加复杂度。（九层模型详解见系列第二篇：[Claude-Code-Harness深度拆解](Claude-Code-Harness深度拆解.md)）

## 7. 本篇深度总结

### 总结一：Harness 是"约束的艺术"，不是"能力的艺术"

十年后回看，Prompt Engineering 教大家"怎么问"，Context Engineering 教大家"喂什么"，Harness Engineering 教的是"**怎么框**"——框的隐喻就是马具：不是否认马力，而是承认马力必须被驾驭才能做功。三者的关系是沉淀而非替代。

### 总结二：可靠交付是乘法不是加法

```
可靠交付 = 模型能力 × 驾驭质量
```

乘法关系意味着：**harness 是杠杆也是天花板**。模型翻倍，交付翻倍；harness 归零，交付归零。2023 年 AutoGPT 的失败不是模型太弱（当时模型确实弱），而是乘了零。同理，今天的最强模型配上裸 loop，依然会在复杂任务上重现 AutoGPT 的灾难。

### 总结三：判断任何 Agent 产品的成熟度，看四个问题

不看宣传看 harness：模型看到什么（上下文供给）？能做什么（工具）？不能做什么（约束）？怎么知道做对了（验收）？**四个问题答不齐的产品，都是裸奔的模型套壳。**
