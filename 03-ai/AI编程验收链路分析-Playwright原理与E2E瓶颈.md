# AI 编程验收链路分析

> 背景：很多公司推广"AI 编程落地 + Playwright 自动验收"，实际体验中链路并不成熟。本文系统性分析该技术链路的真实成熟度、业界实践与 ERP 场景的实战诊断。

## 1. 核心误解澄清：Playwright ≠ 图片识别

最常见的误解是把 Playwright 当成"AI 看屏幕操作"。实际上：

**Playwright 全程不看图片**。原理是通过浏览器调试协议（CDP / 自研协议）与浏览器内核直连，以程序 API 方式操作和读取页面——和 F12 DevTools 是同一套底层能力。

```
测试脚本 → Playwright 客户端 → WebSocket(JSON指令) → 浏览器调试协议 → 内核执行
```

- `page.click('#submit')`：内核 DOM 查询 → auto-wait 检查可见/可点/稳定 → 计算坐标 → 派发真实鼠标事件
- `expect(locator).toBeVisible()`：验证 DOM 属性与渲染状态，纯结构化数据
- `screenshot()`：只是产物输出，不是感知方式

**类比：Playwright = 给浏览器装了个 JDBC**。程序感知页面走 DOM 协议（确定性 API），人类才靠像素。真正"看图操作"的是 Computer Use / Browser Use 类视觉 Agent（截图 → VLM → 坐标点击），那是另一条平行路线，灵活但不可靠。

结论：主流 "AI + Playwright" 链路中（AI 写测试 → Playwright 跑 DOM 断言），**没有任何环节做图片识别**。Playwright 是整条链路里最成熟的一环。

## 2. 两条验收路线的成熟度

| 路线 | 做法 | 成熟度 |
|---|---|---|
| A：DOM 断言 | AI 生成 Playwright 结构化断言 | 工具成熟，但 AI 生成质量有问题 |
| B：视觉验收 | 截图 + VLM 判断"对不对" | demo 好看，生产不可靠 |

路线 B 的三个真实瓶颈：
1. **VLM 像素级定位弱**：理解语义容易，"偏移 3px"、精确坐标难
2. **无 ground truth + 讨好性偏差**：VLM 倾向说"看起来没问题"；像素 diff 又误报多
3. **多步累积误差**：每步 90% 准确率，10 步只剩 35%

路线 A 的两个深层问题：
1. **自证陷阱**：AI 写功能 + AI 写验收测试，生成方和验收方同一模型，错误共振而非互相纠正。测试通过 ≠ 功能正确
2. **AI 修测试而非修产品**：E2E 挂了，AI 把选择器"修"到通过为止，测试从验收者退化为追认者——最隐蔽的坑

## 3. 业界当前的分层验收实践

后端单测之后的前链路验收，业界真实做法是分层防线：

| 层级 | 手段 | 自动化 | 可信度 | 评价 |
|---|---|---|---|---|
| API 契约 | OpenAPI 校验 / Pact / Schemathesis | 全自动 | 高 | ✅ 真好用 |
| 组件测试 + 快照 | Testing Library / Storybook + Chromatic | 全自动 | 中高 | ✅ 性价比最高 |
| 视觉回归 | 像素 diff + 人审 | 半自动 | 高 | ✅ 务实方案 |
| E2E 冒烟 | 10~20 条核心路径 | 半自动 | 中 | ⚠️ 脆但有用 |
| 真人 UAT | staging 抽查 | 手动 | 最高 | 无法替代 |

核心共识：**把"AI 判断对错"改造成"机器找差异 + 人做判断"**——diff 是确定性的，不需要智能。

### 3.1 契约测试（Pact 双向流程）

```
① 消费方 mock 掉提供方跑测试 → Pact 自动记录实际依赖为契约文件
② 契约提交到 Pact Broker
③ 提供方 CI 拉取所有契约，用真实代码回放验证能否满足
✓ 全满足可发布；✗ 任一不满足挡发布
```

价值：无全链路环境下守住接口兼容性。契约独立于代码存在（先约定后实现），红就是真的红——**是解决 AI 验收"自证陷阱"的少数成功模式**。

### 3.2 组件测试

只渲染单个组件，mock 掉 API 与全局状态，测 props/交互 → DOM/回调。要点：
- 用 role/text 定位（用户视角），不用 CSS class → 绕开选择器脆弱
- Storybook stories 枚举组件全部状态 + 截图 diff，人只审 diff 图
- **AI 生成测试本质是上下文理解问题，上下文越小越准**——组件测试上下文小、全 mock、毫秒级，是 AI 时代性价比最高的防线

### 3.3 Spec-first 趋势

人先写形式化验收标准（Gherkin BDD / OpenAPI / 设计 token 契约），测试从规格生成而非从代码生成。是"AI 全自动验收"逻辑上唯一成立的路径，但写规格成本高。

## 4. E2E 为什么是瓶颈

E2E = 模拟真实用户从浏览器走完整业务路径，穿透前端 + 接口 + 后端 + DB 全链路。

四大痛点：
1. **Flaky（假失败）**：时序竞态、选择器失效、环境/数据污染。健康套件 flaky 率 1~5%，治理差达 20%+。经常红但重跑又绿 → 失去门禁资格（狼来了效应）
2. **定位成本高**：红灯可能是前端/接口/后端/数据/测试自身/环境任一问题
3. **维护与 AI 放大**：见上文"修测试不修产品"
4. **慢**：一条 10~60 秒，只能当发布门禁，但稳定性又不配当门禁

应对：收缩（只保核心路径）+ 下沉（组件/契约层）+ 视觉断言只做 diff 不做判断。

## 5. ERP 实战诊断（真实案例）

场景：用 Playwright 验收自研 ERP。现象：**登录（含动态验证码）耗时半小时且经常失败；动态菜单（下拉勾选后才展示）穿越半小时，整体成功率仅 30%**。

### 诊断

1. **验证码对抗是方向错误**：验证码的目的就是反自动化，硬识别等于对抗。数学上：每步 95% 成功率 × 20 步 ≈ 36%，30% 成功率完全吻合——不是某环节烂，是多步串行的必然可靠性衰减。
2. **方案层错误**：把工具当方案。跳过分层设计直接全 E2E 化，等于不做单测直接全链路压测。ERP（深交互、动态渲染、复杂权限）恰是 E2E 最不友好的系统类型，而推广 demo 用的都是两级菜单 SaaS 后台这种最友好场景。

### 修正方案（按投入产出排序）

| 动作 | 成本 | 收益 |
|---|---|---|
| 测试环境关验证码 + storageState 复用登录态 | 半天 | 消灭最大失败源 |
| URL 直达（page.goto 路由）代替菜单穿越 | 每页查一次路由 | 步骤从 20 步降到 3 步 |
| 只固化 5~10 条核心路径 E2E（钱/库存/单据流） | 一周 | 成功率 30% → 90%+ |
| 业务逻辑验证下沉 API 层测试 | 持续 | ERP 验收主战场（金额/库存/审批本质是接口逻辑）|
| 菜单等动态组件单独组件测试 + data-testid | 中 | 菜单回归脱离全链路 |

storageState 复用登录态示例：

```python
# 登录一次保存状态
context.storage_state(path="erp_auth.json")
# 后续所有测试复用，验证码问题从 N 次降为 1 次
context = browser.new_context(storage_state="erp_auth.json")
```

关键认知：**E2E 测试不需要走 UI 导航**。菜单穿越的目的只是到达功能页面，而页面通常有直连 URL。

## 6. 总结

- Playwright 本身生产级成熟，问题在围绕它的"AI 自主判断"部分与方案设计
- 当前业界真实水平：人工回归量压掉 60~80% 已是优秀，剩余视觉细节/交互体验/业务合理性无技术可可靠替代人
- 验收自动化正确路径：**契约测试 + 组件测试/快照 + 视觉 diff 人审 + 少量核心 E2E + 真人把关**，而非全 E2E 化
- 评估推广方方案时问三个问题：验证码怎么处理、动态菜单怎么定位、flaky 率预期多少——答不上来说明方案没做完
