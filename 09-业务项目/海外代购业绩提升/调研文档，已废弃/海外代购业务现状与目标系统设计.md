# 海外代购业务现状与目标系统设计

> 本文是「海外代购业绩提升」专题的第一篇，定位为 **业务侧方案文档**，不是技术细节文档。技术实现（ES schema、字段映射规则、采集 Adapter 规范等）见各模块独立文档。
> 对标对象：**云汉芯城（ickey.cn）**，2025 年电子元器件销售营收 **32.06 亿**，其中海外 2.97 亿、同比 +89.74%。我司当前海外代购规模约 **6 亿**，差距明显。

---

## 一、业务背景

### 1.1 两条业务线的关系

我司主营业务是 **电子元器件自营**：自采、自仓、自卖，拥有完备的商品资料（参数、图片、详情、规格书）。

为拓展长尾业绩，另设 **海外代购** 业务线：
- 对接海外分销商（digikey、mouser、arrow 等 **26 家**），把它们的库存放到我司商城售卖。
- 本质是 **信息撮合 + 履约代采**：用户在我司下单，我司再去上游下单、走跨境物流、报关、交付。
- 商业逻辑：覆盖自营打不到的长尾型号 / 紧缺料 / 停产料，吃「小散临急」的利润。

### 1.2 履约链路：自营与代购的分界点

这是理解后续所有改造的前提：

```
【代购特有段】                    【复用自营段】
上游供应商发货                    自营仓储收货
   ↓                                ↓
跨境运输                         仓储管理
   ↓                                ↓
报关清关  ← 仅代购有               拣货打包
   ↓                                ↓
发货到自营仓 ────────────────────→ 转发给客户
```

**关键认知**：代购和自营的物流在后半段（仓储→客户）是合并的，前半段（供应商→报关→入仓）是代购独有的。这意味着：
- 后半段体验（出库速度、包装、配送）和自营一致，**不是改造重点**。
- 前半段体验（报关时效、上游发货速度、入库准确性）才是代购的差异化瓶颈。

### 1.3 自营 × 代购的资料现状

- 自营商品资料**完备**：参数、图片、详情、规格书齐全。
- 代购商品资料**很薄**：只有上游给的基础字段（型号、品牌、库存、价格），辅助资料缺失。
- 现状做法：**简单通过「型号 + 品牌」做映射**，代购商品复用自营的资料字段。
- **核心问题**：映射规则太简单（型号 + 品牌不完全唯一），无法保证映射命中的就是同一个商品，**所以不敢放开把两者深度融合**。一旦映射错（把 A 型号的参数挂到 B 型号上），会导致详情页参数错误、客户下单错料，风险高于收益。

> 这是后续「商品中心统一模型」要解决的核心问题之一：**用更可靠的归一化规则，把映射准确率拉到能放心深度融合的水平**。

## 二、当前现状（三层架构）

### 2.1 接口层（数据采集）

| 维度 | 现状 |
|---|---|
| 供应商数 | 26 家（digikey、mouser、arrow 等） |
| 采集方式 | 爬虫定时抓取 + 商务对接（供应商定期推送） |
| 数据规模 | **约 1 亿条**商品数据 |
| 更新频率 | 最慢一周一次，最快一天一次 |
| 数据质量 | 基础字段（库存、价格、型号、品牌）齐全；辅助字段（参数、详情、图片、规格书）部分有、部分无 |
| 主要问题 | 数据异构严重、新鲜度差异大、非实时 |

### 2.2 存储层（数据落地）

- **每个供应商一个独立 ES 索引**，给什么存什么，只做轻量清洗。
- 唯一标准化动作：映射到自营商品，复用自营完备资料做内容增强（但受限于 1.3 节的映射准确率问题）。
- 问题：
  - 26 个索引 = 26 套字段 schema，跨供应商无法统一检索 / 聚合 / 比价。
  - 没有统一 SPU / SKU 概念，跨供应商的同一型号无法归并。

### 2.3 搜索层（用户访问）

- 每个供应商索引对应一个独立搜索接口，商城检索时本质是 N 个接口分别查、再合并。
- 体验问题：
  - 同一型号在多个供应商都有货时，无法做「最优货源推荐」（最便宜 / 现货 / 交期最短）。
  - 不能跨供应商比价、聚合库存。
  - 无法做替代料推荐、参数搜索、BOM 配单这些高转化能力。

## 三、问题诊断：为什么我们 6 亿，云汉 32 亿

不是流量问题，是 **供给侧的数字化深度** 问题。逐条对照：

| 维度 | 我司现状 | 云汉芯城（公开数据） | 差距含义 |
|---|---|---|---|
| 数据规模 | 1 亿条原始数据 | 4400 万 SPU + 9300 万参数替代关系 | 我们数据量更大但 **没结构化**，价值密度低 |
| 数据模型 | 26 个供应商各一个索引 | 统一数据中台，标准化 SPU/参数 | 我们跨源检索、统计、推荐都做不了 |
| 商品资料 | 部分有、靠简单型号+品牌映射 | 全量结构化参数 + 规格书 + ECAD 模型 | 详情页转化差 |
| 搜索能力 | 型号 / 关键词 | 型号 + **参数检索** + **国产替代** + **垂直搜索引擎** | 用户找不到 = 不下单 |
| 高阶工具 | 无 | **HiBOM**：BOM 表分钟级解析、准确率 >90% | 错失整批 BOM 询价订单 |
| 客户接入 | 商城下单 | **API 直连客户 ERP**，嵌入式专属商城 | 大客户采购流程一体化 |
| 国产化 | 无 | 78 万替代关系库，搜索自动置顶国产方案 | 错过最大增长红利 |

> **结论一句话：我们囤了 1 亿条数据，但没把它变成可用的知识。** 后续所有改造都要围绕「把数据变成知识、把知识变成体验、把体验变成订单」展开。

## 四、目标系统设计

### 4.1 总体架构（六层）

```
┌───────────────────────────────────────────────────────────────┐
│  ⑥ 体验层：商城搜索 / 参数筛选 / BOM 工具 / 国产替代 / API-ERP   │
├───────────────────────────────────────────────────────────────┤
│  ⑤ 搜索层：统一商品搜索引擎 + 垂直搜索引擎（参数/替代）           │
├───────────────────────────────────────────────────────────────┤
│  ④ 商品中心：统一 SPU 主数据 + 参数库 + 替代关系图谱              │
├───────────────────────────────────────────────────────────────┤
│  ③ 数据中台：标准化 / 归一化 / 主数据管理（MDM） / 质量治理        │
├───────────────────────────────────────────────────────────────┤
│  ② 采集层：26 家供应商统一 Adapter / 实时 API + 定时爬虫          │
├───────────────────────────────────────────────────────────────┤
│  ① 数据源：digikey / mouser / arrow / TI / ADI / 国产原厂 …       │
└───────────────────────────────────────────────────────────────┘
```

核心思想：**从「N 个供应商 = N 个索引」升级为「N 个供应商 → 1 个商品中心 → 1 个搜索引擎」**。供应商越多，商品中心越厚，搜索体验越好，形成正向飞轮。

### 4.2 关键设计原则

1. **数据中台是护城河**。把 1 亿条杂乱数据，清洗成结构化的 SPU + 参数 + 替代关系，这是 32 亿 vs 6 亿的根因。
2. **自营与代购统一商品模型**。把现在的「型号+品牌简单映射」升级为「多维度归一化 + 置信度评分」，准确率拉到能放心深度融合的水平，打开自营资料反哺代购的空间。
3. **搜索体验决定转化**。型号搜索只是及格线，参数搜索、替代推荐、BOM 配单才是拉开身位的能力。
4. **履约确定性比价格更重要**。海外代购的最大痛点是交期、报关、真假。重点优化代购特有段（供应商→报关→入仓）。

## 五、各层方案

### 5.1 采集层：统一 Adapter 模式

将每家供应商的采集逻辑统一为一套 Adapter 规范，按供应商重要性分级采集：

- **核心供应商**（digikey、mouser、arrow）：走官方 API，小时级或实时更新。
- **长尾供应商**：爬虫定时采集，T+1 更新。
- **触发式回查**：用户搜索 / 下单时实时回查上游，保证履约前库存准确。

**业务价值**：数据新鲜度可控，履约前能拿到准实时库存，减少因库存数据过期导致的失单。

### 5.2 数据中台：归一化 + 主数据管理 ⭐ 最核心

数据中台是把 1 亿条杂乱数据清洗成结构化统一商品模型（SPU + SKU）的关键环节，是所有上层能力的地基，提供 MPN 归一化、质量评分、资料增强四大能力。

#### 5.2.1 统一商品模型

定义 SPU（标准产品单元，型号维度）和 SKU（报价维度，= 一个 SPU × 一个供应商 × 一个报价）两层数据模型，所有供应商数据映射到这套模型。

#### 5.2.2 MPN 归一化（最难也最值钱）

解决「同一颗料在不同供应商叫不同名」的问题：
- 后缀归一化（去掉包装后缀 TR / CT / ND）。
- 品牌别名映射（TI = Texas Instruments = 德州仪器）。
- 料号交���引用表（维护 brand + mpn 到各供应商内部料号的全局映射）。
- AI 辅助匹配（对规则匹配不上的，用向量相似度做候选，人工 review）。

**目标**：同一颗料，无论几个供应商供，都归到同一个 SPU 下。这是后续比价、聚合库存、替代推荐、自营代购深度融合的前提。

#### 5.2.3 数据质量治理

给每个 SPU 打三个质量评分，用于搜索排序加权，避免「一周前的库存」误导下单：
- **完整度**：参数、图片、规格书、描述是否齐全。
- **新鲜度**：库存 / 价格按更新时间衰减，过期数据降权展示。
- **可信度**：API 数据 > 商务推送 > 爬虫；官方授权 > 二级代理。

#### 5.2.4 资料增强

通过多层手段把代购商品的资料完整度从「部分有」拉到「绝大多数齐全」：
- 归一化准确率达标后，映射到自营的代购 SPU 直接继承自营资料。
- 未命中自营的，从 digikey / mouser / 原厂官网爬规格书 + 参数自动补全。
- 缺图：从规格书 PDF 第一页提取图像。
- 资料补充优先级按「近 30 天搜索量 × 缺资料程度」排序，保证人力投入在高价值料上。

**业务价值**：详情页转化率显著提升；自营代购的资料深度融合成为可能。

### 5.3 商品中心：统一主数据 + 替代关系图谱

#### 5.3.1 替代料知识图谱（对标云汉 9300 万关系）

构建三层替代关系：
1. **结构化参数匹配**（pin-to-pin）：封装、引脚、关键电气参数完全一致 → 自动判定兼容。
2. **功能替代**：核心功能一致、参数有差异 → 标注差异项，人工 review。
3. **国产化替代**：维护「进口料 → 国产料」专项映射，搜索进口料时自动置顶国产方案（政策红利）。

**业务价值**：覆盖「找不到料」「料太贵」「料停产」三类痛点，把搜索结果页的「无货」从死路变成「有替代可下单」，是海外代购的第二增长曲线。

#### 5.3.2 分类与属性模板

参考行业标准分类（借鉴 digikey / 云汉的分类树），每个品类定义属性模板（电阻的阻值/精度/封装；MCU 的核/主频/Flash/RAM/IO 数等）。

属性模板 = 参数搜索的 schema，没有它参数筛选就做不起来。

### 5.4 搜索层：统一搜索引擎

从「N 个供应商索引分别查、再合并」升级为「SPU + SKU 双索引统一搜索」，提供分级搜索能力：

| 能力 | 描述 | 价值 |
|---|---|---|
| L1 型号精确搜索 | 输入 MPN 直接命中，支持后缀容错 | 及格线 |
| L2 关键词 / 模糊搜索 | 支持中文同义词（如「单片机」=「MCU」） | 及格线 |
| L3 参数搜索 | 选品类 → 按参数模板筛选 | 差异化 |
| L4 跨供应商比价 | 同一 SPU 下聚合所有供应商的库存、价格、交期 | 差异化 |
| L5 替代料推荐 | 缺货 / 搜索结果页推 pin-to-pin & 功能替代 | 差异化 |
| L6 国产化置顶 | 进口料搜索结果自动置顶国产方案 | 政策红利 |
| L7 BOM 配单 | 上传 BOM，批量匹配、报价、缺料找替代 | 拿大客户 |

**排序策略**：综合文本相关性、库存健康度、资料完整度、货源数量、交期、热度，并对过期数据做惩罚。具体权重 A/B test 调。

**业务价值**：搜索结果从「能查到」升级为「能找到最优货源、能找到替代、能按参数筛」，转化率提升。

### 5.5 体验层：高转化工具

#### 5.5.1 HiBOM（BOM 智能配单）

用户上传 Excel BOM（一行一个料号 + 数量），系统批量匹配 SPU，输出：每颗料的匹配结果（命中 / 多义 / 未命中）、全货源最低价 / 最快交期报价、缺料自动推替代料、整单总价 / 预计交期 / 国产化率。

BOM 询价单通常是整批料、客单价高、复购稳定。BOM 解析准确率目标 >90%（对标云汉），关键在 MPN 归一化和同义词库。

**业务价值**：把零散型号询价升级为整批 BOM 询价，客单价量级提升。

#### 5.5.2 API-ERP 直连

对中大客户开放 API（搜索、报价、下单、订单状态全链路），提供「嵌入式专属商城」——客户在自家 ERP 里直接看到我们的库存和价格。

**业务价值**：把订单从「散单」升级为「长期合作」，中大客户的采购流程一体化后迁移成本高，营收天花板打开。

### 5.6 数据同步与一致性

采用业界通用方案：采集 → 消息队列 → 数据中台清洗 → 主数据库 → 增量同步到搜索引擎。搜索引擎只做检索投影，不做事务主库，保证最终一致性。库存 / 价格高频变更走增量更新，避免全量重建。

## 六、候选改造方向（按业务价值排序，最终优先级以诊断结论为准）

> 以下方向**不是固定路线图**，而是候选方案池。最终先做什么、后做什么，以第二篇《履约与商业体验诊断》输出的决策矩阵为准。这里先给出业务价值维度的初步判断。

### 方向 A：数据中台 + 统一搜索（地基）

**业务价值**：⭐⭐⭐⭐⭐
- 解决跨供应商无法比价、无法聚合库存的核心痛点。
- 是所有上层差异化能力（参数搜索、替代料、BOM）的前置依赖。
- 自营代购深度融合的前提（MPN 归一化准确率达标）。

**适用场景**：诊断显示「搜索命中率低」「跨供应商比价缺失」「详情页转化差」时，此方向为最高优先级。

### 方向 B：替代料知识图谱 + 国产化

**业务价值**：⭐⭐⭐⭐⭐
- 覆盖「找不到料」「料太贵」「料停产」三类高频痛点。
- 国产化替代是当前最大的政策红利。
- 直接打开第二增长曲线。

**适用场景**：诊断显示「缺货失单率高」「进口料价格竞争力不足」时，此方向优先级提升。

### 方向 C：履约链路优化（代购特有段）

**业务价值**：⭐⭐⭐⭐
- 重点优化代购特有段：供应商发货 → 报关 → 入仓。
- 后半段（仓储→客户）已复用自营，不是改造重点。

**具体子方向**：
- 上游库存实时性：降低因库存数据过期导致的履约失败。
- 报关时效：识别报关环节的瓶颈，优化清关流程。
- 上游供应商分级：识别履约表现差的供应商，做分级管理。

**适用场景**：诊断显示「履约率低」「交付周期长」「库存准确率低」时，此方向优先级提升。

### 方向 D：HiBOM + API-ERP（拿大客户）

**业务价值**：⭐⭐⭐⭐
- HiBOM 把零散询价升级为整批 BOM 询价。
- API-ERP 把散单升级为客户长期合作。
- 依赖方向 A 的商品中心能力。

**适用场景**：诊断显示「客单价偏低」「大客户占比低」「BOM 询价需求未被满足」时，此方向优先级提升。

### 方向 E：自营 × 代购深度融合

**业务价值**：⭐⭐⭐⭐
- 当前因映射规则简单不敢深度融合。
- MPN 归一化准确率达标后，可放开自营资料反哺代购。
- 自营客户可直接转化为代购客户（长尾型号导流）。

**适用场景**：方向 A 落地后自然衍生，建议作为方向 A 的二期目标。

---

## 七、结论

海外代购的 6 亿到 32 亿，差距不在供应商数量，而在「数据 → 知识 → 体验 → 订单」这条链路的完整度。优先把数据中台（SPU 主数据 + MPN 归一化 + 替代料图谱）和统一搜索引擎做扎实，其他能力都是长在这层之上的应用。

本篇给出的五个候选方向（A 数据中台 / B 替代料 / C 履约 / D HiBOM / E 自营代购融合）是完整的改造空间，**具体先做哪块、后做哪块，以第二篇《履约与商业体验诊断》输出的决策矩阵为准**——用数据排序，不靠主观判断。
