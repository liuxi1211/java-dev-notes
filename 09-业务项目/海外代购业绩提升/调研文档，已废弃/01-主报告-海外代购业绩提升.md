## 二、问题：差距根因

按确定性排序：

### 🟥 根因一：报价可信度低（最确定）

上游数据源不可控是行业硬天花板。但我们的问题不在这，而在拿到数据后**既没快速生效、也没兜住"天生不准"**：

- T+1 全量重建，白天看隔夜数据；实时刷新仅 3-4 家且只夜间跑，回查结果下次才生效，队列高峰期静默丢弃。
- **最致命**：下单链路有同步回查，但**失败时回退 ES 旧数据**——等于"没查到就假装有货"，是跑单/赔付的真正原因，而非"数据不实时"。

### 🟥 根因二：选错了"原子单位"（结构性，总根）

主体应是"型号"而非"某供应商的某条 SKU"。系统把这个关系**倒过来**：底层每家供应商一个独立索引（26 个互不相认），即便商品已映射到自营体系，**搜索侧也没用映射合并**——同一型号在各供应商间各搜各的，跨供应商比价、聚合库存、最优渠道推荐、替代料、参数搜索全做不出来。映射做了，搜索没用上。当前架构天花板是"26 家目录拼接"。

### 🟥 根因三：客户经营空白（最大乘数）

把代购当一次性撮合，系统无客户分层、复购提醒、报价跟进、客户画像。这是放大营收的**乘数杠杆**：获客成本固定时，复购深度直接决定 LTV，当前这个乘数几乎为 1，是被严重低估、一旦补上见效最快的方向。

### 🟧 根因四：履约链路不透明（信任地基）

"先销后采"跑通的另一半是交付稳。履约链路在系统中不透明，无法分段定位瓶颈——哪段慢、哪家供应商履约差，看不清就无法针对性优化。前半段（供应商发货→报关→入仓）是代购独有瓶颈。

### 🟧 根因五：对外渠道封闭 + 定价黑箱（机会缺口）

- **对外渠道**：B 端 API/ERP 对接完全空白，错失"别人系统帮我们卖货"的分销渠道。
- **定价**：加价率手工黑箱，无竞品比价、无动态调价，纯利润未被开发。

## 三、怎么解决：四大主题

所有改造围绕一条营收等式，每个杠杆对应一个乘数：

```
营收 = 可售供给 × 流量 × 转化 × 客单价 × 复购
        A1/A2    B3   B1/A1  C2/C3   C1
        └ AI(B2) 贯穿提效 ┘ └ 履约(D1)保接单，开放(D2)/数据资产(D3)拓新渠道
```
 
### A. 数据与供给底座（决定天花板）

| 杠杆                    | 现状                                               | 改革方向                                                                                             |
|-------------------------|----------------------------------------------------|------------------------------------------------------------------------------------------------------|
| **A1 商品中心化（地基）** | 供应商 SKU 中心，26 索引各搜各的，映射做了搜索没用上 | "型号"立为主体（Product），供应商报价降为挂在其下的 Offer；搜索引擎只做投影；事件驱动增量更新替代全量重建 |
| **A2 供给广度平台化**   | 加一家供应商要改多处代码                           | 供应商插件化：一份配置（适配器+字段映射+凭证+定价规则+新鲜度层级）即可接入                              |

A1 关键内容：统一商品模型（一型号 = 1 商品主数据 + N 报价）；**型号归一化**（后缀归一、品牌别名、料号交叉引用、AI 匹配 + 人工纠偏）；**数据质量三评分**（完整度/新鲜度/可信度，用于搜索排序）；系统记录用关系库，搜索降级为投影。

> **治理定位：全量聚合 + 透明标注 + 用户自筛，不替用户删数据。** 中心化的目的是让同型号能"排到一起"，不是让我们替用户决定留谁删谁。全部供应商数据接入、不删；质量分只用于默认排序权重和"更新于 X 小时前 / 数据陈旧"的透明标注；供应商始终作为一等属性保留并支持筛选——用户认准某家，即使其数据陈旧，也能按供应商筛出来、展开下单/询价。清洗只针对脏记录（爬虫错误包、参数乱码）与全供应商均无活跃报价的幽灵型号（转询价 / 沉冷池，不物理删），**绝不因"数据更新不及时"而清除某个真实存在的供应商**。成交前仍以实时回查确认为准，不拿隔夜数据冒充现货。

针对根因一（报价可信度），配套一套**不依赖上游**的兜底机制：

| 手段                        | 说明                                                                                       |
|-----------------------------|--------------------------------------------------------------------------------------------|
| **下单/询价前强制实时回查** | 成交以下单确认为准；回查失败明示"需确认"，不用隔夜旧数据冒充现货                             |
| **加购/下单触发爬虫回查**   | 对无实时接口的供应商，加购/下单时爬虫实时查一次（量极小，可承受），把"下单确认"扩展到所有供应商 |
| **自有数据快速生效**        | 实时刷新去夜间窗口、回查结果本次生效、队列换 MQ 不丢数据                                     |
| **新鲜度透明化**            | 标注"更新于 X 小时前"，超旧数据降权或转"询价下单"                                           |
| **多供应商 fallback**       | 同型号挂多家，旧/无货自动切另一家确认（依赖 A1 商品中心化）                                   |

#### A1+：撮合交易（聚合展示 + 拆单履约 + 分级确认）

典型场景：客户要 1 万件，A 渠道有 5k、B 渠道有 5k。商城该挂 5k（少卖）还是合并挂 1w（超卖跑单）？叠加"去供应商官网下单有人工参与、要时间"的现实，正解不是二选一，而是**分层库存 + 拆单履约 + 分级撮合**。核心原则:**展示真实可承诺的量、成交前确认、拆单全程透明**——不拿聚合量冒充现货,也不单渠道少卖。

**(1) 库存分层（决定商城挂什么）**——按置信度而非供应商切分展示：

| 层级              | 含义                    | 动作                            |
|-------------------|-------------------------|---------------------------------|
| 可承诺 Confirmed  | 实时接口或刚回查，高置信 | 直接进采购                      |
| 待确认 To-confirm | 近期数据、可能已变       | 加购/下单触发回查（量极小可承受） |
| 询价 RFQ          | 数据陈旧或无库存数据    | 转询价，不展示现货价             |

商城对 5k+5k 场景应展示聚合量并摊开构成，而非一个假总数或单渠道少卖量：

```
STM32F103C8T6   可订 10,000
  ├─ A（实时）  5,000  立即可订     确认时效：即时
  └─ B（近期）  5,000  待确认       确认时效：约 4 小时
```
 
**(2) 拆单履约**：客户下一个 1w 的单 → 内部拆成 5k@A（锁定采购）+ 5k@B（待确认）多张采购单；对客户始终是一个订单，订单页逐段展示状态（已采购 / 确认中 / 已确认 / 部分缺货）。

**(3) 三种撮合模式让客户选**（B 端真实存在的三种诉求，显式做出来强于一个自助流程硬扛）：

| 模式     | 适用                   | 行为                                           |
|----------|------------------------|------------------------------------------------|
| 整单等齐 | 产线不能少，1w 不到不要 | 全部确认齐才发货，凑不齐可整单取消              |
| 部分先发 | 急用一部分             | 先发能确认的 5k，剩余到货补发（二次运费需明示）   |
| 尽力拼凑 | 量可弹性               | 系统尽力凑齐，凑不到自动降级（如 8k）给客户点确认 |

**(4) 缺货自动 fallback**：B 的 5k 回查发现没了，系统**先查 C/D/E**（依赖 A1 跨供应商聚合）能补则无感补上；补不了再回来谈降级，而不是 B 一没就直接砍客户量。

**(5) 人工通道显式化**（把"去官网下单有人工、要时间"诚实落入体验）：小单/单渠道/高置信全自助；大单（超阈值）/拆单 ≥ N 家/含询价段自动转 RFQ 人工跟单，分配客户经理并给明确 SLA（"X 工作小时内回复"）；系统把各渠道库存/价格/交期/置信度备齐给人工，人工只拍板与执行。

> **依赖与边界**：依赖 A1 商品中心化（同型号聚合是前提）、根因一回查兜底（待确认层即加购回查）、D1 履约中台（拆单状态回传）。上游超卖（我们去下单那一刻货已被别人买光）是行业硬天花板、无法消除——所以才必须有"成交前确认 + 缺货 fallback + 降级协商"兜底，而非假装能消除。

#### A1++：数据时效改造（MQ 事件总线 + 增量更新 + 热门商品池）

当前数据时效是 T+1 全量重建、爬虫每天提供 1-2 次、实时刷新锁夜间窗口、Redis List 当队列还静默丢数据（见根因一与技术佐证）。改造不是单一招，是三块叠加，且必须先厘清一个前提。

**前提：两种时效要拆开，MQ 只解其中一个。**

| 时效类型 | 含义                         | 决定因素                             | MQ 能否解决 |
|----------|------------------------------|--------------------------------------|-------------|
| 传输时效 | 拿到数据后多久生效到客户可见 | 自身管道（队列/索引/生效逻辑）         | ✅ 能        |
| 采集时效 | 多久能从上游拿到一次新鲜数据 | 供应商接口能力 / 反爬限频 / 商务合作 | ❌ 不能      |

上游数据源不可控是行业硬天花板（技术佐证原话）。"接入 MQ、爬到就实时提供"对一半：它让**已拿到的数据**秒级生效，但若某供应商一天只能爬一次，MQ 也只是把这"日级一份数据"秒级送出，**数据本身鲜度仍是日的**。MQ 解传输、不解采集；采集要靠第三块热门池 + 分层提频。

**(1) MQ 事件总线 —— 解传输时效 + 不丢数据**

- 现状：Redis List 当队列（>3 万跳过、>10 万静默丢弃）、回查结果异步回写"下次才生效"、实时刷新锁夜间 18:00–08:00 窗口、消费者裸守护线程 `while(true)` 无优雅停机。
- 改：爬虫/实时接口拿到数据 → 发 MQ → 消费者增量写库 + 刷索引，**本次请求即生效**。
- 配套：幂等、重试 + 死信队列、背压（爬虫高峰不压垮索引侧）、优雅停机。

**(2) 增量更新替代全量蓝绿重建 —— MQ 真正有价值的前提**

- 现状：58 个定时任务，主力每日/定期全量重建（新建索引→蓝绿切换），两次全量间数据陈旧。
- 改：**事件驱动增量**，单条/批量变更即时生效；全量重建**降级为兜底校准**（周/月级对账，非主力）。
- 与 A1 强耦合：Offer 模型立起来后，一条 Offer 变更天然就是一个 MQ 事件。没有 A1 主数据，MQ 事件没有正确落点——故属技术佐证切片 B，排在切片 A 之后。

**(3) 热门商品池 + 采集频率分层 —— 解采集时效（投入产出最高）**

把有限的采集算力与接口配额精准投到最该新鲜的型号上，而非平均撒网爬全量 SKU。

- \**怎么定义"热门"**（自动打分、定期重算）：GMV 贡献（近 30 天）、搜索频次、加购/询价频次、价格/库存波动度（波动大也要勤采，否则报价失真）、大客户在采型号加权。
- **采集频率分层**（供应商维度 × 商品维度叠加）：

| 层级             | 采集策略                          | 目标新鲜度  |
|------------------|-----------------------------------|-------------|
| 热门池（头部型号） | 准实时接口全天轮询 / 高频爬       | 分钟~小时级 |
| 腰部             | 定时轮询（每日 N 次）               | 小时级      |
| 长尾             | 按需触发（加购/下单回查）+ 低频兜底 | 按需        |
| 冷门/停产        | 转询价，不主动采                   | —           |

- **反爬是硬约束**：Mouser/DigiKey 等限频，不能无限提频；把 4-5 家实时接口供应商的配额优先喂给热门型号。
- **运营闭环**：热门榜单定期重算（日/周）→ 采集计划动态调整 → 监控热门型号**新鲜度达标率**→ 不达标告警（撞反爬或接口瓶颈，须去解决而非假装在采）。

> **与撮合（A1+）闭环**：热门池型号 → 大概率落在撮合的"可承诺"层（刚采过、置信度高）；长尾 → 落在"待确认/询价"层。数据新鲜度分层是撮合分层库存的输入——这头勤采保证新鲜，那头才敢挂"可承诺"。

> **落地与边界**：热门池可独立先行（仅需商品热度打分 + 采集任务优先级调度，不依赖架构大改，见效最快）；MQ + 增量属切片 B，依赖切片 A 先立。上游天花板（反爬/限频/无商务合作）无法突破，云汉亦然；差异化在"传输时效 + 成交前确认兜底 + 热门池精准投频"，非死磕全网实时。本节充实了上方根因一兜底表中"自有数据快速生效"一行。

### B. 发现与转化引擎（决定流量与转化）

| 杠杆                | 现状                           | 改革方向                                                           |
|---------------------|--------------------------------|--------------------------------------------------------------------|
| **B1 搜索范式升级** | 关键字+通配符，只能按已知型号找 | 参数化选型 + 语义搜索 + BOM 智能配单 + 替代料推荐                  |
| **B2 AI 智能化**    | AI 接口刚起步                  | 选型助手 / BOM 解析纠错 / 智能替代料 / 报价机器人 / 需求与价格预测 |
| **B3 流量与 SEO**   | 代购专区触达有限               | 型号页 + datasheet/参数页内容 SEO + 工程师社区运营                 |

B1 分级能力：型号精确 → 关键词模糊（中文同义词）→ 参数搜索 → 跨供应商比价聚合 → 替代料推荐 → 国产化置顶 → BOM 配单。其中**参数搜索、替代料、BOM 配单**是拉开身位的能力，国产化替代是当前最大政策红利。替代料分三层：pin-to-pin 结构化匹配 → 功能替代（标注差异）→ 国产化专项映射。

### C. 客户与客单价值（决定乘数）

| 杠杆                    | 现状                     | 改革方向                                                                                       |
|-------------------------|--------------------------|------------------------------------------------------------------------------------------------|
| **C1 客户增长引擎**     | 无 CRM、无分层、无复购运营 | CDP + 客户分层（大客户/中小批量/工程师打样）+ 复购引擎（BOM 周期复购/降价/到货提醒）+ RFQ 智能跟进 |
| **C2 一站式 PCBA 闭环** | 已通嘉立创 SMT/BOM 接口  | BOM 配单一键转 SMT/PCBA，代购料与 PCBA 流程无缝衔接，入口互导                                    |
| **C3 智能定价引擎**     | 加价率手工黑箱           | 竞品比价 + 动态定价（供需/库存/交期/客户分层）+ 毛利优化 + RFQ 自动报价                          |

C1 不依赖 A1 架构大改，可独立先行；C2 依托嘉立创 PCB/SMT 生态，是现成的入口。

### D. 履约与开放生态（决定可规模性与新渠道）

| 杠杆                  | 现状              | 改革方向                                                                                      |
|-----------------------|-------------------|-----------------------------------------------------------------------------------------------|
| **D1 履约供应链中台** | 时效弱、链路不透明 | 询价→采购→物流→报关→入库→发货全链路中台；供应商评级 + 智能寻源（多供应商 fallback）；热门料保税仓 |
| **D2 开放 B 端平台**  | API 仅内网        | 开放 B 端 API（搜索/报价/下单/库存）+ ERP 对接 + 第三方分销 + 供应商入驻                        |
| **D3 行业数据资产**   | 数据仅自用        | 价格行情指数 / 交期预警 / 缺货榜单，对工程师免费或会员制提供                                   |

## 四、需要调研的内容与原因

技术侧的根因判断已清楚，但**"哪个杠杆最该先做、投入多大"必须用我方真实数据证明，不能靠主观排序**。以下数据取数性价比最高，能钉死主方向：

| 调研数据                                     | 钉死什么               | 为什么要调研                                                                                                                                   |
|----------------------------------------------|------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| **有效可售 SKU / 搜索零结果率**              | 数据广度是否为头号瓶颈 | 决定 A1/A2（商品中心化、供给平台化）是否最优先。名义上亿 SKU 但鲜活+可搜索的有效量未知，零结果率高说明客户"搜不到"，是供给问题还是搜索问题需数据区分 |
| **报价失真率 / 缺货改价取消率**              | 时效与履约的真实损失   | 决定 A1（下单回查兜底）/ D1（履约中台）的优先级与改造 ROI。当前"回查失败假装有货"造成的跑单/赔付规模未量化，不量化就无法证明这块改造的投入产出       |
| **复购率 / 老客收入占比**                    | 客户引擎是否最大杠杆   | 决定 C1 的优先级。复购深度直接决定 LTV，若我方复购率远低于行业，C1 是投入产出比最高、且不依赖架构大改的方向，应列为第一优先；反之则排后              |
| **各履约段的时效分布**（报关段/跨境段/国内段） | 履约瓶颈定位           | 决定 D1 改哪段。履约链路不透明，只有把时效拆到每一段，才能知道是供应商发货慢、报关卡住、还是入仓慢，避免改造打在错误的环节上                         |
| **资料完整度分布**（参数/图/规格书覆盖率）     | 商品资料短板程度       | 决定 A1 里"数据质量三评分"和资料增强的投入。资料不完整直接影响搜索命中率与转化，覆盖率分布能定位是普遍偏低还是个别供应商拖后腿                   |

### 调研方法与产出

- **先看真实分布**（均值/中位数/分位数），不预设阈值，避免先入为主。
- **归因树**：单一指标无法直接行动，必须拆到根因。例如履约失败 → 上游缺货（库存过期/上游超卖/型号映射错误）/ 报关延误 / 我方采购失败，每个叶子对应一个明确改进方向。
- **GMV 损失量化**：每个有问题的维度，估算"改进到合理水平能挽回的 GMV"。
- **产出决策矩阵**：所有改进项按「GMV 挽回 ÷ 改造成本」排序，即为优先级。高 ROI → 立即立项；低 ROI → 低成本方案或分期；分布正常 → 维持监控。

## 五、决策诉求

1. **业绩天花板由"原子单位"决定。** 在"供应商 SKU 中心"架构上继续打补丁，边际收益递减；必须向"商品中心"演进——把"型号"立为一等公民，供应商数据降级为挂在商品下的"报价"。可分切片独立交付（先建商品主数据 + 型号归一化，让搜索真正用上映射）。
2. **建议第一优先：C1 客户引擎 + A1 商品主数据切片①。** 客户引擎不依赖架构大改可先行，商品主数据是数据改革的基石；两者相互独立、可并行。（最终优先级以上一章调研数据为准。）
3. **定价是对外未开发的杠杆。** 加价率手工黑箱，优化 1-2 个百分点毛利或赢得更多询价都是纯利润。
4. **这是平台级工程，需单独立项，设产品+技术+采购共同 owner。** 型号归一化的准确率依赖采购/运营人工纠偏，开放 B 端 API 涉及定价策略，需业务侧共担，不能靠各团队兼职。
