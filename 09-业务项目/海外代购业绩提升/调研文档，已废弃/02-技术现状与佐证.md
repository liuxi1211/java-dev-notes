## 一、三个项目的真实职责（重要纠偏）

最初对三个项目的描述与代码实证有出入，后续任何改造的主战场定位依赖这个纠偏：

| 项目               | 最初描述     | 代码实证的真实职责                                                                                                                                                                              | 规模              |
|--------------------|--------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------|
| **lcsc-opd**       | 提供商品详情 | ❌ 不是详情服务。是从 zoverseas 拆出的**商品参数清洗 ETL 微服务 + 参数规则运营后台**，把爬虫数据清洗成结构化参数表                                                                                 | ~70 个 Java 文件  |
| **lcsc-zoverseas** | 数据更新维护 | ✅ 海外代购 + 立创订货的**数据中台 / 后台**。ETL、ES 索引构建（全量蓝绿重建）、实时 API 刷新、后置处理器链、运营配置（定价/下架/品牌映射）、对内 Feign/MQ。**真正的"详情查询、实时回查、加购下单"逻辑在这里** | 1191 个 Java 文件 |
| **lcsc-overseas**  | 提供搜索服务 | ✅ 在线**搜索 + 售价计算 + 超阈值实时回源**服务。本身不存商品数据，全部走 ES（数据由 zoverseas 同步）                                                                                                | ~250+ 个核心类    |

> **含义**：业务真正的"详情/报价/下单"中枢是 **zoverseas**，不是 opd。opd 只是一条参数清洗旁支。后续"详情体验"改造主战场在 zoverseas。

## 二、主报告根因的代码级佐证

### 佐证 1：数据广度虚假繁荣 + 时效落后（根因一）

| 现象                         | 代码证据                                                                                                                                                                            |
|------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 名义 26 家，鲜活仅 3-4 家     | 实时价格库存回源仅覆盖 Mouser/DigiKey/Arrow/Verical/Avnet 等 4-5 家；其余供应商两次全量间数据陈旧                                                                                    |
| 实时刷新只夜间跑             | 实时刷新**仅在夜间 18:00–08:00 窗口**执行；DigiKey batch=1 吞吐极低                                                                                                                  |
| 映射已全覆盖（早期误判已修正） | 常量 `OVERSEAS_PRODUCT_NO_MAPPING_PROVIDER` 曾列出 17 家"不做映射"，**该常量现已废弃不生效**——各供应商实际都已映射到自营商品体系。瓶颈不在映射覆盖，而在搜索侧未利用映射做跨供应商合并 |
| 队列丢数据                   | 实时回写用 Redis List 当队列（无 MQ），>3 万跳过、**>10 万静默丢弃*\*                                                                                                                   |
| 主力是 T+1 全量              | 58 个定时任务，主力是每日/定期全量重建（新建当日索引→别名蓝绿切换），两次全量间数据陈旧                                                                                                 |
| 数据质量靠下游拦             | 2026-07 才加"文件行数 vs 历史总量×阈值"前置拦截 + 新旧索引 count 对比告警，注释表明上游爬虫数据包曾大幅缩水/异常                                                                     |

### 佐证 2：供应商 SKU 中心而非商品中心（根因二）

- 每供应商一个独立索引 `product_overseas_{provider}`，26+ 个索引；同一型号散落多处，**不做跨供应商合并**。
- 各供应商商品虽已映射到自营商品体系，但搜索按供应商索引分散执行，**映射结果未被搜索利用**——这是"跨供应商能力做不出来"的直接原因。
- 加一家供应商要改 5+ 处（常量、parser、索引任务、API 适配、加购下单、采购回调），列表硬编码。
- 历史上 **ES 是唯一权威存储**，MySQL 三表同步是 2026-01 才后补的镜像（带调试痕迹），MongoDB 只覆盖 2 家。

### 佐证 3：客户经营完全空白（根因三）

- 代码中**无任何**客户分层、复购提醒、RFQ 跟进、报价历史、客户画像、CRM 痕迹。
- 代购客单价/复购/留存均无系统化度量能力。

### 佐证 4：报价可信度与履约（根因四）

- 实时回写结果走队列**异步回写，本次请求仍返回旧数据，下次才生效**。
- 下单链路实时库存/价格回查是同步取，失败回退 ES → 下单时数据可能仍不准。
- 售价公式多层嵌套：`售价 = 成本价 × (1+品牌加价率) × (1+目录加价率) × 汇率 × 税费系数 × 服务费系数 × 区间利润率`，加价率三层（供应商级/品牌级/目录级）纯手工配置。
- 关税计算用**反射**按配置字符串取税率字段（脆弱、性能差）；特例多（Element14/RS 人民币报价不乘汇率、Future 用平台定价防互压等）。

### 佐证 5：转化链路与渠道缺口

- 商品参数 `param_json` **硬截断到 2048 字符且最多 30 个参数**，长参数商品详情悄悄丢字段；审核标志恒为 1，审核流是摆设。
- 无替代料、无封装图（仅 DigiKey/Arrow 有图）；datasheet 仅存外链 URL，未转存。
- **所有 OpenAPI 都是内网微服务**，无面向外部 B 端的开放 API（整个 API 客户/第三方分销/ERP 对接渠道空白）。
- 已给嘉立创 SMT、BOM 提供专门接口（在 overseas），SMT 已是重要入口；闭环已通，但深度与转化待挖（非"没打通"）。

## 三、关键技术债清单（精简，按对业绩影响排序）

### 报价可信度/数据时效（直接影响转化，最高优先）

> 认知前提：上游数据源不可控是行业硬天花板（无商务合作只能爬虫；商务推送频率对方定），这部分无法突破、云汉也一样。**我们的问题全在"拿到数据后"**：没快速生效、没把"不准"兜住。下表按此定位。

| 问题                                                       | 影响                                                                          |
|------------------------------------------------------------|-------------------------------------------------------------------------------|
| **下单链路同步回查失败时回退 ES 旧数据**（假装有货）         | **最致命**：这是跑单/赔付的真正原因，不是"数据不实时"。改逻辑：失败应明示"需确认" |
| 回查结果走队列异步回写，**本次请求仍返回旧数据、下次才生效** | 客户此刻看到的仍是旧价旧库存                                                  |
| 无 MQ，Redis List 当队列，>10 万静默丢弃                     | 高峰期价格库存回写丢失                                                        |
| 实时刷新仅夜间窗口 + DigiKey batch=1 极慢                  | 白天数据陈旧                                                                  |
| 汇率/定价缓存击穿式反向依赖：C 端请求同步回源刷新           | 高峰期把写侧压力传导给读侧，放大延迟                                           |
| 实时消费者用裸守护线程 `while(true)`，无优雅停机            | 稳定性差                                                                      |
| **无新鲜度透明化 / 无超旧数据转询价模式**                  | 客户对"价格可能已变"无预期，体验上等同于"欺骗"                                 |

> 正解不是死磕上游新鲜度，而是「下单前确认兜底 + 数据快速生效 + 不准透明化」——均在我们可控范围、不依赖上游配合。

### 搜索质量（直接影响转化）

| 问题                                                                          | 影响                                                                                                                |
|-------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| 内存重打分分页：一次取 ~52 条在 JVM 内存按"型号字符包含占比"重算得分再截取分页 | 分页正确性错（深翻页错乱、总数不准）、性能差、排序黑箱无法 A/B（作者注释原话："反正这里很乱…这个供应商排序没有什么意义的"） |
| 三套关键字查询策略并存，靠运行时开关切换                                       | 召回行为不可预测，回归风险高                                                                                         |
| 26 索引扇出，同型号不合并                                                      | 无"最优渠���推荐"，结果重复/分散                                                                                     |

### 可维护性/扩展性（影响改造成本与扩供应商）

| 问题                                                          | 影响                                   |
|---------------------------------------------------------------|----------------------------------------|
| 上帝类：核心搜索服务 3198 行、公共搜索 1613 行、BOM 服务 1031 行 | 改动回归风险极高，新人无法接手          |

## 四、商品中心化的落地路径（分切片，独立交付）

主报告明确了"向商品中心演进"的方向；落地不必一刀切，按价值/风险切片，每片独立上线、独立见效、独立回滚：

1. **切片 A：建商品主数据 + 型号归一化/身份解析** —— 先不动现有 ES/搜索。新建商品主表 + 身份解析服务，让搜索真正基于"商品"而非"供应商索引"工作，**把跨供应商比价/聚合能力做出来**。这是整个改革的基石，也是最快看到业务收益的一步。
2. **切片 B：报价模型 + 事件总线（MQ）** —— 供应商数据落报价表，接 MQ；搜索投影先双写（旧索引 + 新商品索引并行）。消灭 Redis 当队列、消灭静默丢弃。
3. **切片 C：搜索切到商品中心索引** —— 新搜索服务灰度切流，旧服务兜底；切稳后下线内存重打分与 26 索引扇出。
4. **切片 D：新鲜度分层** —— 头部供应商准实时接口全天化，腰部定时轮询，尾部下单回查。对标云汉"数据供应商 + 询价供应商"的分层模式。
5. **切片 E：供应商插件化 + 开放 B 端 API + 分析层**。

> 切片 A 是最高优先级——它解的是"原子单位选错"这个根，且风险最低、业务收益最直接。

## 五、改革的风险与诚实声明

- 这是 **1-2 年级的平台级工程**，不是几个迭代能完成。但每一步都有独立 ROI，不是"全部做完才有用"。
- 最大的风险不在技术，在**组织**：跨多个系统 + 大数据爬虫团队 + 采购/电商系统的协同。需单独立项、产品+技术+采购共同 owner。
- 需业务侧共担的两件事：**型号归一化的人工纠偏**（映射准确率决定一切上层能力是否敢放开）、**开放 B 端 API 的定价策略**（涉及对外报价规则）。
- 代码无法确认、需业务取数的：有效可售 SKU 实际值、复购率/老客占比、报价失真率、各供应商 GMV 贡献集中度（详见主报告第五章诊断项）。
