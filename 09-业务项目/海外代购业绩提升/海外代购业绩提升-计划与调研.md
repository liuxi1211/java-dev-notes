## 二、具体改造项（共 11 项，按 3 大主题分组）

### 🅰 数据与供给底座（决定天花板）

#### 🔹 A1 商品中心化（地基，最高优先）

- **做什么**：把"型号"立为一等公民，供应商报价降为挂在型号下的 Offer。
- **解决什么**：当前 26 个供应商索引各搜各的、映射做了搜索没用上 → 跨供应商比价/聚合库存/最优渠道/替代料/参数搜索全做不出来。
- **业务收益**：⭐⭐⭐⭐⭐ 业绩天花板的结构性根因——必须从"供应商 SKU 中心"升级为"型号中心"。
- **优先级**：**P0**。

**核心模型**：

```
SPU（型号维度，一等公民）
  ├─ 型号归一化身份（MPN、品牌别名、后缀归一、料号交叉引用）
  ├─ 主数据：参数、规格书、图片、分类属性
  └─ Offers（报价维度，N 条）
       ├─ Offer = 1 SPU × 1 供应商 × 1 报价（库存/价格/交期/数据新鲜度）
```


**存储与搜索定位**：
- 系统记录用关系库（MySQL），ES 降级为检索投影，不做事务主库。
- 搜索从"N 个索引分别查再合并"升级为"SPU + Offer 双索引统一搜索"。

**治理定位（重要原则）**：全量聚合 + 透明标注 + 用户自筛

全部供应商数据接入、不删；供应商始终作为一等属性保留并支持筛选——用户认准某家，即使其数据陈旧，也能按供应商筛出来、展开下单/询价。清洗只针对脏记录（爬虫错误包、参数乱码）与全供应商均无活跃报价的幽灵型号（转询价/沉冷池，不物理删），**绝不因"数据更新不及时"而清除某个真实存在的供应商**。

> 📎 **客户决策标签、温和提示标签已移出本项**：A1 只负责商品中心化（型号归一化 + 主数据 + Offer 聚合），标签体系的定义与展示统一归 **A3 履约承诺可信化**。A1 是"数据底座"，A3 是"数据可靠性的证明层"，两者职责分离。

**需业务侧共担**：型号归一化的**人工纠偏**，当前海外代购已经可以映射到自营商品，所以归一化的前提已经铺垫好了

**风险**：这是平台级工程，不是几个迭代能完成

> 🔍 **与现有 MDM 项目的关系（需调研确认）**：公司已有 MDM（主数据管理）项目，本项（A1 商品中心化）描述的能力——型号归一化、统一 SPU 主数据、多供应商 Offer 聚合、数据质量治理——**理应是 MDM 的核心职责**。当前 MDM 项目是否已具备这些能力、做到什么程度、与本项是复用还是新建，**需要调研确认**。若 MDM 已部分建成，本项应优先复用而非重复建设；若 MDM 尚未覆盖，则本项即是 MDM 应补齐的能力。

#### 🔹 A2 数据时效改造（MQ 事件总线 + 增量更新 + 热门商品池）

- **做什么**：消灭 T+1 全量重建、夜间窗口、队列丢数据，让数据快速生效并精准投频采集。
- **解决什么**：白天看隔夜数据、回查下次才生效、高峰静默丢数据；把有限采集算力投到最该新鲜的型号上。
- **业务收益**：⭐⭐⭐⭐ 报价可信度直接拉升。
- **优先级**：**P0**（热门池可独立先行；MQ+增量依赖 A1 切片 B）。

**前提澄清（关键认知）**：两种时效要拆开，MQ 只解其中一个。

| 时效类型 | 含义 | 决定因素 | MQ 能否解决 |
|---|---|---|---|
| 传输时效 | 拿到数据后多久生效到客户可见 | 自身管道（队列/索引/生效逻辑） | ✅ 能 |
| 采集时效 | 多久能从上游拿到一次新鲜数据 | 供应商接口能力/反爬限频/商务合作 | ❌ 不能 |

> 上游数据源不可控是行业硬天花板。"接入 MQ、爬到就实时提供"对一半：它让**已拿到的数据**秒级生效，但若某供应商一天只能爬一次，MQ 也只是把这"日级一份数据"秒级送出，**数据本身鲜度仍是日的**。MQ 解传输、不解采集；采集要靠热门池 + 分层提频。

**(1) MQ 事件总线 —— 解传输时效 + 不丢数据**
- 现状：Redis List 当队列（>3 万跳过、>10 万静默丢弃）、回查结果异步回写"下次才生效"、实时刷新锁夜间 18:00–08:00 窗口、消费者裸守护线程 `while(true)` 无优雅停机。
- 改：爬虫/实时接口拿到数据 → 发 MQ → 消费者增量写库 + 刷索引，**本次请求即生效**。
- 配套：幂等、重试 + 死信队列、背压（爬虫高峰不压垮索引侧）、优雅停机。

**(2) 增量更新替代全量蓝绿重建 —— MQ 真正有价值的前提**
- 现状：58 个定时任务，主力每日/定期全量重建（新建索引→蓝绿切换），两次全量间数据陈旧。
- 改：**事件驱动增量**，单条/批量变更即时生效；全量重建**降级为兜底校准**（周/月级对账，非主力）。
- 与 A1 强耦合：Offer 模型立起来后，一条 Offer 变更天然就是一个 MQ 事件。没有 A1 主数据，MQ 事件没有正确落点——故排在切片 A 之后。

**(3) 热门商品池 + 采集频率分层 —— 解采集时效（投入产出最高）**
- 把有限采集算力与接口配额精准投到最该新鲜的型号上，而非平均撒网爬全量 SKU。
- **怎么定义"热门"**（自动打分、定期重算）：GMV 贡献（近 30 天）、搜索频次、加购/询价频次、价格/库存波动度（波动大也要勤采，否则报价失真）、大客户在采型号加权。
- **热度打分是全站唯一来源**：本项产出的热度分，被 B1（搜索排序）、C1（热门料保税仓前置）及商城侧的复购提醒、动态定价等共同引用，避免各建一套热度指标导致口径不一致。

| 层级 | 采集策略 | 目标新鲜度 |
|---|---|---|
| 热门池（头部型号） | 准实时接口全天轮询 / 高频爬 | 分钟~小时级 |
| 腰部 | 定时轮询（每日 N 次） | 小时级 |
| 长尾 | 按需触发（加购/下单回查）+ 低频兜底 | 按需 |
| 冷门/停产 | 转询价，不主动采 | — |

- **反爬是硬约束**：Mouser/DigiKey 等限频，不能无限提频；把 4-5 家实时接口供应商的配额优先喂给热门型号。
- **运营闭环**：热门榜单定期重算（日/周）→ 采集计划动态调整 → 监控热门型号**新鲜度达标率** → 不达标告警（撞反爬或接口瓶颈，须去解决而非假装在采）。

**与可信化（A3）闭环**：热门池型号 → 大概率落在撮合的"可承诺"层（刚采过、置信度高）；长尾 → 落在"待确认/询价"层。

#### 🔹 A3 履约承诺可信化（数据可靠性的统一证明层）

- **做什么**：通过一套**统一的标签体系 + 承诺体系**，向客户证明"我们的数据可靠、承诺可兑现"——把"我们承诺什么、承诺不了什么、风险在哪"对客户**全程透明**，让客户基于准确信息决策，**而非"先支付后退款"**。本项是 A 节所有数据的**对外可信化出口**：A1 的商品聚合、A2 的数据时效，最终都要通过本项翻译成客户能看懂、敢相信的标签和承诺。
- **解决什么**：当前友商也是先支付后退款、数据不准、出了问题客户主动来问才知道——**全行业都这么做，这就是机会**。我们只要做到"说的就做到、做不到的提前说、风险写明白"，就是差异化。
- **业务收益**：⭐⭐⭐⭐⭐ **差异化护城河**——比功能多更重要，是用户选我们的核心理由：保交货交不了就退款、说多久交货就多久交、数据准确、有风险明说。
- **优先级**：**P0**。

**核心原则**：信任 > 功能。承诺必须可兑现，兑现不了必须提前说，风险必须前置明示。

> ⚠️ **重要澄清：A3 不是要求数据全部实时**。上游接口限制是行业硬天花板，我们做不到、友商也做不到。A3 的核心不是"让数据变准"，而是**"数据有多准就承诺多少、不准就老实说"**——数据新就给 ✅ 现货承诺（竞争力），数据旧就标 ⚠️ 价格可能已变动（诚实，比友商骗人好）。**即使我们的数据更新速度和友商一样慢，A3 也能变成差异化优势——因为我们诚实，友商不诚实。** 这不是高要求，反而是"把做不到的事变成卖点"——友商用旧价骗客户下单，我们用旧价但标注风险让客户知情决策。

**(1) 客户决策标签**（聚合后系统自动算，给客户一眼决策的依据。原属 A1，现统一归本项）：

| 标签 | 含义 |
|---|---|
| **最优价** | 同型号所有渠道里价格最低 |
| **最快交货** | 交期最短的渠道 |
| **最推荐**（综合最优）| 综合价格、交期、库存健康度、渠道可靠度的最优解（权重可 A/B 调）|
| **库存充足 / 现货** | 库存量充足或现货可发 |
| **官方授权** | 该渠道为原厂/官方授权（如实际可区分）|
| **品牌直采** | 直接从品牌方或一级代理采购的渠道 |

**(2) 温和提示标签**（诚实但不惊吓，避免客户基于过期数据下单被误导——不骗客户。原属 A1，现统一归本项）：

| 提示标签 | 触发条件 | 用意 |
|---|---|---|
| **价格可能已变动，下单前请确认** | 报价数据超过一定时长未更新 | 让客户对"价格可能变了"有预期，不把过期价格当准价 |
| **库存需确认** | 库存数据较旧或来源置信度低 | 让客户知道这单可能要人工确认，减少被动等待的投诉 |
| **热门料，建议尽快下单** | 高热度型号 + 库存紧张 | 提示客户抢手，避免错过 |

> 标签的**判定数据**来自 A1（同型号聚合）、A2（数据新鲜度）、C1（支付后回查发现的缺货状态）；本项负责**定义标签规则 + 展示**。C1 的回查发现缺货会驱动"库存需确认"标签更新。

**(3) 三档承诺体系**（给客户一眼决策的依据，每档都明确"承诺什么 / 做不到怎么办 / 给客户看什么"）：

| 承诺档位 | 我们承诺什么 | 做不到怎么办 | 给客户看什么（下单前） |
|---|---|---|---|
| **✅ 现货承诺** | 实时接口确认有货，承诺可发 | 缺货全额退款 + 补偿 | "✅ 实时确认，X 日内发货" |
| **⏳ 时效承诺** | 标注预计交货时间（**含人工采购耗时，不冒充现货**） | 超时可选取消退款 / 提供降级方案 | "⏳ 预计 X 工作日交货（含采购 Y 天）" |
| **⚠️ 风险明示** | 数据置信度低 / 库存待确认 / 价格可能变动 | 客户下单前就知道风险，不被动等待 | "⚠️ 价格待确认 / 库存需核实，下单后 X 小时内反馈" |

**(4) 配套机制**：

- **采购耗时诚实落入时效**：21 家无实时接口的供应商需人工去对方官网下单，有耗时。把这段耗时（如"约 4 工作小时核实 + 1 工作日下单"）**明明白白写进预计交货时间**，不藏，不冒充现货。
- **超时自动退款承诺**：承诺时效内没确认成功的（如"4 小时内反馈"未兑现）→ 系统自动触发退款，**不等客户催**。这是对"承诺可信"的硬兑现。
- **承诺达成率公示**：把"我们承诺的时效达成率"做成**可对客展示的指标**（如"近 30 天现货承诺兑现率 98.2%"）。友商基本不敢亮这个数，这就是差异化。需先内部跑数据，达标后再对外公示。

**依赖与边界**：
- 依赖 A1（同型号聚合，是标签判定的数据基础）
- 依赖 A2（数据越新鲜，承诺越敢给、兑现率越高）
- 依赖 C1（支付后回查产出的"置信度分层"与缺货状态，驱动标签更新）
- **承诺兑现率有硬天花板**：上游数据不可控、上游超卖不可消除——所以承诺体系必须配套 C1 的回查兜底，不能脱离兜底空承诺。
- **需业务侧共担**：超时退款政策、补偿标准、承诺达成率是否对外公示——涉及客服与财务规则，不能靠技术单独决定。

### 🅱 发现与转化引擎（决定流量与转化）

#### 🔹 B1 搜索能力升级

- **做什么**：从关键字 + 通配符升级到选型式搜索。
- **解决什么**：只能按已知型号找、搜不到就流失；参数被截断、无替代料导致搜索命中率与转化低。
- **业务收益**：⭐⭐⭐⭐⭐ 流量转化的核心入口。
- **优先级**：**P0**（依赖 A1）。

> 💡 **参考当前自营搜索能力**：商城自营商品的搜索（型号精确、关键词模糊、参数筛选、分类导航等）已经跑通且稳定，代购搜索升级应**优先复用自营搜索的成熟能力与基础设施**（ES 配置、分词、排序策略、前端筛选组件），而非从零重建。代购侧的重点是接入 A1 的 SPU+Offer 模型，让自营搜索能力直接服务于代购数据。

**分级能力（L1 是及格线，L3/L5/L6/L7 是拉开身位的能力）**：

| 能力 | 描述 | 价值 |
|---|---|---|
| L1 型号精确搜索 | 输入 MPN 直接命中，支持后缀容错 | 及格线 |
| L2 关键词/模糊搜索 | 支持中文同义词（如"单片机"="MCU"） | 及格线 |
| L3 参数搜索 | 选品类 → 按参数模板筛选 | 差异化 |
| L4 跨供应商比价 | 同一 SPU 下聚合所有供应商库存/价格/交期 | 差异化 |
| L5 替代料推荐 | 缺货/搜索结果页推 pin-to-pin & 功能替代 | 差异化 |
| L6 国产化置顶 | 进口料搜索结果自动置顶国产方案 | **政策红利** |
| L7 BOM 配单 | 上传 BOM，批量匹配、报价、缺料找替代 | 拿大客户 |

**替代料三层**：
1. **结构化参数匹配**（pin-to-pin）：封装、引脚、关键电气参数完全一致 → 自动判定兼容
2. **功能替代**：核心功能一致、参数有差异 → 标注差异项，人工 review
3. **国产化替代**：维护"进口料 → 国产料"专项映射，搜索进口料时自动置顶国产方案

**前置依赖**：A1 商品中心化（同型号聚合是比价/聚合的前提）；分类属性模板（电阻的阻值/精度/封装；MCU 的核/主频/Flash/RAM/IO 数）——属性模板是参数搜索的 schema，没有它参数筛选做不起来。

**排序策略**：综合文本相关性、库存健康度、资料完整度、货源数量、交期、热度，并对过期数据做惩罚

#### 🔹 B2 流量与 SEO

- **做什么**：把代购专区的有限触达做大。
- **解决什么**：流量这一乘数当前太弱，有供给也触达不到客户。
- **业务收益**：⭐⭐⭐⭐ 流量杠杆。
- **优先级**：**P1**（与 A1/B1 独立，可并行）。

- **型号页 SEO**：每个 SPU 独立详情页，结构化数据（schema.org Product/Offer）

**与 A1 的关系**：商品中心化后，每个 SPU 一个稳定 URL，是 SEO 的前提。

### 🅲 履约与开放生态（决定可规模性与新渠道）

#### 🔹 C1 履约供应链中台

- **做什么**：在全链路状态已可追溯的基础上，补上**缺货发现、供应商管理、缺货处置、跨境提速**四块尚未建设的能力，让履约从"能看到"升级为"能主动处置、能优化"。
- **解决什么**：链路透明已有，但缺货发现严重滞后（依赖人工事后核实）、供应商无评级（好坏不分）、缺货后无系统化处置（改价/取消/fallback 全靠人工）、跨境段时效无优化手段。
- **业务收益**：⭐⭐⭐⭐ 止损 + 信任地基 + 复购保障。
- **优先级**：**P1**（支付后回查可先做，其余依赖调研定位瓶颈）。

**已有基础（不在本次改造范围）**：
- ✅ 全链路中台：询价→采购→物流→报关→入库→发货，每段状态可追溯、可分段统计时效——**已建成**。

**本次要建设的内容（以上四块均尚未实现）**：

**(1) 支付后异步回查**
- 支付成功的瞬间异步触发爬虫回查，填入"支付→采购撮合（10 分钟定时器）"的时间窗口，把"缺货发现"从人工事后核实提前到下单瞬间自动核实。
- 回查发现一致 → 正常撮合；发现缺货/价变 → 驱动改价协商工单、主动告知客户、A3 超时退款；回查失败 → 进人工核实队列。
- **这是履约段提速的核心——早发现才能早处置**。

**(2) 供应商评级**
- 按履约率、交期、缺货率、响应速度给供应商打分，影响搜索排序（依赖 A1）和采购决策。
- 当前供应商好坏不分，评级数据可为采购选渠道提供依据。

**(3) 缺货处置闭环**
- 改价协商工单、取消退款流程、多渠道 fallback 补救（同 SPU 其他渠道补货，依赖 A1 聚合 + A5 撮合）。
- fallback 结果作为履约状态回传并在订单页分段展示。

**(4) 热门料保税仓**
- 高频热门料前置到保税仓，缩短跨境段时效（依赖 A2 热门商品池产出热度分）。

**调研依赖**：需先调研"各履约段时效分布"（见调研项 4），拆到报关段/跨境段/国内段，才知道保税仓该前置哪些料、改哪段——避免改造打在错误的环节上。

#### 🔹 C2 开放 B 端平台

- **做什么**：把仅内网的 API 开放给外部，提供 B 端集成能力——对标 Digi-Key、Mouser 等大平台均已开放的 API 生态，这是行业标配，我们在补课。
- **解决什么**：当前所有 OpenAPI 都是内网微服务，无面向外部 B 端的开放 API。客户只能通过商城网站手动操作，无法接入自家系统自动化采购。
- **业务收益**：⭐⭐⭐⭐ B 端客户粘性 + 新渠道。
- **优先级**：**P2**（依赖 A1/B1 稳定）。

**代码实证**：所有 OpenAPI 都是内网微服务，无面向外部 B 端的开放 API。

**开放内容（核心是查询 + 下单）**：
- **库存/价格查询 API**：B 端客户在自家 ERP 系统里直接查询我们的实时库存和价格——省去切换到商城网站的操作，提升采购效率（Digi-Key 的 Search API、Mouser 的 Search API 就是被大量客户嵌入 ERP/SaaS 系统的标杆案例）
- **下单 API**：客户在 ERP 里直接下单、查询订单状态——让我们的货进入客户的自动化采购流程，增强粘性
- **第三方分销**：让别人系统帮我们卖货，拓宽分销渠道
- **供应商入驻**：让更多供应商自助接入（依赖 A4 平台化）


**风险**：对外开放后，报价准确性要求更高（见 A3 承诺可信化），否则影响口碑。**需业务侧共担**

#### 🔹 C3 行业数据资产（远期探索）

> ⚠️ **一个探索方向**。依赖 A1+A2+A3 全部达标（至少 1-2 年后），且存在与主营卖货业务的潜在冲突，需单独验证后再决定是否推进。

- **做什么**：把 A1+A2+A3 沉淀的准确数据（26 家供应商聚合、分钟级时效）做成行业级数据产品（价格行情、交期预警、缺货榜单）元器件数据平台, 当前已经有了 MDM 系统，但现在应该只是内部使用
- **业务收益**：⭐⭐ 引流 + 变现 + 行业话语权。
- **优先级**：**P3（远期探索）**。

## 三、不确定的调研项（5 项，调研先行）

> **核心原则**：技术侧的根因判断已清楚，但"哪个杠杆最该先做、投入多大"必须用**我方真实数据**证明，不能靠主观排序。**调研先行，别在数据出来前就把顺序定死**。

### 🟡 调研项 1：有效可售 SKU / 搜索零结果率

**大白话：我们的"1 亿条数据"到底有多少是真能买的？用户搜不到东西，是我们真没货，还是有货没搜出来？**

|            |                                                                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **调研什么**   | **① 有多少数据是"活的"**：名义上亿 SKU，但其中多少是数据新鲜（没过期）、库存有量（不是 0）、能真下单的？去掉僵尸数据后，**有效可售量**到底是多少？<br>**② 搜不到是什么原因**：用户搜索时"零结果"（没搜到任何东西）的频率有多高？每次搜不到，到底是因为**我们真没这个货**（供给问题），还是**其实有货但搜索没匹配上**（搜索问题）？ |
| **钉死什么决策** | **数据广度是不是头号瓶颈** → 如果有效可售量很低，说明得优先补数据（A1/A4）；如果零结果率高且主要是搜索问题，说明得优先改搜索（B1）                                                                                                             |
| **为什么调研**  | 我们一直说"1 亿条数据"，但这个数字可能是虚的——里面可能混着大量过期数据、零库存数据、重复数据。不搞清楚真实有效量，就无法判断"数据够不够"到底是不是当前最大问题。同样，搜索零结果率如果不区分原因，就无法决定该补货还是该改搜索                                                                  |
| **数据来源**   | 商品主数据（看数据新旧、库存量）、搜索日志（看零结果查询）、ES 索引时间戳                                                                                                                                               |
| **方法**     | ① 按型号热度分层抽样（热门 Top 1k / 中部 1w-10w / 长尾 10w-100w / 冷门 100w+），逐层统计有效可售占比；② 把搜索零结果的关键词拿去对照 Digi-Key/Mouser，看同行有没有——同行有我们也有，就是搜索问题；同行有我们没有，就是供给缺口                                        |

### 🟡 调研项 2：报价失真率 / 缺货改价取消率

| | |
|---|---|
| **调研什么** | 报价失真率（售价与上游官网价偏差）；缺货改价/取消率（下单后因缺货改价或取消） |
| **钉死什么决策** | **时效与履约的真实损失** → 决定 A3 承诺 / C1 履约的优先级与改造 ROI |
| **为什么调研** | 当前"降级之后缺货"造成的跑单/赔付规模**未量化**（降级先下单是合理的业绩保护，但缺货发现/告知/赔付的损失规模未量化），不量化就无法证明这块改造的投入产出 |
| **数据来源** | 订单系统（改价/取消记录）、比价脚本（对照上游官网价）、库存对账数据 |
| **方法** | 跑批统计 + GMV 损失量化（失单量 × 客单价 × 复购系数） |

### 🟡 调研项 3：复购率 / 老客收入占比

| | |
|---|---|
| **调研什么** | 90 天复购率、老客收入占比、客户分层分布（大客户/中小/工程师） |
| **钉死什么决策** | **客户经营是否最大杠杆** → 为商城侧客户经营立项（原 C1，已移交商城）提供依据 |
| **为什么调研** | 复购深度直接决定 LTV。**若我方复购率远低于行业，客户经营是投入产出比最高的方向**——但这是商城级能力（含自营），应由商城侧统一立项，代购仅提供数据佐证与消费 |
| **数据来源** | 订单系统（按客户去重、按时间窗口算复购） |
| **方法** | 真实分布（均值/中位数/分位数）+ 用户分层交叉统计 |

### 🟡 调研项 4：各履约段时效分布

| | |
|---|---|
| **调研什么** | 履约链路分段时效：供应商发货段、报关段、跨境运输段、国内段 |
| **钉死什么决策** | **履约瓶颈定位** → 决定 C1 改哪段 |
| **为什么调研** | 履约链路不透明，只有把时效拆到每一段，才能知道是供应商发货慢、报关卡住、还是入仓慢，**避免改造打在错误的环节上** |
| **数据来源** | 物流/清关系统（需拆出报关段、跨境段、国内段时间戳） |
| **方法** | 按供应商分组、按物流模式（空运/海运/快递）分组，P50/P90/P99 分位数 + 箱线图 |

### 🟡 调研项 5：资料完整度分布

| | |
|---|---|
| **调研什么** | 参数/图片/规格书/ECAD 模型覆盖率分布；资料完整度按供应商分布 |
| **钉死什么决策** | **商品资料短板程度** → 决定 A1"数据质量三评分"和资料增强的投入 |
| **为什么调研** | 资料不完整直接影响搜索命中率与转化（代码实证：参数硬截断 2048 字符/30 个、datasheet 仅外链 URL 未转存、封装图仅 2 家有）。覆盖率分布能定位是普遍偏低还是个别供应商拖后腿 |
| **数据来源** | 商品主数据字段（param_json、图片字段、datasheet URL） |
| **方法** | 按 SPU 统计资料完整度评分，按供应商分组 |

## 四、风险与诚实声明

- 这是 **1-2 年级的平台级工程**，不是几个迭代能完成。但**每一步都有独立 ROI**，不是"全部做完才有用"。
- 最大的风险不在技术，在**组织**：跨多个系统 + 大数据爬虫团队 + 采购/电商系统的协同。需单独立项、产品+技术+采购共同 owner。
- **上游数据源不可控是行业硬天花板**（无商务合作只能爬虫；商务推送频率对方定），这部分无法突破。**我们的问题全在"拿到数据后"**：没快速生效、没把"不准"兜住。所有改造都基于这个诚实定位。
- 需业务侧共担的两件事：**型号归一化的人工纠偏**（映射准确率决定一切上层能力是否敢放开）、**开放 B 端 API 的定价策略**（涉及对外报价规则）。
