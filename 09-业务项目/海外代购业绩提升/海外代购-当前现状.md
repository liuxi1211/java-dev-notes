# 海外代购 —— 当前现状与实际运行机制

> 本文档是 [海外代购业绩提升-计划与调研](海外代购业绩提升-计划与调研.md) 的**配套说明**。
>
> 改造清单里给出的每一个方案，都是立在本文档描述的现状之上推导出来的。当读者理解不了"为什么要这样改"时，回到本文档看一眼当前的实际做法，就能找到答案。
>
> 因此本文档的每一节都对应改造清单里的某个/某些改造项，与业绩提升无关的现状（如关税系统、固定定价）不纳入。

## 一、数据对接现状

> 对应改造项：A1 商品中心化、A2 数据时效、A4 供应商平台化、C1 履约中台（含支付后回查）

### 1.1 数据来源（三种渠道）

| 来源方式 | 说明 | 新鲜度 |
|---|---|---|
| 供应商主动提供商品数据文件 | 供应商定期推送全量数据文件给我们 | 一般每天 1 次 |
| 供应商 HTTP 接口下载全量 | 供应商开放接口供我们下载其全量数据 | 取决于我们拉取频率 |
| 我们爬虫爬取 | 我们主动爬对方官网/平台 | 一轮约 1 周 |

### 1.2 实时接口与下单接口覆盖

- **实时查询接口**：约 **5–6 家**供应商提供，可查询准确的实时库存/价格。
- **线上下单接口**：约 **4 家**供应商提供，可自动下单（采购环节的自动化基础）。
- 其余供应商仅有文件/爬虫数据，无实时能力。

### 1.3 数据规模与更新节奏

- 当前对接 **26 家**供应商，商品数据**总量约 1 亿条**。
- 爬虫平均**一周爬完一整轮**；爬虫侧每天爬，但**一天只产出 2 个文件**（两个窗口期），所以爬到的数据**不是实时入库**，要等窗口期。
- 文件对接的供应商一般**每天更新一次**。

### 1.4 数据完整度与落地

- 各家数据**完整度不一致**：价格、库存等基础字段都有；其他字段（参数、图片、规格书等）不一定齐全；总体上**爬虫数据完整度略高**。
- 数据清洗后**直接放入 ES**，**没有 MySQL 主库**（即 ES 既是检索库也是事实数据源）。

## 二、搜索流程现状

> 对应改造项：A1 商品中心化（跨供应商聚合）、B1 搜索范式升级（参数搜索/替代料）

### 2.1 索引结构与搜索维度

- **26 家供应商各自独立索引**，互不合并。
- 当前搜索维度：**型号关键字、品牌、目录、描述**。
- **不支持参数搜索**（按电气参数、封装等筛选）——是后续改造的重点缺口。

### 2.2 自营 × 代购的搜索关系

- 搜关键字时，**自营商品和海外代购会同步搜索、并列展示**（同一搜索结果页）。
- 但搜**参数**时，因为海外代购不支持参数，**代购料搜不到**。
- 自营商品卡片上有一个**"查看更多"按钮**，通过自营商品内部编号（如 C1106）跳转搜索海外代购——这是代购的一个**补充入口**。
- 所有海外代购数据都会**映射到商城自营商品体系**，自营商品有一套内部商品编号（如 C1106）。

### 2.3 商品归一化（型号 + 品牌 → 唯一商品）

> 对应改造项：A1 商品中心化

海外代购映射到自营商品的模块，本质上就是一套**商品归一化能力**，已经用了很久、效果稳定。当前方案：

| 能力 | 说明 |
|---|---|
| **归一化主键** | **元器件型号 + 品牌** → 确定唯一一个商品 |
| **前提假设** | 元器件型号是业界统一的，加上品牌即可唯一定位一个商品 |
| **型号归一化** | 有专门的型号归一化功能，**去除型号里乱七八糟的字符**后再匹配 |
| **品牌映射** | 有专门的品牌映射功能，处理品牌别名（如 TI = 德州仪器 = Texas Instruments）等差异 |
| **切片/包装差异** | 同一商品的不同切片方式、包装后缀、供应商内部编号差异——**都算同一个商品**，因为元器件型号本身是一样的 |

### 2.4 数据消费方（对外接口）

当前商品数据/搜索能力提供给以下消费方使用：

| 消费方 | 用途 |
|---|---|
| 商城主站搜索 | 主搜索入口 |
| BOM 工具 | BOM 配单时查询商品数据 |
| 嘉立创总部 | 提供内部接口，对方可对接下单 |
| 自家外贸商城 | 提供接口，外贸商城消费商品数据下单 |

> 这 4 个是当前**已对接的数据消费方**，是后续 C2 开放 B 端平台的现实起点。

## 三、加购与下单现状

> 对应改造项：C1 履约中台（支付后回查，先成单保业绩，后回查早发现缺货）、调研项 2（丢单率量化）

### 3.1 加购下单的数据来源

| 情况 | 数据来源 |
|---|---|
| 供应商有实时接口 | 调用实时接口取库存/价格 |
| 供应商无实时接口 | 直接用 ES 数据 |
| 实时接口调用失败（降级） | 回退用 ES 数据 |

### 3.2 支付与履约确认

- 当前**直接让用户支付**，不做"先确认有货再支付"的拦截。
- 如果后续交货不了，**给用户退款**。
- **丢单率暂时未统计**（建议纳入调研项 2「报价失真率/缺货改价取消率」一起量化，以证明 C1 改造的投入产出）。

### 3.3 加购与爬虫的关系

- 加购下单**目前没有和爬虫联动**。
- 原因：加购对响应速度有要求，不确定把爬虫实时回查融入进来是否够快——这个判断需要后续验证。

## 四、履约（采购）现状

> 对应改造项：C1 履约供应链中台（含支付后回查、缺货处置闭环）

下单成功后订单流转到采购系统，按供应商能力分两档执行：

### 4.1 有实时接口的供应商（自动化）

- 采购系统有**定时器，每 10 分钟一次**自动撮合订单。
- 主动调用供应商接口完成采购。

### 4.2 无实时接口的供应商（人工）

- 由**业务人工专门去对方官网下单**。
- 如果人工下单失败（无货/价格变了等），**报无货 → 给用户推消息 → 退款**。

> 这一段对应改造清单里 C1 强调的"降级之后的缺货发现"——当前缺货发现完全依赖人工下单成败，反馈链路长，是 C1 改造的核心切入点。

---

## 五、送货（物流）现状

> 对应改造项：C1 履约供应链中台（前半段是代购独有瓶颈）

完整链路：

```
国外供应商发货
   ↓
送到我们香港仓库
   ↓
签约供应链上门提货 → 报关 → 送到我们国内仓储   ← 代购独有段，瓶颈主要在这
   ↓
国内仓储收货后转发给用户                        ← 复用自营段
```

- 报关由**签约的第三方供应链**负责（上门提货 + 报关 + 送国内仓）。
- 国内仓储收到货后**转发给用户**，这一段和自营合并复用。
- **前半段（供应商→香港仓→报关→国内仓）是代购独有的履约瓶颈**，也是后续 C1 改造的重点。
