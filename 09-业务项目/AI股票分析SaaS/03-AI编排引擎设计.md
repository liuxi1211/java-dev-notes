# AI 编排引擎设计 — 标准分层与场景 DAG

## 1. 分层架构

```
┌──────────────────────────────────────────────────┐
│ 接入层：场景 API(SSE) · 异步任务接入 · 会话与上下文管理 │
├──────────────────────────────────────────────────┤
│ 编排引擎（核心）                                     │
│  场景注册表(DAG定义·版本化)                          │
│  DAG 执行器(节点调度·检查点恢复)                      │
│  上下文管理器(token预算·子代理隔离)                   │
├──────────────────────────────────────────────────┤
│ 能力层                                             │
│  LLM 网关(模型路由·重试·核算)                        │
│  工具注册中心(取数函数·Schema声明)                    │
│  Prompt 注册中心(版本·灰度·A/B)                      │
├──────────────────────────────────────────────────┤
│ 支撑层：Trace 全链路追踪 · Eval 质量回归 · 合规守卫·计费配额 │
└──────────────────────────────────────────────────┘
```

## 2. 核心抽象：场景 = 一张 DAG，节点只有 5 种类型

整个引擎最重要的设计决策是**节点类型收敛到 5 种**（LangGraph、Anthropic 模式库同思路）：类型越少，编排越可预测，运营越容易配新场景。

| 节点类型 | 职责 | 对应原个人环境的东西 |
|---|---|---|
| `ToolNode` | 调取数函数，拿结构化数据 | 原 MCP 数据调用 |
| `LLMNode` | 单次模型调用，Prompt 引用 + 结构化输出 | 原 skill 里的分析步骤 |
| `ParallelNode` | fan-out/fan-in，子上下文隔离 | 多空对撞（见 02 文档） |
| `TransformNode` | 纯代码：清洗、计算、token 裁剪 | 数据预处理 |
| `GuardNode` | 合规过滤、置信度短路、配额检查 | 工程兜底 |

```java
public interface ScenarioNode<I, O> {
    O execute(I input, RunContext ctx);
    // RunContext 携带：traceId、用户配额、节点级重试策略、token 预算
    // 每个节点独立可测、可重试、可缓存、可打点 —— 这是 Eval 体系的地基
}
```

## 3. 场景定义 DSL（存库 + 版本化），不发版上线新场景

```yaml
# 场景：个股多空研判 v3
scenario: stock_debate
version: 3
nodes:
  pack:      { type: tool,      tools: [quote, fund_flow, financials, news] }
  debate:    { type: parallel,  workers: [bull, bear], fan_in: judge }
  bull:      { type: llm,       prompt: bull_analyst@v12, output: BullVerdict }
  bear:      { type: llm,       prompt: bear_analyst@v12, output: BearVerdict }
  judge:     { type: llm,       prompt: debate_judge@v7,  output: Verdict }
  guard:     { type: guard,     rules: [compliance_v2, conviction_short_circuit] }
edges: [ pack→debate, debate→guard, guard→output ]
```

场景、Prompt、守卫规则**全部存库带版本**，运营在后台改配置就能灰度一个新场景——这是 P3 阶段"场景配置化"的全部秘密，**架构第一天就要留好这个口**。

## 4. 编排形态：Workflow，不是 Mega-Prompt，也不是自主 Agent

> 术语（Anthropic 定义）：**Workflow** = LLM 步骤按代码预定义路径编排；**Agent** = LLM 动态自主决定下一步。

### 反模式：巨型 Prompt（mega-prompt）

把"第一步查行情、第二步分析资金流、第三步对比同业……"全塞一个提示词的问题：
- 单步失败整体重来，无法按步重试和缓存
- 无法对单步做 eval
- 改一步全链路回归

正确做法：**编排逻辑在代码里，每个节点一个小而专注的 Prompt**（Prompt Chaining 模式）：
- 每个节点的输入输出都是结构化契约，上一节点输出 JSON 直接注入下一节点 Prompt
- 单节点可独立测试、独立换模型、独立调版本
- 原 skill 迁移时天然就是"一个 skill 拆成 N 个节点"，颗粒度现成

### 何时才需要"更重的 Agent 框架"

判断标准：出现"路由本身需要 LLM 动态决定下一步调什么工具"的场景（用户自由提问、工具超过 20 个、无法穷举路径）时，再把 Router 节点升级为带 Function Calling 的自主 agent。在那之前，**确定性 DAG + 结构化契约就是最前沿的生产形态——前沿不是"更智能的框架"，而是"更受控的编排"**。

## 5. 执行通道

| 通道 | 实现 | 说明 |
|---|---|---|
| 在线快速分析 | 内存 DAG + `CompletableFuture` 并行，秒级，SSE 流式 | 挂了就挂了，用户重试 |
| 异步深度报告 | **Temporal** workflow，分钟级 | durable execution：进程崩溃后从上一个 activity 恢复，不重复烧 token；比自研检查点省一个数量级复杂度 |

## 6. 技术选型汇总

| 组件 | 选型 | 理由 |
|---|---|---|
| LLM 接入 | Spring AI 1.x | ChatClient / 结构化输出 / Advisor / 流式 |
| 在线编排 | 自研轻量 DAG（5 种节点，几百行代码） | 确定性编排不需要重框架 |
| 备选 | LangChain4j agentic graph | 出现复杂循环/条件分支图时再引入，MVP 不必 |
| 异步长任务 | Temporal | Java 原生 durable execution 行业标准 |
| Trace | OpenTelemetry + 节点级 span | 每次 LLM 调用记录 prompt 版本、token、耗时 |
