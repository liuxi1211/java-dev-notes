# 总体架构与技术选型

## 1. 目标架构：四层 + 异步通道 + 平台支撑

核心思路：把个人"Claude Code 自动匹配 Skill → 调 MCP 拿数据 → AI 分析"的链路，拆成四层可独立伸缩的服务。

```
┌─────────────────────────────────────────────────┐
│  客户端 Web / App（SSE 流式输出对话与报告）          │
└────────────────────┬────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────┐
│  API 网关：鉴权 · 限流 · 配额计费                   │
└────────────────────┬────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────┐
│  AI 编排服务（核心）                                │
│  意图路由 → 场景流水线(DAG) → Prompt 模板组装        │
│  每个 Skill 固化为一条场景流水线                     │
└─────────┬───────────────────────┬───────────────┘
          ▼                       ▼
┌──────────────────┐   ┌──────────────────────────┐
│  数据访问层        │   │  LLM 网关                 │
│  行情/三表/新闻    │   │  多模型路由·故障切换·成本核算│
│  替代个人 MCP      │   │  路由用小模型，分析用强模型  │
└──────────────────┘   └──────────────────────────┘
          │                       │
          └───────┬───────────────┘
                  ▼
┌─────────────────────────────────────────────────┐
│  异步深度报告队列（MQ）：三表预测等长任务，完成后推送   │
└─────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────┐
│  平台支撑：用户体系 · 配额计费 · 合规过滤 · 观测评估   │
│  合规过滤是 C 端证券产品的生死线                      │
└─────────────────────────────────────────────────┘
```

## 2. 核心选型（Java 生态，2026 年现状）

| 组件 | 选型 | 理由 |
|---|---|---|
| 编排层 | Spring Boot 3 + **Spring AI 1.x** | ChatClient / Prompt 模板 / Function Calling / 结构化输出 / 流式，与 Spring 栈无缝 |
| 在线编排 | **自研轻量 DAG**（5 种节点，几百行代码） | Anthropic 共识：能简单组合就不上重框架；编排是确定性的，不需要 LangGraph |
| 异步长任务 | **Temporal** | durable execution 行业标准，Java SDK 一等公民，进程崩溃从上个 activity 恢复不重复烧 token |
| 消息队列 | RocketMQ | 深度报告异步化 + 完成通知 |
| 流式输出 | SSE（SseEmitter / WebFlux） | AI 分析没有流式，用户等 30 秒必流失 |
| 存储 | MySQL（用户/订单/会话）+ Redis（上下文、行情短缓存）+ 可选向量库 | |
| 观测 | OpenTelemetry + 节点级 span | 每次 LLM 调用记录 prompt 版本、token、耗时——eval 和成本核算都靠它 |

**LLM 网关设计要点**：意图路由用便宜小模型（flash/turbo 档），深度分析用强模型，按任务分级路由；统一封装重试、故障切换（多供应商）、成本核算。

## 3. Skill → 场景流水线的固化方式

原 skill 不是直接迁移，而是拆解固化：

```java
// 每个原 skill 对应一条流水线定义
public class StockAnalysisPipeline {
    // 1. 取数计划：声明这条流水线需要哪些数据工具
    List<DataToolSpec> dataTools;   // 如: 实时行情 + 资金流 + 龙虎榜
    // 2. 数据预处理：清洗、组装成模型可读的上下文块
    // 3. Prompt 模板：从 skill 的系统提示词迁移而来，存库并做版本管理
    String promptTemplateVersion;
    // 4. 输出 Schema：结构化 JSON（观点/依据/风险/数据来源）
    Class<? extends AnalysisResult> outputSchema;
    // 5. 后处理：合规过滤 + 免责声明注入
}
```

**Prompt 模板必须存数据库做版本化**，而不是硬编码——上线后要反复调它，每次改动都要能灰度、能回滚、能 A/B。详见 [03-AI编排引擎设计](03-AI编排引擎设计.md)。

## 4. 三个最容易踩的工程坑

1. **Token 成本**：一次深度分析可能消耗几万 token。对策：
   - 行情/财报数据按时间粒度缓存（日 K 一天内不变）
   - 路由意图用便宜的小模型，分析用强模型
   - 按用户配额限流

2. **质量回归**：Prompt 改一个字，所有场景输出都可能变。对策：建 eval 集（存量问题 + 期望要点），每次改模板跑一遍打分，否则调优全靠手感。

3. **取数失败降级**：数据源超时/缺失时，流水线要能降级输出（缺哪块数据就明说"该部分暂缺"），不能整条链路挂掉。

## 5. 合规设计（C 端证券产品的生死线）

- 无证券投资咨询牌照 → 产品定位只能是**数据参考工具**，不能荐股
- 文案层：全站禁用"推荐/建议买入/目标价"类表述
- 输出层：**合规守卫节点**对模型输出做敏感词拦截，强制附加风险提示
- Prompt 层：所有分析结论性表述改写为"数据显示/历史规律表明"
- 每个 skill 迁移时 Prompt 都要按此标准重写

## 6. 在线/离线双执行通道（关键工程决策）

| 通道 | 适用场景 | 实现 | 失败策略 |
|---|---|---|---|
| 在线快速分析 | 个股速览、涨跌归因、多空研判 | 内存 DAG + CompletableFuture 并行，秒级，SSE 流式 | 挂了就挂了，用户重试 |
| 异步深度报告 | 三表预测、深度研报 | Temporal workflow，分钟级 | durable execution，从检查点恢复，不重复烧 token |
