# 意图路由设计与技术演进

## 1. 定位：编排引擎的路由入口

意图识别的准确定位：**意图 = 场景 DAG 的 key，槽位 = DAG 首节点的入参**。它的输出不是"分类标签"，而是一个结构化的路由指令。

失败成本不对称：路由错了，后面整条 DAG 白跑，token 全浪费。所以核心设计原则是**级联 + 置信度分流，低置信度不硬猜而是反问**。

## 2. 三级级联路由 + 置信度分流

生产共识（OpenAI/Anthropic agent 路由实践）：不做单点大分类器，而是级联——规则层拦截确定性的、小模型处理模糊的。

```
用户输入 + 会话上下文
      ▼
L0 · Query 改写（仅多轮时）
   「那它呢」→「贵州茅台近30日走势如何」
      ▼
L1 · 规则层（零成本，微秒级）
   股票代码/名称词表精确命中 → 补槽位后短路返回，不进 LLM
      ├─ 命中 ──────────────────────┐
      ▼ 未命中                       │
L2 · 小模型意图 + 槽位联合抽取（一次调用）│
   输出：意图 / 槽位 / 置信度 / Top-2 候选 │
      ▼                              │
   置信度分流                         │
   ├─ ≥ 0.8   直接路由场景 DAG  ◄────┘
   ├─ 0.5~0.8 Top-2 候选渲染成 UI 按钮，用户一点即定
   └─ < 0.5   反问澄清：「您是想看…还是…」
      ▼
路由指令 → 场景 DAG 执行器（intent=dag key, slots=首节点入参, 全量落库）
      ▼
bad case 回流标注 → 每周迭代 few-shot 示例
```

### 各层职责

| 层 | 实现 | 成本 |
|---|---|---|
| L0 改写 | 轻量改写（与 L2 可合并为一次调用：先输出改写后句子，再输出意图） | 一次小模型调用 |
| L1 规则 | 股票代码/名称词表（本地缓存）精确命中 | 零，微秒级 |
| L2 联合抽取 | 小模型（flash/turbo 档）+ few-shot + 结构化输出 | 便宜 |

### 置信度分流落地

| 置信度 | 行为 | 前端形态 |
|---|---|---|
| ≥ 0.8 | 直接路由进 DAG，流式执行 | 正常分析输出 |
| 0.5 ~ 0.8 | 不执行，返回 Top-2 候选 | 两个按钮：「个股速览」/「多空研判」，点一下就定 |
| < 0.5 | 反问澄清 | "您是想看贵州茅台的估值争议还是板块资金流向？" |

中间档是关键设计——**让用户一次点击替代模型赌博**。模糊输入占比不低，按钮确认的体验远好于路由错了再重来 30 秒。

## 3. 意图体系设计（先于代码）

意图识别的上限由意图体系设计决定，不由模型决定。原则：**意图集 = 场景 DAG 的 key，互斥、可枚举、不超过 15 个**；每个意图声明自己的槽位。必须有 `GENERAL_CHAT` 兜底——用户输入永远会有意图集之外的，没有兜底模型会被迫瞎贴标签。

```java
public enum Intent {
    STOCK_QUICK_VIEW,      // 个股速览     slots: code, range?
    BULL_BEAR_DEBATE,      // 多空研判     slots: code
    SECTOR_ROTATION,       // 板块轮动     slots: period?
    MOVE_ATTRIBUTION,      // 涨跌归因     slots: code, date?
    FINANCIAL_FORECAST,    // 三表预测     slots: code, years?
    GENERAL_CHAT           // 兜底闲聊     slots: none
}

public record RouteResult(
    Intent intent,
    double confidence,
    Map<String, String> slots,      // code=600519, range=30d
    String rewrittenQuery,          // L0 改写后的完整问句
    List<Intent> alternatives       // Top-2 候选，供低置信度时用
) {}
```

## 4. L2 核心实现：意图 + 槽位一次调用联合抽取

```java
@Service
public class IntentRouter {

    private final ChatClient classifier;   // 绑定便宜的小模型
    private final StockLexicon lexicon;    // 股票代码/名称词表，本地缓存

    public RouteResult route(String query, List<ChatMessage> history) {
        // L1 规则层：词表精确命中，零成本短路
        Optional<RouteResult> hit = lexicon.matchWithIntent(query);
        if (hit.isPresent()) return hit.get();

        // L2：小模型联合抽取
        String systemPrompt = """
            你是股票分析助手的路由器。将用户请求分类到以下意图之一：
            - stock_quick_view: 个股行情速览、基本信息
            - bull_bear_debate: 多空判断、该不该看好、估值争议
            - sector_rotation: 板块、行业、市场主线
            - move_attribution: 为什么涨/跌、异动归因
            - financial_forecast: 财务预测、三表建模、估值测算
            - general_chat: 以上都不属于
            同时抽取槽位：股票代码(优先6位数字或明确公司名)、时间范围。
            置信度低于0.5时如实给低分，不要猜。
            """;   // 存 Prompt 注册中心，版本化

        RouteResult r = classifier.prompt()
            .system(systemPrompt)
            .user(buildContext(query, history))   // 多轮时附最近3轮摘要
            .call()
            .entity(RouteResult.class);            // Spring AI 结构化输出

        return confidenceBranch(r);
    }
}
```

两个工程细节决定真实水位：

- **few-shot 示例动态注入**：从 bad case 库挑 3-5 条与本 query 最相近的历史纠错样本塞进 Prompt，每周回流标注，准确率持续爬升——**意图识别是运营出来的，不是一次写出来的**
- **路由 Prompt 走注册中心**：与场景 DAG 一样存库带版本，改它不发版，出问题可回滚

## 5. 两个必须建的闭环

1. **落库闭环**：每次路由结果（query / intent / confidence / 用户后续行为）全量落库。用户点纠正按钮 = 免费的高质量标注数据。
2. **评估闭环**：维护 200 条标注 query 做回归集，每次改路由 Prompt 或换模型跑一遍。没有这个，路由准确率变化完全无感知。

## 6. 意图路由技术四世代演进史

### 时间线总览

| 世代 | 时期 | 方案 | 突破 | 死穴 |
|---|---|---|---|---|
| Gen 1 | ~2015 | 关键词/正则/决策树 | 微秒级、零成本、结果确定 | 语义泛化为零，规则爆炸 |
| Gen 2 | 2015-2019 | 监督学习（BERT微调/Rasa/LUIS） | 准确率高、推理成本低 | 每意图数百条标注，加意图=重训，冷启动以月计 |
| Gen 3 | 2021-2023 | SBERT + 余弦相似度 | 零训练、冷启动快、毫秒级 | 相似≠分类、抽不了槽位、阈值玄学 |
| Gen 4 | 2024-至今 | LLM 结构化路由（小模型联合抽取） | 真语义理解、意图+槽位+置信度一次拿全 | 延迟与成本（用级联+小模型化解） |

**终局：演进不是替代，是分层吸收。** Gen1 规则→L1 短路层；Gen3 向量→bad case 检索器；Gen2 思想→评估回归集；Gen4 LLM→兜底主力。生产系统把四代叠成级联，每代从"主角"降级为"新一代表格里的一层"。（同构先例：TCP 没杀死 UDP，L3 交换没杀死路由器。）

### Gen 3 → Gen 4 转折的技术本质（最有含金量的一段）

**余弦相似度度量的是"语义距离"，不是"决策边界"。** 通用场景下两者近似等价，垂直领域系统性失灵——因为垂直领域所有意图共享同一套领域词汇，向量空间里天然挤成一团：

```
"贵州茅台为什么跌"        → move_attribution（归因）
"贵州茅台值得买吗"        → bull_bear_debate（研判）
"贵州茅台最新财报怎么样"   → financial_forecast（财务）

三句话 embedding 距离非常近——主语都是茅台、句式都是疑问、情绪都偏谨慎。
余弦相似度分不出谁是谁。
```

分类器学的是**决策边界**（"为什么"指向归因、"值得买"指向研判），向量路由只会说"这三句话都很像"。**领域越垂直、意图越细分，向量路由崩得越彻底**——股票场景恰好是它的最坏情况。

外加三个结构性缺陷：抽不了槽位（还得挂 NER，两步管道）；阈值无理论依据只能拍；无法处理否定和复合（"不用看资金面了，直接给我估值"会被路由到资金面意图——字面相似度最高）。

### Gen 4 成立的两个技术前提

1. **Structured Output（约束解码）成熟**：早期 LLM 输出 JSON 全靠祈祷，随手多个逗号解析就炸。2024 年 OpenAI Structured Outputs 等落地了约束解码——推理时用语法约束强制模型只能生成合法 JSON Schema 的 token，正确率从"大概率"变成"语法级保证"。Spring AI `.entity()` 封装了这套。这是"一次调用拿全部结果"在工程上成立的前提。
2. **小模型够便宜且够用**：意图分类不需要 GPT-4 级推理，flash/turbo 档准确率已够，成本劣势从"贵 1000 倍"缩到"绝对值可忽略"——准确率优势压倒一切。

### 为什么联合抽取优于先分类再抽槽位

不是 LLM 新发明——NLP 学术界 2019 年已验证（JointBERT、Rasa DIET 都是 joint model），LLM 只是让它从"专门训联合模型"变成"一次 API 调用"。

分两步的死法：**误差传播**。两步各自 95% 准，串起来 90%（0.95²），且第一步错第二步全白跑。

更关键是**互消歧**：意图和槽位互相提供证据。"五粮液呢"单看意图分类是个 followup 意图不明；但槽位抽取先识别出"五粮液是股票"，反帮意图判定锁定"沿用上轮意图、只换标的"。分开做两边都缺对方手里的线索。

## 7. MVP 策略

MVP 阶段如果 UI 已是显式选场景，**L1/L2 整套可先不上**——场景 key 由前端直接传入，`IntentRouter` 只做槽位抽取（"贵州茅台"→600519）。开放自由输入框后再打开 L2 分类。架构上两者是同一个接口：规则层命中率从 100% 降下来，L2 自然接管流量。
