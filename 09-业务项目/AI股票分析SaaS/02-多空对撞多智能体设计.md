# 多空对撞多智能体设计

## 1. 模式定性：受控多智能体，不是自主多智能体

需求：分析股票时用两个独立上下文分别做多头、空头判断，然后交给主上下文裁决综合。

行业前沿（Anthropic《Building Effective Agents》、OpenAI《A Practical Guide to Building Agents》，2024-2025 生产级共识）的明确结论：

> 生产系统里，**自主多智能体（agent 自己决定 spawn 谁、调什么）尽量少用**；主流做法是**确定性代码编排 + 隔离上下文的 LLM 工人**。

本设计对应 **Orchestrator-Workers 模式** + **对抗辩论（Adversarial Debate）** 变体——与 Anthropic 自己的多智能体研究系统同构：lead agent 不自己干活，spawn 多个 subagent 各自带独立上下文窗口研究，结果回传给 lead 综合。

## 2. 四条工程铁律（缺一条辩论就失效）

1. **数据包统一**：多头和空头必须注入**同一份数据包**。辩论的意义是解释分歧，不是信息不对称——两边看到的数据不同，综合结果毫无意义。
2. **上下文完全隔离**：多头看不到空头的输出（反之亦然），只在裁决阶段汇合。否则先输出的一方会锚定另一方。
3. **结构化裁决契约**：子代理不返回自由文本，返回固定 Schema 的 JSON（立场/置信度/证据链/失效条件），裁决 Prompt 才稳定可测。
4. **确定性短路**：双方置信度都低于阈值时，代码直接短路输出"信号不足"，不进裁决——工程兜底优先于模型自觉。

## 3. 执行流程

```
用户研判请求
      ▼
编排器 · 组装统一数据包（多空双方注入完全相同的证据）
      ▼ fan-out（并行）
┌─────────────────────┐   ┌─────────────────────┐
│ 多头子代理（独立上下文）│   │ 空头子代理（独立上下文）│
│ 只做单边论证          │   │ 只做空头论证          │
│ 输出结构化裁决 JSON    │   │ 输出结构化裁决 JSON    │
└─────────┬───────────┘   └──────────┬──────────┘
          └─────── fan-in ────────────┘
                     ▼
主上下文 · 裁决综合（多空证据对撞 + 数据摘要）
  ├─ 双方皆低置信 → 代码短路输出「信号不足」
                     ▼
合规守卫 · 输出过滤
                     ▼
结构化研判结果（SSE）
```

上下文互相隔离的目的：避免锚定效应。

## 4. Java 实现（编排逻辑是普通代码，不是框架魔法）

```java
@Service
public class BullBearDebateService {

    private final LlmGateway llmGateway;      // 封装 Spring AI ChatClient 的异步调用
    private final DataPackService dataPackService;
    private final ComplianceGuard complianceGuard;

    public DebateResult judge(String stockCode) {
        // 铁律1：同一份数据包，双方证据完全一致
        MarketDataPack pack = dataPackService.build(stockCode);  // 行情+资金流+财报+新闻

        // 铁律2：并行 + 上下文隔离（两个独立调用，互不可见）
        CompletableFuture<BullVerdict> bull = llmGateway.callAsync(
                LlmTask.of(PromptRef.of("bull_analyst", "v12"), pack, BullVerdict.class));
        CompletableFuture<BearVerdict> bear = llmGateway.callAsync(
                LlmTask.of(PromptRef.of("bear_analyst", "v12"), pack, BearVerdict.class));

        var b = bull.join();
        var r = bear.join();

        // 铁律4：确定性短路，不依赖模型自觉
        if (b.conviction() < 0.4 && r.conviction() < 0.4) {
            return DebateResult.insufficientSignal(stockCode);
        }

        // 裁决：主上下文拿到 双方结构化裁决 + 数据摘要
        Verdict verdict = llmGateway.call(
                LlmTask.of(PromptRef.of("debate_judge", "v7"),
                           pack.summary(), b, r, Verdict.class));

        // 合规过滤在出口
        return complianceGuard.sanitize(DebateResult.of(b, r, verdict));
    }
}
```

## 5. 结构化裁决契约（整个模式可测试的关键）

```json
{
  "stance": "bull",
  "conviction": 0.72,
  "thesis": "核心逻辑一句话",
  "evidence": [
    { "claim": "北向连续5日净流入", "data_ref": "pack.fund_flow" }
  ],
  "invalidated_by": ["若跌破20日均线且放量，本逻辑失效"]
}
```

**`invalidated_by`（失效条件）字段是点睛之笔**：它让裁决阶段可以做**证据对撞**——空头的证据如果命中多头的失效条件，裁决就有了结构化依据，而不是各说各话。

`data_ref` 指回数据包字段，保证证据可溯源、可校验（防止模型编造数据）。

## 6. 设计要点备忘

- 子代理 Prompt（bull_analyst / bear_analyst / debate_judge）全部走 Prompt 注册中心版本化管理，与场景 DAG 一起迭代
- 裁决节点的输入只给 `pack.summary()` 而非全量数据包——控制裁决上下文的 token 预算，裁决靠的是双方论证质量而非重新读原始数据
- 该模式天然映射到编排引擎的 `ParallelNode`（fan-out/fan-in，子上下文隔离），见 [03-AI编排引擎设计](03-AI编排引擎设计.md)
