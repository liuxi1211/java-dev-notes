# 虚拟线程落地四大坑详解（Pinning / ThreadLocal / 生态 / 场景错配）

> 源自对公众号文章《Java 虚拟线程已凉》（涛哥）的分析讨论。文章结论：虚拟线程没凉，是"百万并发银弹"的宣传失败了；它正在成为 Java 21+ 新项目的默认选项，存量项目门槛在迁移成本而非技术本身。

## 背景：虚拟线程的工作原理

虚拟线程不与 OS 线程 1:1 映射，而是挂载（mount）到少数**载体线程（carrier，平台线程）**上。核心机制：

- 执行到 I/O 阻塞点（socket read 等）时，虚拟线程从载体线程**卸载（unmount）**，载体线程去跑其他虚拟线程——这是省资源的核心。
- 卸载前提：虚拟线程调用栈必须能完整搬走。

## 一、Pinning（钉住）问题

**触发条件（Java 21）**：
1. 在 `synchronized` 块内部发生阻塞（栈被监视器锁钉在载体线程上）
2. JNI / 本地方法执行期间阻塞

```java
// 事故代码：synchronized 内做 I/O
public String fetchUser(long id) {
    synchronized (lock) {
        return httpClient.send(...).body();  // 阻塞时无法卸载
    }
}
```

**症状**：载体线程池默认 = CPU 核数（如 8），大量任务被 pin 住时并发度骤降为 8，吞吐反而不如传统线程池——"假并发"。

**诊断**：`-Djdk.tracePinnedThreads=full`，输出中 `monitors:1` 标记即为钉住点。

**解法**：
- Java 21：`synchronized` 换 `ReentrantLock`
- Java 24（JEP 491）：JVM 重写 synchronized 实现，阻塞时也可卸载，根治。但主流生产环境还在 8/11/17，享受不到。

## 二、ThreadLocal 问题

**冲突本质**：传统模型线程几十~几百个，ThreadLocal 成本可忽略；虚拟线程"每任务一线程"，一天创建百万级线程，重量级 ThreadLocal 成本被指数放大。

**经典事故场景：MDC**

```java
MDC.put("traceId", req.getTraceId());  // logback MDC 本质是 ThreadLocal<Map>
```

三个具体问题：
1. **线程不复用 → MDC 失效**：虚拟线程每次是新线程，父线程 MDC 不自动传递，日志大量丢 traceId，链路追踪断裂。
2. **GC 压力**：每线程一份 HashMap，年轻代分配速率飙升，minor GC 频率可翻数倍。
3. **`InheritableThreadLocal` 语义崩坏**：虚拟线程由调度器创建而非父业务线程，继承关系错乱。

**解法：ScopedValue**（Java 21 预览，Java 25 转正）

```java
private static final ScopedValue<TraceContext> TRACE = ScopedValue.newInstance();

ScopedValue.where(TRACE, new TraceContext(traceId)).run(() -> service.doBusiness());
// 出作用域自动失效，天然防泄漏、不可变
```

**现实痛点**：logback / skywalking / 事务管理器底层都是 ThreadLocal 实现，单方面改 ScopedValue 无用，需生态整体跟进。

## 三、框架生态"半支持"

不是单一 bug，是一堆"能跑但体验退化"的碎片：

| 组件 | 问题 | 修复版本 |
|---|---|---|
| MySQL Connector/J | 驱动内部 synchronized 导致 pinning，应用层不可见 | 8.0.33+ |
| 线程命名 | 虚拟线程默认无名/一次性名字，线程 dump 无法定位请求，监控大盘退化 | 需改用 JFR + 任务命名 |
| log4j2 / Spring Boot | ThreadContext 兼容问题；Tomcat 需 SB 3.2+ 且 `spring.threads.virtual.enabled=true` | SB 3.2+ |

任一组件版本不齐 → 偶发诡异问题，排查成本极高。

## 四、场景错配：CPU 密集型无收益

虚拟线程只解决"I/O 等待期间占着 OS 线程干等"的浪费���CPU 密集任务（转码、加解密、ETL）：

- 吞吐与平台线程完全一样（CPU 就那几个核），还多付 mount/unmount 调度开销
- 失去线程池 `setCorePoolSize` 的天然限流能力，无上限任务反而加剧上下文切换

```java
// 正确姿势
// I/O 密集 → 虚拟线程
Executors.newVirtualThreadPerTaskExecutor();
// CPU 密集 → 固定平台线程池 = 核数
Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());
```

## 总结

| 问题 | 触发条件 | 症状 | 解法 |
|---|---|---|---|
| Pinning | synchronized 内阻塞 I/O | 并发度=核数，吞吐骤降 | ReentrantLock / Java 24 JEP 491 |
| ThreadLocal | MDC/事务上下文 + 海量线程 | 丢 traceId、GC 飙升 | ScopedValue（待生态跟进） |
| 生态半支持 | 老驱动/监控/日志版本 | 偶发诡异问题 | 全链路版本升级 |
| 场景错配 | CPU 密集任务 | 无收益甚至更慢 | 混用两种线程池 |

四个问题共同点：不是"不能用"的证据，而是**从线程池思维切换过来的隐性迁移成本**——新技术已成熟，迁移的经济账不好算（JDK 8→21 + SB 2→3 + 全链路压测 ≈ 数月人力，收益不挂钩业务需求）。

最值得记住的观察：**最需要虚拟线程的 I/O 密集型服务，往往也是技术债最重、最不敢动的服务**——供给（技术）与需求（场景）的错位才是"落地慢"的根源。
